# APP 测试理论

> APP 测试是针对安装在移动设备上的应用程序进行的质量验证。除了验证业务功能，还要重点关注设备、系统、网络、权限、性能和移动场景对 APP 的影响。

## 一、APP 测试与 Web 测试的区别

| 对比项 | APP 测试 | Web 测试 |
| --- | --- | --- |
| 运行环境 | 手机、平板等移动设备 | 浏览器 |
| 版本更新 | 用户可能长期不更新，多版本并存 | 服务端更新后用户通常直接使用新版本 |
| 兼容性 | 品牌、机型、系统版本、屏幕、CPU 等 | 浏览器种类、版本和分辨率 |
| 特有场景 | 安装、卸载、升级、中断、弱网、权限、前后台 | 页面跳转、浏览器缓存、Cookie 等 |
| 性能关注 | 启动时间、CPU、内存、流量、耗电、发热 | 页面响应、并发和服务器资源 |

APP 测试不是只把 Web 的功能测试在手机上再执行一遍，而是要补充移动端特有的测试场景。

## 二、APP 测试的核心思路

可以从以下六个角度分析一个 APP：

1. **功能是否正确**：业务流程和数据处理是否符合需求。
2. **在哪些设备上可以正常使用**：不同品牌、机型、系统和屏幕下是否兼容。
3. **环境变化时是否稳定**：网络切换、来电、锁屏、前后台切换时是否出错。
4. **长时间使用是否流畅**：是否卡顿、闪退、发热或资源占用过高。
5. **用户数据是否安全**：权限、隐私、登录态和敏感数据是否正确处理。
6. **出现异常后能否恢复**：失败时有无明确提示，重试后数据是否重复或丢失。

## 三、功能测试

功能测试的基本方法与普通软件一致，需要覆盖正常、异常、边界和状态变化。

### 基本测试点

- 实际功能是否与需求、原型和设计稿一致。
- 业务主流程能否正常完成。
- 必填项、输入长度、数据类型和边界值限制是否正确。
- 重复点击、快速操作、连续提交时是否产生重复数据。
- 返回、取消、重试、刷新后的页面和数据状态是否正确。
- 多账号或多角色之间的数据和权限是否隔离。
- APP 端、Web 端和服务端之间的数据是否一致。

### 状态测试

一个功能要考虑不同用户状态，例如：

- 未登录、已登录、登录过期。
- 新用户、普通用户、VIP 用户、被禁用用户。
- 无数据、少量数据、大量数据。
- 正常请求、请求超时、服务异常。
- 首次进入、再次进入、从后台恢复。

## 四、安装、卸载与升级测试

### 安装测试

- 从官方应用商店、安装包、二维码等不同入口安装。
- 首次安装能否成功，安装后图标、名称和版本号是否正确。
- 存储空间不足、网络中断、安装被取消时提示是否正确。
- 低于最低支持系统版本时是否被正确拦截。
- 覆盖安装和重复安装时是否异常。

### 卸载测试

- 能否正常卸载。
- 卸载后图标、主程序和应清理的本地数据是否移除。
- 重新安装后是否出现旧数据异常恢复、旧账号自动登录等问题。
- 云端业务数据不应因卸载 APP 而丢失。

### 升级测试

- 从上一个正式版本升级到当前版本。
- 跨多个版本升级。
- 强制更新与非强制更新流程是否正确。
- 更新过程中取消、断网、锁屏或空间不足时能否正确处理。
- 升级后账号登录态、用户数据、设置和缓存是否正确。
- 升级后核心业务和新功能是否正常。
- 新旧客户端与服务端的接口是否兼容。

> [!tip] 升级测试重点
> 不能只验证“新版本能安装”，还要验证“旧用户的数据和业务能平稳过渡”。

## 五、兼容性测试

兼容性测试用于确认 APP 在不同设备和系统环境下能否正常运行。

### 覆盖维度

- **操作系统**：Android、iOS 及其不同版本。
- **设备品牌与机型**：主流品牌、主流机型和目标用户常用机型。
- **硬件配置**：CPU、内存、存储空间和高低端设备。
- **屏幕**：分辨率、屏幕尺寸、横竖屏、刘海屏、挖孔屏和折叠屏。
- **系统设置**：深色模式、字体大小、系统语言和时区。
- **网络环境**：Wi-Fi、5G/4G、弱网和无网。

### 机型选择原则

实际项目不可能覆盖所有机型，应优先选择：

1. 用户占比高的机型和系统版本。
2. 业务要求明确支持的最低和最高系统版本。
3. 高端、中端和低端设备。
4. 历史上问题较多的品牌或机型。
5. 新系统版本和新型屏幕设备。

## 六、交叉事件测试（中断与前后台）

交叉事件测试是指：用户正在 APP 中执行某项业务时，插入另一个系统事件或应用事件，验证 APP 在被打断以及恢复后的显示、数据和业务状态是否正确。

### 设计思路

```text
当前业务 + 事件发生时机 + 交叉事件 + 恢复后验证
```

设计测试时重点考虑：

- **业务类型**：普通浏览、表单填写、上传下载、音视频、订单提交和支付等。
- **发生时机**：操作前、操作中、请求已发出但尚未返回、操作刚完成时。
- **APP 状态**：前台、后台、锁屏或进程被系统回收。
- **恢复方式**：继续执行、重试、取消、回滚或重新进入。
- **结果验证**：页面、业务状态、本地数据和服务端数据是否一致。

### 常见中断场景

- 来电、短信、闹钟、系统通知。
- 锁屏、解锁和屏幕超时关闭。
- 切换到其他 APP，再返回当前 APP。
- 切换前后台、杀掉进程后重启。
- 音乐、视频播放时被其他声音打断。
- 拍照、选图、定位、支付等跳转第三方应用后再返回。
- 低电量提示、充电状态变化和设备关机。

### 验证重点

- APP 是否闪退、卡死、黑屏或白屏。
- 中断前填写的内容是否需要保留。
- 业务是继续、重试、取消还是回滚，是否符合设计。
- 订单、支付、提交等重要操作是否出现重复或数据不一致。
- 返回 APP 后页面、弹窗、键盘和焦点是否正常。

## 七、网络测试

### 网络类型

- Wi-Fi、5G/4G 等正常网络。
- 高延迟、低带宽、高丢包等弱网。
- 无网络。
- Wi-Fi 与移动网络之间切换。
- 正常网络、弱网和无网之间反复切换。

### 验证重点

- 无网或超时时是否给出准确、可理解的提示。
- 是否提供重试机制，恢复网络后能否继续操作。
- 是否重复提交订单、支付或表单。
- 加载中、空数据、请求失败是否有区分。
- 页面是否长时间转圈、假死或无法操作。
- 图片、视频和大文件在弱网下的加载、暂停、重试和断点续传是否正确。
- 本地缓存数据的展示和网络恢复后的同步是否正确。

> [!warning] 高风险场景
> 在“提交成功但客户端未收到响应”的情况下，用户可能重复点击。此时要重点检查接口幂等性、订单状态查询和重复提交防护。

## 八、权限测试

常见权限包括相机、相册、麦克风、定位、通知、蓝牙和通讯录等。

### 测试场景

- 首次使用功能时才申请对应权限，不应无理由提前索取。
- 允许权限后功能是否正常。
- 拒绝权限后 APP 是否闪退，是否有可理解的提示和替代操作。
- 选择“仅使用期间允许”、“仅允许一次”或“仅限部分照片”时是否正常。
- 拒绝后再次使用功能，引导是否符合系统规则。
- 在系统设置中关闭、开启权限后，APP 状态是否及时刷新。
- 功能无关时不应读取对应权限和数据。

## 九、通知与消息推送测试

### PUSH 的基本原理

PUSH 是服务端向指定用户或设备主动发送消息的机制，用户不需要一直打开 APP 或手动刷新。

```text
业务服务端
    ↓ 创建推送任务
推送服务（系统或厂商通道）
    ↓ 根据设备标识发送
手机操作系统
    ↓
通知栏或 APP
```

设备安装并启动 APP 后，通常会获取用于标识设备和 APP 实例的 Token。业务服务端需要正确维护“用户、账号、设备与 Token”的绑定关系，才能把消息发给正确对象。

### 常见消息形式

- **通知栏消息**：由系统在通知栏展示标题和内容，用户点击后打开 APP 或指定页面。
- **透传/数据消息**：推送通道将数据交给 APP，由 APP 决定如何解析、保存和展示。
- **APP 内消息**：用户打开 APP 后在消息中心、弹窗或角标中看到的消息，需要与通知栏消息区分验证。

### 测试前的关键条件

- 推送的用户、账号、设备和 Token 绑定正确。
- 手机网络正常，系统通知权限符合测试前置条件。
- APP 的前台、后台和进程结束状态明确。
- 手机的勿扰模式、省电策略、后台限制和通知分类设置符合测试预期。
- 测试前记录 APP 版本、设备、系统、账号、推送任务和发送时间。

### 核心测试点

- APP 在前台、后台和进程被结束时能否收到通知。
- 登录、未登录和切换账号后，消息接收对象是否正确。
- 通知标题、内容、图标、时间和未读数是否正确。
- 点击通知能否跳转到正确页面，未登录时是否先完成登录。
- 多条通知的排序、合并、覆盖和去重是否正确。
- 关闭系统通知权限后，APP 是否正确引导用户。
- 用户退出账号后，是否仍能收到上一个账号的敏感消息。
- 单个用户、指定用户组、全量用户和定时推送的范围与时间是否正确。
- 同一账号登录多台设备时，推送策略是否符合业务设计。
- 离线期间的消息在恢复网络后是否补发，是否出现丢失或重复。
- 升级、卸载重装、清除 APP 数据后，Token 更新和旧 Token 失效是否正确。

### 收不到 PUSH 时的排查顺序

1. 确认业务服务端是否成功创建推送任务。
2. 确认推送对象、账号、标签和发送时间是否正确。
3. 确认设备 Token 是否存在、有效并与当前用户正确绑定。
4. 确认手机是否联网，推送通道是否返回异常。
5. 检查系统通知权限、通知分类、勿扰模式和省电/后台限制。
6. 分别在 APP 前台、后台和进程结束状态下对比验证。
7. 查看 APP 日志，确认是“未收到消息”还是“已收到但解析或展示失败”。
8. 如果可以展示但点击无效，继续检查跳转参数、登录状态和目标页面路由。

## 十、界面与易用性测试

- 页面是否与设计稿一致，布局、颜色、字体、图标和间距是否正确。
- 刘海、挖孔、状态栏、导航栏和底部安全区是否遮挡内容。
- 横竖屏切换后布局和数据是否正确。
- 弹出键盘后输入框和按钮是否被遮挡，键盘类型是否正确。
- 连续点击、滑动、缩放和返回操作是否符合用户习惯。
- 按钮的可点击区域是否合理，是否存在误触。
- 加载、无数据、失败、禁用和成功等状态是否有明确反馈。
- 开启大字体、深色模式或其他辅助功能后是否可用。

## 十一、性能与稳定性测试

APP 性能测试不能只记录一个瞬时数值。应在固定的设备、版本、网络、数据和业务步骤下重复测试，结合平均值、峰值、趋势、异常发生时间和用户感受进行分析。

### 常见指标概览

- **启动时间**：冷启动、热启动和从后台恢复的时间。
- **CPU**：普通使用和高负载操作时的 CPU 占用。
- **内存**：长时间使用后内存是否持续增长，是否存在内存泄漏。
- **流畅度**：页面滑动、动画和页面切换是否卡顿。
- **网络流量**：前台、后台和静置时是否产生不必要的流量。
- **耗电与发热**：长时间定位、视频、音频或后台运行是否异常耗电和发热。
- **安装包大小**：是否符合项目目标，是否存在不必要的资源。

### 通用测试流程

1. **明确目标**：确认要测的指标、核心场景和项目验收标准。
2. **固定变量**：记录设备、系统、APP 版本、网络、电量、屏幕亮度和测试数据。
3. **准备环境**：关闭与测试无关的应用，保证每轮的初始状态尽量一致。
4. **记录基线**：先记录 APP 未执行目标操作时的初始数据。
5. **执行固定场景**：按相同步骤和时长执行操作，同时记录关键时间点。
6. **重复测试**：避免使用单次结果下结论，必要时和旧版本或竞品使用相同条件对比。
7. **分析结果**：关注平均值、峰值、持续时间、恢复情况和异常时对应的业务操作。

> [!important] 性能结论的前提
> 不同设备、系统和业务的合理范围不同。应优先使用项目验收标准、历史基线和相同环境的对比数据，不要脱离场景套用单一阈值。

### CPU 测试

CPU 占用反映 APP 在某个时间段内使用处理器资源的情况。除了峰值，还要关注高占用是否长时间持续、离开页面后能否回落。

#### 测试步骤

1. 启动性能监控工具，记录 APP 静置时的 CPU 基线。
2. 分别执行页面加载、快速滑动、图片处理、音视频和核心业务。
3. 记录平均占用、峰值、高占用持续时间和对应操作。
4. 停止操作或退出页面，观察 CPU 是否回落到合理水平。

#### 常见问题

- 页面静置或 APP 进入后台后，CPU 仍持续高占用。
- 退出页面后异常任务、计时器或定位仍在运行。
- 某个操作的 CPU 峰值与卡顿、发热或耗电同时出现。

### 内存测试

内存测试不只看“占用多少”，更要看重复操作后是否持续增长，离开页面或停止业务后是否能够恢复。

#### 测试步骤

1. 启动 APP 并稳定一段时间，记录初始内存。
2. 按固定次数反复进入退出页面、加载图片、刷新列表或执行核心流程。
3. 记录每个阶段的内存、峰值和增长趋势。
4. 停止操作并退出相关页面，观察内存是否回落。
5. 对持续增长且无法恢复的场景，结合工具和日志进一步排查。

#### 常见问题

- 重复进出页面后内存持续阶梯式上升。
- 大图、列表、视频或页面对象使用完后没有正常释放。
- 内存过高导致系统回收进程、卡顿或闪退。

### 流畅度测试

流畅度主要关注界面渲染是否连续，常结合帧率、单帧耗时、卡顿帧/丢帧和用户实际感受判断。

#### 测试步骤

1. 选择首页滑动、长列表、页面切换、动画、输入和大图加载等场景。
2. 启动帧率或帧耗时监控，按固定方式执行操作。
3. 记录明显卡顿的时间点、对应页面和当时的 CPU、内存状态。
4. 在高、中、低端设备上对比，验证卡顿是否只在特定配置下出现。

#### 结果分析

- 不要只看平均帧率，短时间的严重卡顿可能被平均值隐藏。
- 帧率需要结合设备刷新率、页面目标帧率和实际场景分析。
- 发现卡顿后要关联同一时间点的 CPU、内存、网络和日志。

### 流量测试

流量测试要分别记录上行、下行和总流量，并分析流量是由正常业务、重复请求、资源未缓存还是后台异常请求产生。

#### 测试步骤

1. 清理或保留缓存，并在结果中明确记录当前条件。
2. 清零流量统计，分别执行首次加载、再次加载、图片/视频浏览和核心业务。
3. 记录上行、下行、总流量和请求次数。
4. 将 APP 切换到后台或静置，观察是否仍持续产生不必要流量。
5. 对比新旧版本在相同操作下的差异。

#### 常见优化方向

- 减少重复或过于频繁的接口请求。
- 对图片、静态资源和可复用数据合理使用缓存。
- 根据展示需要使用合适的图片尺寸、压缩和分页策略。
- 减少 APP 静置或后台时非必要的轮询和上报。

### 电量与发热测试

电量测试需要关注单位时间耗电、耗电趋势和设备发热，并结合 CPU、网络、定位、音视频、蓝牙和后台任务分析。

#### 测试步骤

1. 固定设备、初始电量范围、屏幕亮度、音量、网络和测试时长。
2. 记录测试前的电量、温度和后台应用情况。
3. 持续执行视频播放、定位、导航、下载、上传或核心业务等固定场景。
4. 记录测试后的电量、温度和单位时间耗电。
5. 在相同条件下重复测试，必要时与旧版本或系统待机状态对比。

#### 常见问题

- APP 在后台仍持续定位、频繁请求网络或唤醒设备。
- 长时间高 CPU、高帧率或高强度音视频处理导致耗电和发热。
- 退出相关功能后，定位、相机、麦克风或传感器仍在使用。

### APP 启动速度测试

- **冷启动**：APP 进程不存在，系统需要创建进程并完成初始化。
- **热启动**：APP 进程仍然存在，通常从后台恢复到前台。

#### 起止点

启动时间的统计口径必须统一。常见起点是用户点击图标或系统收到启动指令，常见终点是首屏已完成必要渲染并可以进行主要操作。

#### 测试步骤

1. 固定设备、系统、网络、账号状态和首页数据。
2. 冷启动前确认 APP 进程已结束；热启动前确认 APP 仍在后台。
3. 使用同一工具和统一起止点分别重复测量。
4. 记录每次结果，分析平均值、最慢值和波动情况。
5. 对异常慢的次数结合启动阶段、主线程、网络请求和首屏渲染进行分析。

### 稳定性场景

- 长时间连续运行核心业务。
- 快速、反复进入和退出页面。
- 大量列表数据的加载和滑动。
- 反复切换前后台、网络和横竖屏。
- 存储空间或内存较低时使用 APP。
- 并发上传、下载、播放或多任务操作。

发现闪退、无响应或卡死时，应记录设备信息、系统版本、APP 版本、操作步骤、发生时间和日志。

## 十二、安全与隐私测试

- 密码、验证码、Token、身份证和银行卡等敏感信息不应明文展示或记录。
- 登录过期、退出登录和修改密码后，旧 Token 应失效。
- 切换账号后，不应看到上一个账号的缓存数据。
- 截图、最近任务缩略图和剪贴板不应泄露高敏感信息。
- 深层链接、通知和第三方跳转不应绕过登录或权限校验。
- 用户拒绝隐私政策时，不应提前采集非必要数据。
- 权限申请应符合最小必要原则，并告知用途。
- 日志、埋点和错误上报中不应包含完整敏感数据。

> [!note]
> 安全测试不只是“能不能攻击成功”，也包括越权、会话失效、敏感信息泄露和隐私合规等日常测试点。

## 十三、数据与缓存测试

- 首次启动、清除缓存和清除数据后 APP 是否正常。
- 缓存数据是否过期，是否可以正确刷新。
- 前端、接口和数据库中的数据是否一致。
- 断网时产生的本地数据，联网后是否正确同步。
- 时区、系统时间和语言变化后，日期、时间和金额是否正确。
- 升级、卸载重装和切换账号后的数据保留规则是否符合设计。

## 十四、常用测试工具

- **ADB**：安装、卸载 APP，查看设备信息、进程和 Android 日志。详见 [[01_通用技术栈/08_专项测试工具/ADB/ADB命令|ADB 命令]]。
- **Fiddler/Charles**：抓取和修改网络请求，辅助定位前后端问题。详见 [[01_通用技术栈/08_专项测试工具/Fiddler/fiddler笔记|Fiddler]]。
- **GT（课程演示工具）**：用于监控 CPU、内存、流畅度、流量和电量等性能数据；学习时重点掌握“固定场景、开始采集、保存数据、对应操作、分析趋势”的通用方法。
- **Android Studio Profiler**：分析 Android APP 的 CPU、内存和网络使用情况。
- **Xcode Instruments**：分析 iOS APP 的性能、内存和耗电情况。
- **Appium**：执行 Android 和 iOS 端的 UI 自动化测试。
- **Monkey**：通过随机事件进行 Android APP 稳定性测试。

## 十五、APP 测试基本流程

1. **需求分析**：理解业务、用户、系统要求和风险。
2. **确定范围**：明确本次版本的新功能、改动点和回归范围。
3. **准备环境**：准备账号、数据、安装包、机型、系统和网络环境。
4. **设计用例**：覆盖功能、异常、边界、兼容、中断、网络、权限和性能。
5. **冒烟测试**：先确认 APP 可安装、可启动，且核心流程可测。
6. **执行与提缺陷**：记录环境、步骤、实际结果、期望结果、截图/录屏和日志。
7. **回归测试**：验证缺陷修复，并检查相关功能是否受影响。
8. **发布评估**：结合用例执行、缺陷、兼容性和风险情况给出结论。

## 十六、发布前快速检查清单

- [ ] 安装、启动、升级和卸载正常。
- [ ] 登录、首页和核心业务流程通过。
- [ ] 主流机型和目标系统版本通过。
- [ ] 无网、弱网和网络切换时处理正常。
- [ ] 来电、锁屏和前后台切换后 APP 正常。
- [ ] 拒绝、关闭或再次开启权限时处理正常。
- [ ] 通知推送、点击跳转和未读状态正常。
- [ ] 无严重卡顿、闪退、无响应、发热或异常耗电。
- [ ] 账号、权限、隐私和敏感数据处理正确。
- [ ] 版本号、应用名称、图标和更新说明正确。
- [ ] 遗留缺陷已评估，无阻断发布的高风险问题。

## 十七、常见面试题

### 1. 你是怎么测试一个 APP 的？

可以按以下思路回答：

> 首先分析需求和业务风险，确定本次版本的测试范围。功能方面会覆盖正常流程、异常流程、边界值和数据一致性；移动端专项方面会测试安装升级、兼容性、弱网、中断、前后台、权限、通知、性能、安全和隐私。测试完成后再根据用例执行率、缺陷情况和遗留风险评估是否可以发布。

### 2. APP 的弱网测试怎么做？

> 我会模拟高延迟、低带宽和丢包环境，同时覆盖无网、弱网恢复以及 Wi-Fi 和移动网络切换。重点检查页面提示、超时和重试机制，并特别关注订单、支付等操作是否出现重复提交或数据不一致。

### 3. APP 闪退时怎么定位？

1. 记录设备型号、系统版本、APP 版本和发生时间。
2. 确认稳定的复现步骤和前置数据。
3. 对比其他机型、账号和网络环境，缩小问题范围。
4. Android 可使用 ADB 抓取 logcat，iOS 可查看设备分析数据或崩溃日志。
5. 结合日志中的异常堆栈、页面、时间点和最后一步操作协助开发定位。

### 4. APP 的兼容性测试怎么选机型？

> 不会平均选择机型，而是结合用户机型占比、系统版本、项目最低支持范围、高中低端配置和历史缺陷数据选择测试矩阵。先覆盖主流用户，再覆盖边界系统和高风险机型。

## 十八、一句话总结

> APP 测试 = 业务功能测试 + 移动端特有场景测试。核心是验证 APP 在不同设备、系统、网络、权限和中断环境下，仍能正确、稳定、安全地完成业务。
