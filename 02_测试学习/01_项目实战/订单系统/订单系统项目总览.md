# 订单系统项目总览

## 项目背景/业务描述

订单系统是电商业务的核心链路，负责把用户的购买行为转化成可支付、可履约、可售后的交易记录。

本项目参考 `E:\CRMEB\CRMEB` 源码进行学习。CRMEB 是一个电商系统，订单模块不是单独的一个接口，而是由商品、购物车、用户地址、优惠券、支付、物流、售后、发票、后台管理等多个模块共同组成。

我基于这个项目学习和开发接口自动化框架，重点不是只会调用接口，而是理解真实业务接口之间的数据依赖、状态流转、数据库落库结果和异常处理。

## 系统分层理解

从源码看，CRMEB 的订单模块大致是下面这种分层：

```text
前端页面/小程序/移动端
    ↓
template/uni-app/api/order.js
    ↓
app/api/route/v1.php
    ↓
app/api/controller/v1/order
    ↓
app/services/order
    ↓
app/dao/order
    ↓
app/model/order
    ↓
MySQL 数据表
```

接口自动化测试主要站在接口层发起请求，但不能只看接口返回，还要理解 Service 层做了什么业务处理，最后再结合数据库验证业务结果是否正确。

## 核心业务链路

### 正向主流程

```text
用户登录
    ↓
浏览商品/选择规格
    ↓
加入购物车或立即购买
    ↓
订单确认
    ↓
计算订单金额
    ↓
创建订单
    ↓
订单支付
    ↓
后台发货
    ↓
用户确认收货
    ↓
订单完成/评价
```

### 逆向流程

```text
未支付订单 -> 用户取消/系统超时取消
已支付订单 -> 申请退款/售后
已发货订单 -> 申请退货退款 -> 填写退货物流 -> 后台审核退款
已完成订单 -> 删除订单/评价
```

### 状态理解

订单状态不能只看一个字段，实际要结合多个字段判断：

| 业务状态 | 关键字段理解 |
| ---- | ---- |
| 待支付 | `paid = 0`，订单已创建但未支付 |
| 待发货 | `paid = 1`，`status = 0` |
| 待收货 | `paid = 1`，`status = 1` |
| 已收货/待评价 | `paid = 1`，`status = 2` 或 `status = 3` |
| 已取消 | `is_cancel = 1` 或订单被系统取消 |
| 已删除 | `is_del = 1` 或 `is_system_del = 1` |
| 退款中 | `refund_status = 1` 或售后表存在申请记录 |
| 已退款 | `refund_status = 2` 或退款单完成 |

这也是自动化测试中需要注意的点：不能简单把订单状态理解成一个枚举字段，很多业务判断是组合状态。

## 认证和响应格式

用户端接口通过 `AuthTokenMiddleware` 鉴权，请求头中会读取：

```text
Authori-zation: Bearer <token>
```

源码中也兼容：

```text
Authorization: Bearer <token>
```

统一响应由 `crmeb\utils\Json` 生成，常见结构是：

```json
{
  "status": 200,
  "msg": "success",
  "data": {}
}
```

失败时常见结构是：

```json
{
  "status": 400,
  "msg": "错误信息或错误码"
}
```

部分接口会使用业务状态包装，例如创建订单、支付订单时，`data` 中可能包含：

```json
{
  "status": "SUCCESS",
  "result": {
    "orderId": "订单号",
    "key": "订单缓存 key"
  }
}
```

所以接口自动化断言不能只写 HTTP 状态码，还要检查响应体中的 `status`、`msg`、`data`、`data.status`、`data.result` 等字段。

## 数据库核心表

CRMEB 的 Model 中使用无前缀表名，例如 `store_order`，实际安装 SQL 中有 `eb_` 前缀。

| 表名 | 作用 | 自动化校验关注点 |
| ---- | ---- | ---- |
| `eb_user` | 用户表 | 登录用户、用户余额、积分 |
| `eb_store_product` | 商品表 | 商品状态、库存、价格 |
| `eb_store_product_attr_value` | 商品规格表 | SKU 库存、规格价格 |
| `eb_store_cart` | 购物车表 | 加购记录、数量、是否已购买 |
| `eb_store_order` | 订单主表 | 订单号、用户、金额、支付状态、订单状态 |
| `eb_store_order_cart_info` | 订单商品明细表 | 商品快照、购买数量、SKU 信息 |
| `eb_store_order_status` | 订单操作记录表 | 创建、支付、发货、收货等状态日志 |
| `eb_store_order_refund` | 退款/售后表 | 退款金额、退款类型、退款状态 |
| `eb_store_order_invoice` | 发票表 | 发票申请、开票状态 |

下单主流程的核心数据关系：

```text
eb_user
    ↓
eb_store_cart
    ↓
eb_store_order
    ↓
eb_store_order_cart_info
    ↓
eb_store_order_status
```

## 测试范围

### 功能测试

- 订单创建是否成功
- 订单金额计算是否正确
- 优惠券、积分、会员价、运费是否正确参与计算
- 库存是否正确扣减
- 订单状态是否按规则流转
- 支付、取消、发货、收货、退款、评价是否受状态限制
- 订单列表和详情展示是否正确

### 接口测试

- 单接口正常和异常参数测试
- 多接口主流程测试
- 接口之间的数据提取和传递
- token 认证和未登录访问
- 用户只能查看和操作自己的订单
- 后台接口和用户接口权限隔离

### 数据库校验

- 创建订单后 `eb_store_order` 是否新增记录
- 订单商品明细是否写入 `eb_store_order_cart_info`
- 购物车记录是否被标记为已购买
- 支付后 `paid`、`pay_type`、`pay_time` 是否更新
- 发货后物流字段和订单状态是否更新
- 退款后 `refund_status`、`eb_store_order_refund` 是否正确
- 状态操作是否写入 `eb_store_order_status`

### 性能测试

- 下单接口
- 支付接口和支付回调
- 订单列表接口
- 抢购、秒杀、优惠券等高并发接口
- 后台订单列表和统计接口

### 安全测试

- 未登录不能创建订单、查看订单、申请售后
- A 用户不能查看 B 用户订单详情
- A 用户不能取消、删除、收货 B 用户订单
- 普通用户不能调用后台发货、退款、改价接口
- 不能通过篡改金额、优惠券 ID、商品数量绕过后端计算
- 不能重复提交订单导致重复扣库存或重复生成订单

## 重点测试点

### 1. 金额正确性

订单金额是最高风险点之一，需要重点覆盖：

- 商品原价
- SKU 价格
- 购买数量
- 优惠券
- 积分抵扣
- 会员价
- 运费
- 礼品订单附加费
- 后台改价
- 退款金额

断言不能只看接口返回的金额，还要对比数据库中的 `total_price`、`pay_price`、`coupon_price`、`deduction_price`、`pay_postage` 等字段。

### 2. 库存一致性

重点覆盖：

- 正常下单扣库存
- 取消订单是否释放库存
- 支付失败是否不扣或回滚库存
- 退款后是否恢复库存，具体要看业务规则
- 并发购买最后一件商品是否超卖

### 3. 状态流转

重点验证不允许跨状态操作：

- 未支付订单不能确认收货
- 未支付订单不能评价
- 已取消订单不能支付
- 已删除订单不能继续操作
- 已完成订单不能重复确认收货
- 已退款订单不能再次退款
- 非本人订单不能操作

### 4. 幂等性

重点场景：

- 重复点击创建订单
- 重复支付同一订单
- 支付回调重复通知
- 网络超时后用户再次提交
- 后台重复发货
- 重复申请退款

期望结果是：不能重复生成订单、不能重复扣库存、不能重复扣钱、不能重复退款。

### 5. 权限和越权

订单系统非常容易出现水平越权：

- 修改 URL 中的 `orderId` 或 `uni`
- 修改请求体中的 `uid`
- 使用自己的 token 操作别人的订单
- 普通用户调用管理端订单接口

接口自动化中要专门设计“用户 A 创建订单，用户 B 尝试查看/取消/退款”的用例。

## 自动化测试设计思路

### 框架目标

这个项目适合用 `pytest + requests + yaml + jsonpath + allure` 做接口自动化。

核心目标：

- 用 YAML 管理接口测试数据
- 用 requests 统一发送请求
- 用 pytest 组织单接口和流程用例
- 用 jsonpath 提取 token、商品 ID、购物车 ID、订单号等变量
- 用上下文管理接口之间的数据依赖
- 用数据库查询验证真实业务结果
- 用 Allure 展示请求、响应、断言和失败原因

### 下单主流程自动化步骤

```text
1. 登录，提取 token
2. 查询商品列表，筛选有库存、上架、可购买商品
3. 查询商品详情，提取 product_id、attr_unique、price、stock
4. 加入购物车或立即购买
5. 获取购物车列表，提取 cart_id
6. 查询默认地址，提取 addressId
7. 调用 order/check_shipping
8. 调用 order/confirm，提取 key 或确认页关键字段
9. 调用 order/computed/:key，校验金额
10. 调用 order/create/:key，提取 orderId
11. 查询 order/detail/:uni，校验订单详情
12. 查询数据库，校验订单主表和订单明细表
```

### YAML 用例中应重点维护的数据

- 请求方法
- 接口路径
- 请求头
- 请求参数
- 是否需要 token
- 断言规则
- 提取变量
- 数据库断言
- 前置步骤
- 后置清理

示例关注点：

```yaml
order_create_success:
  method: post
  url: /order/create/${{order_key}}
  headers:
    Authori-zation: Bearer ${{token}}
  json:
    addressId: ${{address_id}}
    couponId: 0
    payType: yue
    useIntegral: 0
    shipping_type: 1
  assert:
    - check: $.status
      comparator: eq
      expect: 200
    - check: $.data.status
      comparator: eq
      expect: SUCCESS
  extract:
    order_id: $.data.result.orderId
```

## 测试用例设计方向

### 正向用例

- 普通商品立即购买下单成功
- 加购物车后下单成功
- 使用优惠券下单成功
- 使用积分抵扣下单成功
- 余额支付成功
- 订单列表能查到新订单
- 订单详情金额、商品、地址正确
- 后台发货后用户能确认收货
- 完成订单后可以评价

### 异常用例

- 未登录创建订单
- 空购物车创建订单
- 商品下架后创建订单
- 库存不足时创建订单
- 地址为空时创建订单
- 优惠券不可用时创建订单
- 篡改支付金额
- 重复提交同一个下单 key
- 已取消订单再次支付
- 未支付订单确认收货
- 非本人订单查看详情
- 非本人订单申请退款

### 售后用例

- 已支付未发货订单申请退款
- 已发货订单申请退货退款
- 退款金额不能大于订单实付金额
- 退款数量不能大于购买数量
- 取消退款申请
- 提交退货物流
- 后台同意退款
- 后台拒绝退款
- 已退款订单不能重复退款

### 并发用例

- 同一用户重复点击创建订单
- 多用户抢购同一个低库存商品
- 支付回调重复请求
- 后台重复点击发货
- 退款审核重复提交

## 项目痛点/风险点

- 钱、库存、状态流转是最高风险区域
- 订单状态是组合字段，容易断言不完整
- 第三方支付回调可能延迟、重复或丢失
- 物流和发票属于外部服务，环境不稳定时容易影响自动化结果
- 测试数据准备复杂，需要稳定商品、库存、地址、优惠券和用户余额
- 并发下可能出现超卖、重复扣库存或状态跳转异常
- 权限控制不严会导致水平越权查看或操作他人订单
- 只校验接口响应不够，必须增加数据库结果校验

## 当前学习项目可以逐步完善的方向

1. 先打通下单主流程：登录 -> 商品 -> 购物车 -> 确认订单 -> 创建订单。
2. 再补订单查询和数据库校验：订单主表、明细表、购物车状态。
3. 然后补异常用例：未登录、库存不足、地址为空、重复提交。
4. 接着补权限用例：用户 A 的订单不能被用户 B 查看或操作。
5. 再补支付、发货、收货、售后退款等状态流转。
6. 最后补并发、性能、CI、报告通知和测试数据自动准备。

## 面试表达要点

订单系统我会重点围绕业务链路、状态机、资金流、库存和权限来设计测试。

我参考 CRMEB 源码梳理过订单模块，用户端订单接口主要集中在 `app/api/route/v1.php` 和 `StoreOrderController.php`，业务实现集中在 `services/order`，数据库核心表包括 `eb_store_order`、`eb_store_order_cart_info`、`eb_store_cart`、`eb_store_order_status` 和 `eb_store_order_refund`。

做接口自动化时，我不会只校验接口返回，而是会用 YAML 管理用例数据，通过 pytest 和 requests 跑通登录、商品、购物车、订单确认、金额计算、创建订单等主流程，用 jsonpath 提取 token、商品 ID、购物车 ID、订单号等上下文变量，最后结合数据库校验订单是否真实落库、金额是否正确、库存和订单状态是否一致。

异常流程我会重点覆盖重复提交、重复支付、库存不足、优惠券不可用、弱网超时、支付回调重复、售后退款和越权访问。因为订单系统最核心的风险就是钱不能错、库存不能乱、状态不能跳、权限不能越。
