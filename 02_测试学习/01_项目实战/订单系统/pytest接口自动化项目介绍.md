# pytest 接口自动化项目介绍

## 项目背景

`pytest_auto_api_my` 是一个基于 `pytest + requests + yaml + allure` 搭建的接口自动化测试项目。

这个项目主要围绕订单系统的下单主流程展开，把接口测试用例写在 YAML 文件里，再通过 pytest 自动读取用例、发送接口请求、执行断言、提取上下文变量，并生成 Allure 测试报告。

它不是单纯写几个接口脚本，而是在练习一个接口自动化框架的基本结构：配置层、数据层、工具层、用例层和报告层。

## 项目目标

这个项目的目标是把接口测试从“手动调用接口”变成“自动化执行流程”。

核心思路是：

- 用 YAML 管理接口用例数据
- 用 pytest 组织和执行测试用例
- 用 requests 发送 HTTP 请求
- 用 jsonpath 从响应中提取字段
- 用上下文管理器保存流程变量
- 用断言模块统一校验接口返回
- 用 Allure 展示测试结果和请求响应详情

## 技术栈

| 技术 | 作用 |
| ---- | ---- |
| pytest | 测试框架，用来收集和执行测试用例 |
| requests | 发送 HTTP 接口请求 |
| PyYAML | 读取 YAML 格式的测试数据 |
| jsonpath | 从接口响应 JSON 中提取字段 |
| allure-pytest | 生成接口测试报告 |
| pytest.ini | 配置 pytest 执行参数、测试路径和报告目录 |

## 当前已经实现的功能

### 1. 多环境配置

项目在 `common/config.yaml` 中维护环境配置，目前包含 `test` 和 `prod` 两套环境。

`conftest.py` 中通过 `--env` 参数支持运行时切换环境，例如：

```bash
pytest --env test
```

当前项目默认环境是 `test`，接口基础地址由 `HOST` 统一管理。

### 2. YAML 数据驱动

接口用例主要写在 `data/` 目录下的 YAML 文件中。

每个 YAML 文件可以包含：

- `case_common`：公共配置，例如统一的 url、method、headers
- 具体用例 ID：例如 `login_success`
- `data`：请求体数据
- `assert`：断言规则
- `extract`：需要从响应里提取的变量

这样做的好处是测试数据和测试代码分离，后续新增接口用例时，不一定要频繁修改 Python 代码。

### 3. 公共参数合并

`util/readFileUtils/get_yaml_data_analysis.py` 会读取 YAML 用例，并把 `case_common` 和具体用例内容合并。

比如登录接口所有用例共用 `/login` 和 `post`，每条用例只需要维护自己的请求数据和断言。

### 4. 占位符替换

`util/readFileUtils/placeholder.py` 支持 `${{变量名}}` 形式的占位符替换。

它可以从上下文管理器中读取变量，也支持 `${{host()}}` 获取当前环境的 HOST。

这个能力主要用于接口之间的数据关联，比如后一个接口需要使用前一个接口返回的 `token`、商品 ID、地址 ID 等。

### 5. 请求封装

`util/requestsUtils/requestControl.py` 对 requests 做了统一封装。

目前支持：

- 自动拼接 HOST 和接口路径
- 默认请求头处理
- 自动从上下文中读取 token 并加入 Authorization
- 支持 params、data、json 请求参数
- 记录请求方法、URL、headers、params、data、json
- 返回统一响应结构，包括 status_code、body、text、headers、elapsed_ms
- 请求异常时返回调试信息，方便定位问题

### 6. 上下文变量管理

`util/context/context_manager.py` 实现了一个简单的上下文变量仓库。

它主要负责在流程测试中临时保存接口返回的数据，例如：

- 登录接口返回的 token
- 商品列表中筛选出的商品 ID
- 商品详情中的 sku 信息
- 默认地址 ID
- 订单确认流程中需要的业务字段

`conftest.py` 中的 `flow_context` 和 `case_context` 会在测试前后清空上下文，避免不同用例之间互相污染。

### 7. 响应字段提取

`util/extract/extract_control.py` 支持从响应体中提取数据并写入上下文。

当前支持两类提取方式：

- 普通 JSONPath 提取，例如 `token: $.data.token`
- 条件筛选提取，例如从商品列表里筛选符合库存、状态等条件的商品，再取指定字段

这个功能是接口流程自动化的关键，因为真实业务流程通常不是单接口独立运行，而是前后接口之间存在数据依赖。

### 8. JSONPath 断言

`util/assertion/assert_control.py` 对断言做了统一封装。

当前支持：

- HTTP 状态码断言
- JSONPath 字段提取
- `eq` / `==` / `equals`
- `ne` / `!=`
- `in`
- `contains`
- `exists`

断言失败时会输出请求信息和响应信息，包括请求 URL、headers、params、json、响应状态码和响应体，方便排查失败原因。

### 9. 单接口和流程执行器

`util/case_runner.py` 是当前项目的核心执行器。

它提供了两个主要能力：

- `run_case()`：执行单个 YAML 用例
- `run_flow_steps()`：按顺序执行多个接口步骤

执行顺序大致是：

```text
读取 YAML 用例
    ↓
合并公共参数
    ↓
替换占位符
    ↓
发送接口请求
    ↓
写入 Allure 请求响应详情
    ↓
执行断言
    ↓
提取响应字段到上下文
```

### 10. 下单主流程测试

当前项目已经实现了一个下单主流程测试，位置是 `test_case/test_order_main_flow.py`。

主流程包括：

```text
用户登录
    ↓
商品列表
    ↓
商品详情
    ↓
默认价格
    ↓
个人中心
    ↓
直接购买
    ↓
检查发货
    ↓
获取默认地址
    ↓
订单确认
```

这个流程体现了接口自动化里很重要的一点：接口之间不是孤立的，登录后的 token、商品信息、地址信息都需要在流程中传递。

### 11. Allure 报告

项目已经接入 `allure-pytest`。

`pytest.ini` 中配置了：

```ini
addopts = -q -s --alluredir=./report/tmp --clean-alluredir
```

`run.py` 在 pytest 执行完成后，会调用 Allure 命令生成 HTML 报告：

```bash
allure generate ./report/tmp -o ./report/html --clean
```

`case_runner.py` 还会把每个接口的请求和响应详情作为 JSON 附件写入 Allure，方便查看接口执行细节。

## 当前项目的亮点

- 已经具备接口自动化框架的基本分层，不是把所有逻辑都写在测试用例里
- 测试数据和测试代码分离，方便维护 YAML 用例
- 支持接口之间的数据传递，能覆盖真实业务流程
- 请求、断言、提取、流程执行都有独立模块，后续方便扩展
- Allure 中能看到每个接口的请求响应详情，排查失败更直观
- 已经开始从单接口测试过渡到业务主流程测试

## 可以提升的地方

### 1. 修正测试收集命名问题

`test_case/login/test_login.py` 里的测试方法当前命名为 `login`，pytest 默认只收集 `test_` 开头的方法。

建议改成：

```python
def test_login(self, case_id, case):
```

否则登录模块的参数化用例可能不会被 pytest 自动收集。

### 2. 让流程 YAML 真正驱动主流程

当前 `data/order_main_flow.yaml` 已经写了流程步骤，但 `test_case/test_order_main_flow.py` 中仍然手动维护了一份 `ORDER_MAIN_FLOW` 列表。

后续可以让测试代码直接读取 `order_main_flow.yaml`，这样流程增删步骤时只改 YAML，不改 Python。

### 3. 增加日志体系

现在主要依赖 pytest 输出和 Allure 附件定位问题。

后续可以增加统一日志模块，记录：

- 用例开始和结束
- 请求 URL 和请求参数
- 响应状态码和响应耗时
- 断言失败原因
- 变量提取结果

日志可以按日期输出到 `logs/` 目录，方便本地排查和长期追踪。

### 4. 增强失败重试能力

接口自动化中有些失败可能来自网络波动、服务临时不稳定或测试环境偶发问题。

后续可以引入失败重试机制，例如：

- 对超时请求做有限次数重试
- 对指定接口设置重试策略
- 区分真正业务失败和环境偶发失败

但重试不能滥用，关键业务断言失败不能简单靠重试掩盖。

### 5. 增加数据库校验

当前项目主要校验接口响应。

订单系统这类业务里，接口返回正确不代表数据库状态一定正确。后续可以增加数据库校验，例如：

- 下单后订单表是否生成记录
- 库存是否正确扣减
- 地址 ID、商品 ID、用户 ID 是否关联正确
- 订单状态是否符合预期

这会让测试从“接口返回校验”提升到“业务结果校验”。

### 6. 增加 Mock 或测试数据准备能力

当前流程依赖真实测试环境接口和真实数据。

后续可以补充：

- 测试前自动准备商品、库存、地址等数据
- 对不稳定的第三方接口进行 Mock
- 对需要固定返回的数据构造稳定测试场景

这样可以减少环境数据变化对自动化结果的影响。

### 7. 扩展断言能力

当前断言已经支持常见的相等、不等、包含和存在判断。

后续可以继续扩展：

- 大于、小于、大于等于、小于等于
- 字段类型校验
- 列表长度校验
- 正则匹配
- 多字段组合断言
- 响应时间断言

这样 YAML 用例能覆盖更多测试场景。

### 8. 接入 CI 持续集成

后续可以把项目接入 Jenkins、GitHub Actions 或 GitLab CI。

实现效果：

- 每次提交后自动执行接口测试
- 定时执行核心接口回归
- 生成 Allure 报告
- 失败后自动通知测试人员

这样项目就不只是本地运行脚本，而是可以服务于持续回归。

### 9. 管理敏感数据

当前 YAML 中直接维护了账号、密码等测试数据。

后续可以把敏感配置放到：

- 环境变量
- 单独的本地配置文件
- CI 密钥管理

这样可以降低账号密码泄露风险，也方便不同环境使用不同账号。

### 10. 增加报告通知

Allure 报告目前可以本地生成。

后续可以增加通知能力，例如：

- 测试执行完成后发送钉钉或企业微信通知
- 通知中包含执行结果、失败用例数、报告地址
- 失败时附带核心错误摘要

这样接口自动化结果可以更及时地被团队看到。

## 学习复盘

这个项目让我练习了接口自动化框架的核心思路：不是只会用 requests 调接口，而是把接口测试拆成配置、数据、请求、断言、提取、上下文和报告几个模块。

通过下单主流程，我能理解接口自动化真正难的地方不只是发送请求，而是处理接口之间的数据依赖、业务链路的顺序、测试环境的数据稳定性，以及失败后的定位能力。

## 面试表达

我做过一个基于 pytest 的接口自动化项目，主要测试订单系统的下单主流程。项目用 YAML 管理接口用例数据，通过 requests 封装统一请求发送，用 jsonpath 做响应字段提取和断言，并用上下文管理器保存 token、商品 ID、地址 ID 等流程变量。测试执行时，pytest 会按业务步骤跑通登录、商品、购物车、地址和订单确认接口，同时把请求响应详情写入 Allure 报告。这个项目让我比较熟悉接口自动化框架的分层设计、数据驱动、接口关联、断言封装和测试报告生成。

## 后续优先优化顺序

如果继续完善这个项目，我会按下面顺序推进：

1. 先修正 pytest 测试收集问题，保证所有测试能被正常执行。
2. 再让 `order_main_flow.yaml` 真正驱动主流程，减少 Python 中的硬编码。
3. 然后增加日志体系和更丰富的断言能力，提高失败定位效率。
4. 接着补充数据库校验和测试数据准备能力，让测试更接近真实业务验证。
5. 最后接入 CI、报告通知和敏感数据管理，让项目具备团队落地能力。
