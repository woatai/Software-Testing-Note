# AI 生成 UI 自动化脚本

> [!info] 笔记定位
> 这篇笔记回答“输入自然语言用例后，怎样提高元素定位和 UI 脚本生成成功率”。以下是待实现、待实验验证的工程方案，不代表当前项目已经完成。

## 一、核心思路

不要让 AI 每次根据截图和整页 DOM 从零猜元素，而要把任务变成“自然语言用例编译 + 页面能力检索 + 受约束执行”。

```text
自然语言用例
→ 结构化步骤 DSL
→ 检索已审核的页面能力 / 元素记录
→ 未知步骤才探索候选元素
→ 执行动作
→ 校验页面或业务状态
→ 人工确认低置信度结果
→ 回归验证后入库复用
```

关键点不是准备更多 CSS、文本和 XPath 备选，而是减少 AI 的搜索空间，并阻止错误状态继续向下传播。

## 二、页面能力库

优先保存可复用的业务动作，例如 `选择会员`、`选择支付方式`、`提交订单`，由 Page Object 封装具体定位器；生成器优先组合这些动作，而不是重复生成原始点击代码。

元素或动作记录至少包含：

| 字段 | 作用 |
| --- | --- |
| `app/page/component/state` | 限定元素所在范围和使用前提 |
| `intent/action` | 业务意图与动作，例如“选择支付宝 / click” |
| `primary_locator` | 已审核的主定位器 |
| `fallback_locators` | 少量经过验证的备选定位器 |
| `frame/shadow/dialog` | iframe、Shadow DOM、弹窗等上下文 |
| `precondition` | 动作前必须满足的页面状态 |
| `postcondition` | 动作后必须出现的 URL、元素、接口或业务状态 |
| `app_version/last_verified` | 有效版本与最近验证时间 |
| `source/status` | AI 探索或人工确认；待审、已审、失效 |

这里可以借鉴 [[00_RAG核心知识#4. 混合检索|混合检索]]，但不应只用向量相似度：先按应用、页面、组件和状态做确定性过滤，再对业务意图做关键词与语义排序。

## 三、元素候选与定位规则

定位优先级通常为：

1. 已审核的 Page Object / 页面能力；
2. `role + accessible name`、`label` 等用户可感知语义；
3. 与开发约定的稳定 `data-testid`；
4. 稳定业务属性、局部文本，并限定在表格行、弹窗或表单等容器内；
5. 短 CSS 作为受控兜底；
6. 长 CSS、绝对 XPath、动态 class、`nth()` 只作为低置信度候选，不能静默入库。

候选元素评分可以综合：语义匹配、页面/容器匹配、唯一性、可见且可操作、历史成功率和版本有效性；动态属性、多个匹配、低稳定性定位器应扣分。第一名置信度不足，或与第二名分差过小时，转人工确认，不应随机点击。

截图适合辅助识别图标、Canvas 或无障碍语义差的自定义控件，但普通 Web 页面应优先使用 DOM 与 accessibility tree，因为截图不能单独证明元素唯一、可操作或处于正确页面状态。

## 四、脚本生成与执行门禁

自然语言先转换成结构化步骤，每一步明确：前置状态、动作、业务目标、输入数据和预期结果。模型只能调用白名单 Page Object、Fixture、断言和公共工具；信息不足时输出待确认项，不得编造页面能力。

执行阶段采用状态机：

```text
检查前置状态 → 唯一定位 → 检查可操作性 → 执行动作 → 检查后置状态
```

后置状态必须验证业务意图是否实现，例如 URL、标题、弹窗、选中值、订单号、接口响应或数据库状态。元素“可以点击”不等于“点对了”，后置状态校验用于阻止错误继续传播。

生成代码还应经过确定性门禁：语法、格式、类型或 lint、禁止固定 `sleep`、禁止无理由 `force=True`、禁止绝对 XPath、禁止修改框架边界、每个关键动作必须有断言。之后在隔离测试数据上试运行，支付等有副作用的步骤需要 `case_id`、幂等或后端查询，不能盲目整条重跑。

## 五、人工介入与自愈

人工介入应设计成最小确认动作：系统展示当前页面、Top-N 候选、定位证据、置信度和失败原因，人只确认正确候选，或要求开发补充稳定 `data-testid`。

人工结果不能直接写成一条提示词经验。它应先形成版本化元素记录或 Page Object 修改，经过真实回归后再标记为已审核。自愈只能生成候选，不应静默修改断言或吞掉原始失败。

## 六、怎样证明成功率提高

建立包含简单页面、重复文本、表格行、弹窗、iframe、动态渲染、多语言和无稳定属性元素的 Gold Set，并保留未参与规则调整的 holdout 集。固定浏览器、应用版本、账号、测试数据、模型和 Prompt，对新旧方案做 A/B 回归。

至少记录：

- 元素 Top-1 定位正确率；
- 已审核页面能力复用率；
- 脚本首次生成并端到端通过率；
- 人工介入率与平均重试次数；
- 错误状态继续传播率；
- 同一脚本重复执行的 flaky 率；
- 平均生成时间、执行时间和模型成本。

失败应分类为：用例歧义、页面知识缺失、步骤规划错误、元素映射错误、状态断言缺失、环境/数据问题和真实产品缺陷。只优化对应层，不用无限重试或模型“自我反思”掩盖根因。

相关评测方法见 [[01_RAG评测与测试]]。

## 七、面试表达

> 我不会让 AI 每次拿着截图和整页 DOM 从零探索，而会把系统设计成“自然语言用例编译、页面能力检索、受约束执行、逐步状态校验、人工确认和经验入库”的闭环。先将用例拆成带前置状态、动作和预期结果的结构化步骤；已知页面优先复用审核过的 Page Object 和元素库，未知页面再根据 accessibility tree、DOM、testid 和页面上下文生成候选并打分。每一步执行后都验证 URL、关键元素或接口状态，防止点错元素后继续向下走。低置信度或候选不唯一时让人只确认候选，验证通过后版本化入库。最后用 Top-1 定位正确率、首次端到端成功率、人工介入率、平均重试次数和 flaky 率做版本对比，证明方案真的提高了成功率。
