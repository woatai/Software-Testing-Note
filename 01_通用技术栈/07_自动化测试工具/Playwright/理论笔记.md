## 一、为什么使用 Playwright

### 1.1 和 Selenium 的核心差异

Playwright 和 Selenium 都可以用于 Web UI 自动化测试，但二者的设计思路不同。

Selenium 更像传统浏览器驱动方案：测试脚本通过 WebDriver 协议和浏览器驱动通信，再由浏览器驱动控制浏览器。它生态成熟、历史悠久、语言支持广，但在现代前端页面中，经常需要额外处理等待、弹窗、iframe、新窗口、动态元素等问题。

Playwright 更像为现代 Web 应用重新设计的一套浏览器自动化框架。它直接面向 Chromium、Firefox、WebKit 等浏览器引擎，内置自动等待、网络监听、trace 调试、截图、视频、测试运行器等能力，减少了很多传统 UI 自动化里容易导致脚本不稳定的处理成本。

可以简单理解为：

| 对比点 | Selenium | Playwright |
| --- | --- | --- |
| 出现时间 | 更早，生态成熟 | 较新，面向现代 Web |
| 浏览器控制方式 | 依赖 WebDriver 和浏览器驱动 | Playwright 自带浏览器控制能力 |
| 等待机制 | 经常需要显式等待或封装等待 | 内置自动等待机制 |
| 调试能力 | 依赖第三方报告、截图、日志 | 官方内置 trace、video、screenshot |
| 多浏览器 | 支持 Chrome、Firefox、Edge、Safari 等 | 支持 Chromium、Firefox、WebKit |
| 适合场景 | 老项目、已有 Selenium 体系、兼容性项目 | 新项目、现代前端、企业回归测试 |

对学习和企业落地来说，Playwright 的优势主要不是“能不能点页面”，而是它把很多工程化能力内置好了，例如自动等待、失败追踪、并行执行、多浏览器、登录态复用和测试报告，这些能力能降低 UI 自动化维护成本。

### 1.2 Playwright 优势速览

Playwright 的核心优势可以从稳定性、效率、调试、工程化四个角度理解。

**1. 自动等待机制**

Playwright 在点击、输入、断言前会自动等待元素达到可操作状态，例如元素可见、可点击、未被遮挡等。这样可以减少大量 `sleep` 和手写等待逻辑。

这对 UI 自动化非常重要，因为很多页面是动态加载的。如果等待机制处理不好，用例就容易出现“本地能跑、CI 偶尔失败”的问题。

**2. Web-first assertions**

Playwright 的断言会自动重试，直到条件满足或超时。例如：

```python
expect(page.get_by_text("Checkout")).to_be_visible()
```

这类断言比一次性判断更稳定，适合验证异步加载后的页面状态。

**3. 定位器更贴近真实用户**

Playwright 推荐优先使用：

- `get_by_role()`
- `get_by_label()`
- `get_by_text()`
- `get_by_placeholder()`
- `get_by_test_id()`

这些定位方式比单纯依赖 XPath 或复杂 CSS 更稳定，也更贴近用户看到和操作页面的方式。

企业项目中，如果前端能配合添加 `data-testid`，UI 自动化维护成本会明显降低。

**4. 官方调试能力强**

Playwright 支持：

- 截图
- 视频
- trace 追踪
- Inspector 调试
- HTML Report

其中 trace 很适合定位失败原因。它可以看到每一步操作、页面快照、网络请求、控制台信息。企业里排查 UI 自动化失败时，这比只看日志直观很多。

**5. 支持登录态复用**

真实项目中，不建议每条用例都通过 UI 登录。Playwright 可以保存登录后的 cookies、localStorage 等状态，然后在其他用例里复用。

这可以提升执行效率，也能减少登录页面不稳定对整套回归测试的影响。

**6. 支持 UI + API 混合测试**

Playwright 不只能操作页面，也可以发 API 请求。企业落地时可以用 UI 完成用户关键操作，再通过 API 校验后台状态，例如：

- 前台提交订单
- API 查询订单状态
- API 校验支付状态
- API 校验用户信息是否保存成功

这种方式比只靠 UI 页面断言更可靠。

### 1.3 技术对比和选型参考

选择 UI 自动化工具时，不应该只看“哪个更流行”，而要看项目现状、团队技术栈、维护成本和业务目标。

| 场景 | 推荐选择 | 原因 |
| --- | --- | --- |
| 新项目从 0 搭建 UI 自动化 | Playwright | 工程化能力完整，学习和维护成本较低 |
| 现代前端项目，例如 Vue、React、Next.js | Playwright | 对动态页面、弹窗、iframe、多窗口支持更好 |
| 已经有成熟 Selenium 框架 | Selenium 或逐步迁移 | 直接替换成本较高，需要考虑历史资产 |
| 需要 Python + pytest 企业测试框架 | Playwright Python | 可结合 pytest、Allure、CI、接口校验 |
| 需要跨浏览器回归 | Playwright | 可跑 Chromium、Firefox、WebKit |
| 只做少量浏览器自动化脚本 | Playwright 或 Selenium 都可以 | 简单场景差异不大 |

对我当前学习目标来说，更适合选择：

```text
Python + pytest + pytest-playwright + Playwright + Allure/pytest-html + GitHub Actions
```

原因：

- Python 适合测试人员学习和落地。
- pytest 适合组织测试用例、fixture、参数化和标记。
- Playwright 适合现代 Web UI 自动化。
- Allure 或 pytest-html 适合生成测试报告。
- GitHub Actions 适合练习 CI 自动化执行。
