# Playwright 理论基础

## 一、Web 自动化测试工具

Playwright：用于 Web UI 自动化测试的工具，可以控制浏览器完成点击、输入、断言、截图、录制、接口请求等操作。

常见用途：

+ UI 自动化回归测试
+ 兼容性测试
+ 冒烟测试
+ 登录、下单、支付等核心流程验证
+ UI + API 混合测试

### 1.1 和 Selenium 对比

| 对比点 | Selenium | Playwright |
| ------ | -------- | ---------- |
| 浏览器控制 | 依赖 WebDriver | 自带浏览器控制能力 |
| 等待机制 | 常需要自己封装等待 | 内置自动等待 |
| 调试能力 | 依赖日志、截图、第三方工具 | 内置 trace、video、screenshot |
| 多浏览器 | Chrome、Firefox、Edge、Safari | Chromium、Firefox、WebKit |
| 适合场景 | 老项目、已有框架 | 新项目、现代前端、企业回归 |

Playwright 主要优势：

+ 自动等待：减少 `sleep`
+ 定位器丰富：更贴近用户操作
+ 调试方便：trace 可以看到每一步
+ 支持登录态复用：不用每条用例都登录
+ 支持 API 请求：方便做 UI + API 校验

### 1.2 推荐技术栈

```text
Python + pytest + pytest-playwright + Playwright + Allure/pytest-html + CI
```

原因：

+ Python：适合测试人员学习和落地
+ pytest：适合管理用例、fixture、mark、参数化
+ Playwright：适合现代 Web UI 自动化
+ Allure/pytest-html：适合生成测试报告
+ CI：适合定时执行和回归测试

### 1.3 Playwright 核心对象关系

可以把 Playwright 的对象关系理解成一层一层往下控制浏览器：

```text
Browser
└── BrowserContext
    └── Page
        └── Locator
```

| 对象 | 含义 | 常见用途 |
| --- | --- | --- |
| `Browser` | 浏览器实例 | 启动 Chromium、Firefox、WebKit |
| `BrowserContext` | 隔离的浏览器会话 | 管理 cookie、localStorage、权限、登录态 |
| `Page` | 一个标签页或页面 | 打开 URL、点击、输入、监听网络 |
| `Locator` | 元素定位器 | 找元素并执行操作或断言 |
| `expect()` | Web-first 断言 | 自动等待页面状态符合预期 |

`pytest-playwright` 里最常用的是 `page` fixture。它已经帮我们创建好了浏览器上下文和页面，所以多数用例可以直接从 `page.goto()` 开始。

如果需要模拟多个互相隔离的用户，可以创建多个 `BrowserContext`。不同 context 之间的 cookie 和 localStorage 默认不共享。



```shell

```

### 2.2 创建用例

文件名：`test_baidu.py`

```python
import re

from playwright.sync_api import Page, expect


def test_baidu_search(page: Page):
    page.goto("https://www.baidu.com")

    page.locator("#kw").fill("Playwright")
    page.locator("#su").click()

    expect(page).to_have_title(re.compile("Playwright"))
```

说明：

+ `page`：`pytest-playwright` 提供的 fixture
+ `goto()`：打开页面
+ `fill()`：输入内容
+ `click()`：点击元素
+ `expect()`：断言页面结果

## 三、深入掌握 Playwright

学习 Playwright 时，可以先把能力分成两层：

+ `Page`：关注整个页面，例如打开页面、刷新页面、读取标题、键盘输入、截图。
+ `Locator`：关注某个元素，例如按钮、输入框、复选框、列表项。

再按“内容”和“动作”区分：

| 分类 | 关注点 | 常见方法 |
| --- | --- | --- |
| 页面导航 | 决定被测页面是哪一个 | `goto()`、`wait_for_url()`、`go_back()`、`reload()` |
| 页面内容 | 页面整体展示了什么 | `title()`、`url`、`content()`、`screenshot()` |
| 页面动作 | 对页面整体做操作 | `keyboard.press()`、`mouse.click()`、`set_viewport_size()` |
| 元素内容 | 某个元素里有什么 | `inner_text()`、`text_content()`、`input_value()`、`get_attribute()` |
| 元素动作 | 对某个元素做操作 | `click()`、`fill()`、`check()`、`select_option()`、`hover()` |

### 3.1 页面导航

页面导航决定“当前测试的是哪个页面”。自动化用例通常先进入目标页面，再等待页面稳定到可测试状态。

```python
from playwright.sync_api import Page, expect


def test_page_navigation(page: Page):
    page.goto("https://example.com")

    expect(page).to_have_url("https://example.com/")
    expect(page).to_have_title("Example Domain")
```

常用写法：

```python
page.goto("https://example.com")
page.reload()
page.go_back()
page.go_forward()

page.wait_for_url("**/home")
page.wait_for_load_state("domcontentloaded")
```

使用建议：

+ `goto()`：打开指定页面。
+ `wait_for_url()`：等待跳转到目标地址，适合登录、下单、提交表单之后。
+ `wait_for_load_state()`：多数情况下不需要额外调用；确有需要时等待明确的加载阶段，不使用 `networkidle` 判断业务页面是否就绪。
+ 页面是否真正可用，优先使用后面的 `expect()` 等待具体的用户可见结果。

### 3.2 页面内容

页面内容关注“整个页面现在展示了什么”。它适合检查页面标题、当前地址、HTML、截图等页面级信息。

```python
title = page.title()
url = page.url
html = page.content()

print(title)
print(url)
print(html)
```

常见断言：

```python
from playwright.sync_api import expect


expect(page).to_have_title("首页")
expect(page).to_have_url("https://example.com/home")
```

调试时也可以保存页面截图：

```python
page.screenshot(path="home.png", full_page=True)
```

### 3.3 页面动作

页面动作关注“对整个页面做操作”。这类操作不一定绑定某个元素，常见于键盘、鼠标、窗口大小、滚动等场景。

```python
page.goto("https://demo.playwright.dev/todomvc")

page.keyboard.press("Tab")
page.keyboard.press("Enter")
page.mouse.wheel(0, 600)
page.set_viewport_size({"width": 1280, "height": 720})
```

Todo 示例：

```python
from playwright.sync_api import Page, expect


def test_add_todo(page: Page):
    page.goto("https://demo.playwright.dev/todomvc")

    page.get_by_placeholder("What needs to be done?").fill("学习 Playwright")
    page.keyboard.press("Enter")

    expect(page.get_by_text("学习 Playwright")).to_be_visible()
```

### 3.4 元素内容

元素内容关注“某个具体元素里有什么”。先通过定位器找到元素，再读取它的文本、属性、输入框值或数量。

```python
username = page.locator(".username").inner_text()
message = page.locator(".message").text_content()
keyword = page.get_by_label("搜索").input_value()
href = page.get_by_role("link", name="详情").get_attribute("href")
count = page.locator(".goods-item").count()

print(username)
print(message)
print(keyword)
print(href)
print(count)
```

使用建议：

+ `inner_text()`：读取用户能看到的文本。
+ `text_content()`：读取 DOM 中的文本内容，可能包含隐藏文本。
+ `input_value()`：读取输入框当前值。
+ `get_attribute()`：读取元素属性，例如 `href`、`src`、`data-id`。
+ `count()`：统计匹配到的元素数量。

### 3.5 元素动作

元素动作关注“对某个具体元素做操作”。这是 UI 自动化中最常见的一类操作。

```python
page.goto("https://example.com")

page.get_by_label("用户名").fill("admin")
page.get_by_label("密码").fill("123456")
page.get_by_role("button", name="登录").click()

page.get_by_role("checkbox", name="同意协议").check()
page.get_by_role("combobox", name="城市").select_option("shanghai")
page.get_by_text("个人中心").hover()
```

综合示例：

```python
from playwright.sync_api import Page, expect


def test_login(page: Page):
    page.goto("https://example.com/login")

    page.get_by_label("用户名").fill("admin")
    page.get_by_label("密码").fill("123456")
    page.get_by_role("button", name="登录").click()

    expect(page).to_have_url("https://example.com/home")
    expect(page.get_by_text("登录成功")).to_be_visible()
```

## 四、定位器

定位器：找到页面元素，再进行点击、输入、断言。

### 4.1 常用定位方式

```python
page.get_by_role("button", name="登录").click()
page.get_by_text("提交成功").click()
page.get_by_label("用户名").fill("admin")
page.get_by_placeholder("请输入密码").fill("123456")
page.get_by_test_id("submit-btn").click()
page.locator("#username").fill("admin")
page.locator(".login-btn").click()
```

推荐顺序：

1. `get_by_role()`
2. `get_by_label()`
3. `get_by_text()`
4. `get_by_test_id()`
5. `locator(css/xpath)`

备注：

> 企业项目建议前端添加 `data-testid`，用例会更稳定。

定位方式选择思路：

+ `get_by_role()`：优先用于按钮、链接、复选框、输入框等有明确语义的元素。
+ `get_by_label()`：优先用于表单项，因为它接近真实用户看到的字段名称。
+ `get_by_text()`：适合定位稳定文案，例如成功提示、菜单项、弹窗标题。
+ `get_by_test_id()`：适合前端专门为自动化测试暴露的稳定标识。
+ `locator("css")`：适合页面没有语义信息，或者需要用 `id`、`class`、`data-*` 属性定位时。

当前支付项目并不是只使用 CSS。选择器会根据页面实际提供的信息决定：

```python
# 主 checkout 没有稳定 label，使用业务属性定位支付方式。
page.locator('.payment-method_item[data-type="jpay_card"]')

# 第三方页面有稳定的可访问名称，使用角色定位。
page.get_by_role("button", name="Submit", exact=True)

# 3DS 输入框有稳定 placeholder。
page.get_by_placeholder("Enter 6-digit code", exact=True)
```

`exact=True` 表示名称或 placeholder 必须完全匹配，适合页面存在相似按钮时缩小范围。
如果文案中包含动态数据，则可以用正则表达式表达稳定格式，而不是把动态值写死。

### 4.2 CSS 和 XPath

CSS 选择器通过元素的 `id`、`class`、标签、属性和层级关系定位元素。Playwright 使用 `page.locator("CSS 选择器")` 创建对应的 `Locator`：

```python
page.locator("#username").fill("admin")
page.locator(".login-form input[name='password']").fill("123456")
```

当前支付项目中的常见 CSS 写法：

| CSS 写法 | 项目示例 | 含义 |
| --- | --- | --- |
| `#id` | `#email` | 定位 `id="email"` 的元素 |
| `.class` | `.language-text` | 定位包含 `language-text` class 的元素 |
| `.class1.class2` | `.currency-text.search-text` | 定位同时包含两个 class 的同一个元素 |
| `标签.class` | `button.adyen-checkout__button--pay` | 定位指定 class 的 `button` 元素 |
| `[属性="值"]` | `[data-language="EN"]` | 定位属性值完全匹配的元素 |
| `.class[属性="值"]` | `.payment-method_item[data-type="adyen_card"]` | class 和属性必须同时匹配 |
| `父级 后代` | `.payment-pirce .currency-name` | 定位父级内部任意层级的后代元素 |
| `[属性="值"] 标签` | `[data-cse="encryptedSecurityCode"] iframe` | 定位指定字段容器内部的 iframe |

下面是根据项目选择器整理的简化 DOM，用于观察 CSS 选择器实际命中的元素：

```html
<input id="email" type="email">

<div class="currency-text search-text">
    USD
</div>

<ul class="payment-method-list">
    <li
        class="payment-method_item"
        data-type="adyen_card"
    >
        Adyen Card
    </li>
</ul>

<div class="payment-pirce">
    <span class="currency-name">USD</span>
</div>

<div id="card-container">
    <div data-cse="encryptedSecurityCode">
        <iframe title="安全码输入框"></iframe>
    </div>

    <button class="adyen-checkout__button--pay">
        Pay
    </button>
</div>
```

CSS 与上面 DOM 的对应关系：

```python
page.locator("#email")
# 命中：<input id="email">

page.locator(".currency-text.search-text")
# 命中：同时具有 currency-text 和 search-text 的 <div>

page.locator('.payment-method_item[data-type="adyen_card"]')
# 命中：支付方式列表中的 <li>

page.locator(".payment-pirce .currency-name")
# 命中：payment-pirce 内部的 <span>

page.locator("button.adyen-checkout__button--pay")
# 命中：card-container 内的 <button>

page.locator('[data-cse="encryptedSecurityCode"] iframe')
# 命中：安全码字段容器内部的 <iframe>
```

注意下面两个选择器含义不同：

```css
.currency-text.search-text
.payment-pirce .currency-name
```

+ `.currency-text.search-text` 中间没有空格，表示同一个元素同时具有 `currency-text` 和 `search-text`。
+ `.payment-pirce .currency-name` 中间有空格，表示在 `.payment-pirce` 内部寻找 `.currency-name` 后代元素。

根据上面的 DOM：

```css
/* 可以命中，因为两个 class 在同一个 div 上 */
.currency-text.search-text

/* 不能命中，因为 search-text 不是 div 内部的另一个元素 */
.currency-text .search-text

/* 可以命中，因为 currency-name 是 payment-pirce 内部的 span */
.payment-pirce .currency-name

/* 不能命中，因为两个 class 不在同一个元素上 */
.payment-pirce.currency-name
```

**动态属性选择器**

项目使用 Python f-string 把支付方式、国家、州和卡字段类型放进 CSS 属性选择器：

```python
def payment_method_item(self, method: str) -> Locator:
    return self.page.locator(
        f'.payment-method_item[data-type="{method}"]'
    )
```

假设 `method` 是 `"adyen_card"`，最终生成的 CSS 是：

```css
.payment-method_item[data-type="adyen_card"]
```

这里的 `f"..."` 是 Python 动态字符串语法，生成结果才是传给 Playwright 的 CSS 选择器。

**先定位容器，再定位内部元素**

Adyen Page Object 先定位支付组件容器，再把后续定位范围限制在容器内部：

```python
@property
def adyen_card_container(self) -> Locator:
    return self.page.locator("#card-container")

@property
def adyen_pay_button(self) -> Locator:
    return self.adyen_card_container.locator(
        "button.adyen-checkout__button--pay"
    )
```

执行过程：

1. `page.locator("#card-container")` 定位主页面中的 Adyen 容器。
2. `container.locator(...)` 只在这个容器内部寻找支付按钮。
3. 对返回的 `Locator` 执行 `click()` 或 `expect()` 时，Playwright 才真正查询当前 DOM。

这种链式定位相当于把范围逐层缩小。页面中存在相似按钮或多个第三方组件时，比从整个页面直接查找更明确。

**CSS 定位与 Playwright 过滤器**

下面代码中的 `.transaction-value` 是 CSS，`filter(visible=True)` 是 Playwright 对匹配结果的进一步过滤，不属于 CSS 语法：

```python
def transaction_id(self) -> Locator:
    return self.page.locator(
        ".transaction-value"
    ).filter(visible=True)
```

**CSS 定位 iframe 的边界**

CSS 可以定位主页面中的 iframe 元素：

```python
iframe_locator = self.adyen_card_container.locator(
    f'[data-cse="{field_type}"] iframe'
)
```

但 CSS 不能直接跨进 iframe 内部继续寻找输入框。项目通过 `iframe_locator.content_frame` 进入 iframe，再定位内部元素，具体见 `8.5 iframe`。

当前项目的 CSS 定位原则：

+ 唯一且稳定的输入框优先使用 `id`，例如 `#email`。
+ 业务属性稳定时使用 `data-*` 属性，例如 `data-type`、`data-value` 和 `data-cse`。
+ 没有更合适的语义定位时，使用稳定的 class 或 class 组合。
+ 页面存在重复区域时，先定位容器，再在容器内部定位目标元素。
+ 不依赖 `nth-child`、很长的 DOM 层级或 iframe 出现顺序。
+ CSS 选择器统一放在 Page Object 中，测试用例只调用页面操作和业务断言。
+ 按钮、提示等元素具有稳定的可访问语义时，仍优先考虑 `get_by_role()` 等用户可感知定位方式。
+ 页面存在相似的角色或 placeholder 时，使用 `exact=True` 明确完全匹配。
+ 文案包含订单号、成功码等动态内容时，使用正则表达式描述稳定格式。

XPath 也可以传给 `locator()`：

```python
page.locator("//button[text()='登录']").click()
```

当前项目的 Page Object 没有使用 XPath。只有页面缺少稳定的语义、`id`、class 或 `data-*` 属性，并且 CSS 难以清晰表达时，才考虑 XPath。

### 4.3 多元素处理

```python
items = page.locator(".goods-item")

expect(items).to_have_count(3)

items.first.click()
items.nth(1).click()
items.last.click()
```

当前项目的成功页可能同时保留隐藏和可见的同类节点，因此使用可见性过滤：

```python
def transaction_id(self) -> Locator:
    return self.page.locator(".transaction-value").filter(visible=True)
```

这里不是按位置选择第一个元素，而是表达“只要当前用户能看到的交易编号”。
如果直接使用 `.first`，DOM 顺序变化后可能命中隐藏模板。

### 4.4 组合定位

```python
page.locator(".goods-item").filter(has_text="手机").get_by_role(
    "button",
    name="加入购物车",
).click()
```

当前项目还使用了两类组合定位：

```python
# 先按 role 找 alert，再按动态文本格式过滤。
page.get_by_role("alert").filter(
    has_text=re.compile(r"^\s*Success code:\s*\d+\s*$")
)

# 先进入第三方 iframe，再按 role 和精确名称找按钮。
page.frame_locator('iframe[title="pacypay iframe"]').get_by_role(
    "button",
    name="Pay",
    exact=True,
)
```

组合过程是逐层缩小范围：先确定页面区域或语义类型，再用文本、角色或属性锁定最终目标。

### 4.5 Locator 和元素句柄的区别

`Locator` 不是“立刻抓到一个元素”，而是保存一套定位规则。真正执行 `click()`、`fill()`、`expect()` 时，Playwright 会重新根据规则查找元素，并配合自动等待。

```python
save_button = page.get_by_role("button", name="保存")

expect(save_button).to_be_enabled()
save_button.click()
```

这种写法比提前保存一个页面元素更稳定。现代前端经常重新渲染 DOM，如果保存的是某一次查到的元素快照，页面刷新后容易失效；`Locator` 会在每次操作前重新匹配当前页面上的元素。

在当前项目中，Page Object 的属性返回的也是定位规则：

```python
@property
def jpay_pay_button(self) -> Locator:
    return self.page.locator(".jpaycard-btn.checkout-btn")
```

执行时间线：

```text
step 1：访问 jpay_pay_button，得到 Locator
step 2：测试或 Page Object 调用 click()/expect()
step 3：Playwright 此时才查询当前 DOM
step 4：页面重新渲染时，后续调用会再次按同一规则定位
```

当前 Page Object 没有保存 `ElementHandle`。对于会重新渲染的 checkout 和第三方支付组件，
持续使用 `Locator`、`FrameLocator` 更符合项目的稳定性要求。

## 五、断言

断言：验证实际结果是否符合预期。

Playwright 推荐使用 `expect()`，因为它会自动等待。

### 5.1 页面断言

```python
import re

from playwright.sync_api import expect


expect(page).to_have_title("首页")
expect(page).to_have_title(re.compile("Playwright"))
expect(page).to_have_url("https://example.com/home")
expect(page).to_have_url(re.compile(".*/home"))
```

当前项目同时使用精确 URL 和正则 URL：

```python
# 打开 checkout 后，完整地址是已知值。
expect(page).to_have_url(checkout_url)

# 第三方 3DS 地址包含动态路径或查询参数。
expect(page).to_have_url(
    re.compile(r"^https://sandbox-stc\.onerway\.com/3ds-auth\?")
)
```

完整地址固定时使用字符串更严格；只有订单号、会话 ID、查询参数等部分动态时才使用正则。
正则也应约束协议、域名和稳定路径，避免只写一个过宽的关键词。

### 5.2 元素断言

```python
expect(page.get_by_text("登录成功")).to_be_visible()
expect(page.locator(".error")).to_be_hidden()
expect(page.locator(".username")).to_have_text("admin")
expect(page.locator(".message")).to_contain_text("成功")
expect(page.locator(".goods-item")).to_have_count(10)
expect(page.get_by_role("checkbox", name="同意协议")).to_be_checked()
```

当前支付项目中的常用元素断言：

| 断言 | 项目场景 | 验证的用户结果 |
| --- | --- | --- |
| `to_be_visible()` | 支付按钮、卡表单、3DS 输入框、失败 toast | 元素最终展示 |
| `to_be_hidden()` | Safari mask、成功图标 | 元素最终隐藏或未出现 |
| `to_be_enabled()` | 支付失败后的重新支付按钮 | 按钮恢复可操作状态 |
| `to_have_attribute()` | 当前币种、支付方式类型 | DOM 业务属性正确 |
| `to_have_class()` | 支付方式包含 `selected` | 支付方式已选中 |
| `to_have_text()` / `to_contain_text()` | 币种、订单号、失败原因 | 文本完全匹配或包含稳定片段 |
| `to_have_value()` | Stripe 卡号、JPay Thread code | 输入框实际值正确 |

例如，支付方式的 class 往往还包含其他样式类，所以项目使用正则验证独立的
`selected` 单词，而不是把完整 class 字符串写死：

```python
expect(payment_item).to_have_class(re.compile(r"\bselected\b"))
```

### 5.3 普通断言

```python
price = page.locator(".price").inner_text()
assert price == "￥100"

count = page.locator(".goods-item").count()
assert count > 0
```

备注：

> 页面状态优先用 `expect()`，普通数据比较可以用 `assert`。

当前项目中，普通断言主要用于已经取得的 Python 数据：

```python
order_id, order_key = parse_order_received_url(page.url)

assert order_id == "12345"
assert order_key == "abc"
```

JPay 失败用例会先用 `expect()` 等待失败 toast，再立即检查当前 URL 没有进入成功路径：

```python
expect(checkout_page.payment_failure_toast).to_be_visible(timeout=60000)
assert "/checkout/order-received/" not in page.url
```

这里的顺序很重要：`expect()` 先完成异步同步，后面的 `assert` 才是在稳定检查点比较普通字符串。

### 5.4 `expect()` 和 `assert` 的使用边界

| 场景                 | 推荐写法                                 | 原因                                 |
| ------------------ | ------------------------------------ | ---------------------------------- |
| 页面标题、URL、元素可见、文本变化 | `expect()`                           | 会自动等待，适合异步 UI                      |
| 接口返回数据、变量值、计算结果    | `assert`                             | 普通 Python 数据，不需要页面等待               |
| 判断元素此刻是否可见         | 优先 `expect(locator).to_be_visible()` | 比 `locator.is_visible()` 更适合等待页面变化 |

不太推荐：

```python
assert page.get_by_text("保存成功").is_visible()
```

更推荐：

```python
expect(page.get_by_text("保存成功")).to_be_visible()
```

原因是 `is_visible()` 更像“看一眼当前状态”，不会像 `expect()` 一样持续等待页面最终达到预期。

当前项目的断言职责分为三层：

| 位置 | 负责内容 | 示例 |
| --- | --- | --- |
| UI 测试 | 当前用例独有的用户结果 | 支付方式已选中、3DS 页面、失败 toast |
| `assert_order_received()` | 多个成功支付流程共享的结果 | 成功 URL、交易编号、成功图标、邮箱 |
| Unit 测试 | 纯 Python 规则 | URL 解析、YAML 数据构建校验、失败证据内容 |

共享成功断言的执行过程：

```text
step 1：等待 URL 进入 order-received
step 2：把 page.url 解析为订单号和 key
step 3：用 expect() 等交易编号、成功图标和邮箱渲染
step 4：把订单号和成功页截图附加到报告
```

Page Object 主要提供 Locator 和页面动作；测试结果通常留在测试或共享断言工具中。
这样页面操作可以复用，同时不会把某一条用例的业务预期隐藏在点击方法内部。

## 六、等待机制

等待用于处理页面加载、接口返回、动画渲染、元素状态变化等异步场景。

Playwright 的核心思路不是“先固定等几秒再操作”，而是：

> 等待一个可以观察和判断的条件；条件一旦满足就立即继续，超过上限才报超时。

Playwright 通常不需要像 Selenium 那样创建 `WebDriverWait`，因为等待能力已经分布在三个位置：

| 等待层次 | 解决的问题 | 常用方式 |
| ------- | ---------- | -------- |
| 动作自动等待 | 元素现在能不能操作 | `click()`、`fill()`、`check()` |
| 断言自动重试 | 操作后的页面结果是否出现 | `expect()` |
| 明确事件等待 | URL、接口响应、下载、新窗口等事件是否发生 | `wait_for_url()`、`expect_response()`、`expect_download()`、`expect_popup()` |

### 6.1 动作的自动等待

执行元素动作时，Playwright 会先检查与该动作有关的可操作条件，满足后才真正操作元素。

例如：

```python
submit_button = page.get_by_role("button", name="提交")
submit_button.click()
```

`click()` 的执行过程可以理解为：

```text
step 1：根据 Locator 查找按钮
step 2：确认只匹配到一个目标元素
step 3：等待元素可见并且位置稳定
step 4：等待元素没有被遮挡，可以接收点击事件
step 5：等待元素处于启用状态
step 6：执行点击
```

不同动作检查的条件不完全相同：

| 动作 | 主要自动等待条件 |
| ---- | ---------------- |
| `click()` | 唯一、可见、稳定、可接收事件、已启用 |
| `fill()` | 唯一、可见、已启用、可编辑 |
| `check()` | 唯一、可见、稳定、可接收事件、已启用 |

自动等待只保证“执行动作前，目标元素已经可以操作”，不保证动作后的业务结果已经完成。

例如，下面的 `click()` 成功只代表按钮被点击了，并不代表订单已经提交成功：

```python
page.get_by_role("button", name="提交订单").click()
```

因此通常还要继续等待一个用户可见的业务结果：

```python
page.get_by_role("button", name="提交订单").click()
expect(page.get_by_text("下单成功")).to_be_visible()
```

### 6.2 `expect()` 的自动重试

`expect()` 不是只检查一次。条件暂时不满足时，它会在超时时间内重复检查。

```python
success_message = page.get_by_text("保存成功")
expect(success_message).to_be_visible()
```

执行过程可以理解为：

```text
step 1：第一次检查“保存成功”是否可见
step 2：如果不可见，继续等待并重新检查
step 3：元素变为可见后，断言立即通过
step 4：超过断言超时时间仍不可见，断言失败
```

因此，验证异步页面状态时推荐：

```python
expect(page.get_by_text("保存成功")).to_be_visible()
```

不推荐：

```python
assert page.get_by_text("保存成功").is_visible()
```

`is_visible()` 更像“立即看一眼当前状态”，不会像 `expect()` 一样持续重试。

### 6.3 如何选择等待方式

| 场景 | 推荐写法 | 原因 |
| ---- | -------- | ---- |
| 点击、输入、勾选元素 | 直接使用 `click()`、`fill()`、`check()` | 动作自身已有自动等待 |
| 验证文本、可见性、属性、数量 | `expect(locator)` | 自动重试并表达测试预期 |
| 验证页面最终 URL | `expect(page).to_have_url()` | 同时完成等待和断言 |
| 只需要同步 URL 跳转流程 | `page.wait_for_url()` | 等待流程进入下一页面 |
| 等待元素出现或消失后继续执行 | `locator.wait_for()` | 适合流程控制，不负责表达业务断言 |
| 等待接口、下载或新窗口事件 | `expect_response()` 等事件上下文 | 可以在触发动作前注册监听 |
| 等待固定秒数 | 正式用例中不使用 | 无法判断页面是否真正就绪 |

判断原则：

1. 元素动作能直接完成时，不额外等待。
2. 能等待用户可见结果时，优先使用 `expect()`。
3. 只有后续流程依赖某个明确事件时，才使用显式等待。
4. 等待的条件应描述业务状态，而不是描述时间长度。

### 6.4 常见的显式等待

#### 等待 URL

如果 URL 本身就是需要验证的测试结果，使用 `expect()`：

```python
import re

expect(page).to_have_url(
    re.compile(r".*/checkout/order-received/.*")
)
```

如果只是需要等待跳转完成，再执行后续操作，可以使用：

```python
page.wait_for_url("**/checkout/order-received/**")
```

两者的区别：

| 写法 | 主要目的 |
| ---- | -------- |
| `expect(page).to_have_url()` | 验证最终 URL 符合预期 |
| `page.wait_for_url()` | 控制执行流程，等跳转发生后再继续 |

#### 等待元素状态

`locator.wait_for()` 支持以下状态：

| 状态 | 含义 |
| ---- | ---- |
| `attached` | 元素已经进入 DOM |
| `detached` | 元素已经从 DOM 移除 |
| `visible` | 元素可见 |
| `hidden` | 元素不可见或者已经从 DOM 移除 |

例如，等待第三方支付表单显示后再填写：

```python
card_form = page.locator(".adyen-checkout__dropin--ready")
card_form.wait_for(state="visible")
```

如果“支付表单必须可见”本身就是测试结果，则应使用断言：

```python
expect(card_form).to_be_visible()
```

#### 等待接口响应

等待事件时，应先注册监听，再执行触发事件的操作：

```python
with page.expect_response(
    lambda response: "/api/orders" in response.url and response.status == 200
) as response_info:
    page.get_by_role("button", name="提交订单").click()

response = response_info.value
assert response.ok
```

执行过程：

```text
step 1：expect_response() 开始监听符合条件的响应
step 2：点击“提交订单”
step 3：页面发送订单请求
step 4：监听器捕获响应并结束等待
step 5：通过 response_info.value 取得 Response 对象
```

不推荐先点击再开始等待：

```python
# 错误示例：点击发生时还没有注册响应监听。
page.get_by_role("button", name="提交订单").click()

with page.expect_response("**/api/orders") as response_info:
    pass
```

接口响应很快时，可能在进入 `expect_response()` 之前就已经完成，后面的监听将等不到这次响应。

同样的“先监听、再触发”原则也适用于下载和新窗口：

```python
with page.expect_download() as download_info:
    page.get_by_role("button", name="下载报表").click()

download = download_info.value
```

```python
with page.expect_popup() as popup_info:
    page.get_by_text("打开新窗口").click()

new_page = popup_info.value
```

#### 等待页面加载状态

页面导航时可以指定基础加载状态：

```python
page.goto(checkout_url, wait_until="domcontentloaded")
```

`DOMContentLoaded` 或 `load` 只代表浏览器加载阶段，不一定代表业务页面已经可用。前端页面还可能继续请求接口和渲染组件，因此导航后仍应等待具体的页面结果：

```python
page.goto(checkout_url, wait_until="domcontentloaded")
expect(page.get_by_role("button", name="提交订单")).to_be_visible()
```

不建议把 `networkidle` 当成通用的“页面完全加载”标准：

```python
# 不推荐作为通用等待方案
page.wait_for_load_state("networkidle")
```

现代页面可能持续轮询、上报日志或保持长连接，网络不一定会进入空闲状态。即使网络暂时空闲，也不能证明目标按钮或业务数据已经准备好。

### 6.5 超时时间的层级

超时是“最多等多久”，不是“必须等待多久”。条件提前满足时，代码会立即继续。

Playwright Python 中常见的超时分为：

| 超时类型 | 设置方式 | 主要影响 |
| -------- | -------- | -------- |
| 普通操作超时 | `page.set_default_timeout()` | Locator 动作、`locator.wait_for()` 等操作 |
| 导航超时 | `page.set_default_navigation_timeout()` | `goto()`、`reload()`、`wait_for_url()` 等导航 |
| 断言超时 | `expect.set_options()` | `expect()` 自动重试 |
| 单次超时 | 方法的 `timeout` 参数 | 只覆盖当前这次操作或断言 |

统一配置示例：

```python
from playwright.sync_api import expect

page.set_default_timeout(10000)
page.set_default_navigation_timeout(30000)
expect.set_options(timeout=10000)
```

确实较慢的单个业务结果，可以局部覆盖：

```python
expect(page.get_by_text("支付成功")).to_be_visible(timeout=15000)
```

推荐做法：

+ 为普通操作、导航和断言设置合理的统一上限
+ 只有已知的慢业务场景才设置更长的局部超时
+ 超时后应保留截图、trace、当前 URL 等失败证据

不推荐为了让用例“看起来不失败”而统一设置特别长的超时，也不推荐设置 `timeout=0` 无限等待。

### 6.6 是否需要统一封装等待

通常不需要再封装 Selenium 风格的通用等待工具。

例如下面的封装没有明显价值：

```python
def wait_and_click(page, selector: str) -> None:
    locator = page.locator(selector)
    locator.wait_for(state="visible")
    locator.click()
```

原因：

+ `click()` 本身已经等待元素满足点击条件
+ 只等待 `visible` 仍不能保证元素未被遮挡或已经启用
+ 通用封装会隐藏原始 Locator 和 Playwright 的调用日志
+ 所有操作经过同一个封装后，难以表达不同业务真正要等待的状态

更适合统一的是“超时策略”和“有业务语义的等待”：

```python
class PaymentPage:
    def wait_for_card_form(self) -> None:
        self.card_form.wait_for(state="visible")

    def wait_for_order_received(self) -> None:
        self.page.wait_for_url("**/checkout/order-received/**")
```

方法名直接说明等待的业务状态，比 `wait_for_element()` 更容易阅读和排查。

### 6.7 不推荐的等待写法

#### 固定等待

```python
import time

time.sleep(3)
```

或者：

```python
page.wait_for_timeout(3000)
```

固定等待的问题：

+ 等太短时，页面尚未准备好，用例仍然失败
+ 等太长时，即使页面已经准备好也要继续空等
+ 无法证明页面进入了预期业务状态
+ 不同机器和 CI 环境速度不同，容易产生偶发失败

`page.wait_for_timeout()` 可以在本地调试时临时使用，但不应保留在正式测试用例中。

更好的写法是等待明确结果：

```python
page.get_by_role("button", name="提交").click()
expect(page.get_by_text("提交成功")).to_be_visible()
```

#### 用 `force=True` 掩盖等待问题

```python
# 不要为了绕过遮挡、动画或禁用状态而默认强制点击
page.get_by_role("button", name="提交").click(force=True)
```

`force=True` 会跳过部分可操作性检查，它不是另一种等待方式。只有明确知道页面行为并且确实需要强制操作时才使用。

#### 捕获超时后直接忽略

```python
from playwright.sync_api import TimeoutError as PlaywrightTimeoutError

try:
    page.get_by_text("支付成功").wait_for()
except PlaywrightTimeoutError:
    pass
```

直接忽略超时会让用例在页面未达到预期状态时继续执行。只有超时本身对应明确的业务分支时，才应该捕获，例如“可选支付方式不存在则跳过用例”。

### 6.8 当前支付项目中的等待实践

当前 checkout UI 项目已经采用了以下等待方式：

| 项目位置 | 等待方式 | 目的 |
| -------- | -------- | ---- |
| `conftest.py` 的 `page` fixture | 设置普通操作超时和导航超时 | 统一项目等待上限 |
| `ensure_payment_method` fixture | `locator.wait_for(state="visible")` 并捕获超时 | 必需支付方式缺失时失败，可选方式缺失时跳过 |
| `AdyenPage.wait_for_card_form()` | 等待卡表单和 iframe 可见 | 第三方支付组件加载完成后再填写 |
| `assert_order_received()` | `wait_for_url()` 后使用 `expect()` | 先等待订单成功跳转，再验证订单号、成功图标和邮箱 |

这些例子体现了三个边界：

1. 普通点击和输入依赖 Playwright 自动等待。
2. 测试结果使用 `expect()` 进行自动重试和断言。
3. 只有支付组件、URL 或支付方式策略等明确业务状态才单独等待或封装。

### 6.9 复习结论

+ Playwright 一般不需要 `WebDriverWait`
+ 动作自动等待解决“现在能不能操作”
+ `expect()` 解决“操作后的结果是否最终出现”
+ 显式等待用于 URL、接口、下载、新窗口等明确事件
+ 监听事件时遵循“先监听、再触发”
+ 超时是等待上限，不是固定休眠时间
+ 不使用 `sleep()` 和 `wait_for_timeout()` 处理正式用例同步
+ 不封装通用的 `wait_and_click()`，只封装有业务语义的等待

## 七、pytest 集成

`pytest-playwright` 把浏览器、上下文和页面等 Playwright 能力提供为 pytest fixture。
pytest 再负责测试发现、前置数据、参数化、筛选执行、失败报告和资源清理。

### 7.1 常用 fixture

| fixture | 作用 |
| ------- | ---- |
| `page` | 当前页面，最常用 |
| `context` | 浏览器上下文，可管理 cookie、storage |
| `browser` | 浏览器实例 |
| `playwright` | Playwright 主对象，可创建 API 请求 |

测试函数通过同名参数请求 fixture：

```python
def test_checkout(page, settings, checkout_data):
    ...
```

pytest 在调用测试之前先找到并执行这些 fixture，再把它们的返回值传给测试。
fixture 也可以依赖其他 fixture，因此会形成依赖链。

当前项目覆盖了 `pytest-playwright` 的 `page` fixture，改为从插件提供的
`context` 创建页面，并设置项目自己的超时：

```python
@pytest.fixture
def page(context: BrowserContext) -> Page:
    page = context.new_page()
    page.set_default_timeout(10000)
    page.set_default_navigation_timeout(30000)
    yield page
    page.close()
```

执行过程：

```text
step 1：pytest-playwright 创建 BrowserContext
step 2：pytest 把 context 传给项目的 page fixture
step 3：fixture 创建 Page 并设置超时
step 4：执行到 yield，把 Page 交给测试
step 5：测试结束后 fixture 从 yield 后继续
step 6：关闭当前 Page
```

当前项目主要使用两种 scope：

| scope | 当前 fixture | 生命周期 |
| --- | --- | --- |
| `session` | `settings`、`test_data`、`test_info` | 整次 pytest 会话只创建一次 |
| `function` | `page`、`payment`、`checkout_data`、`ensure_payment_method` 等 | 每条测试重新创建，测试结束后销毁 |

`test_info` 在 session 内生成一次随机测试邮箱；`checkout_data` 则按每条测试当前的
`PAYMENT_KEY` 重新执行构建和校验。构建器会返回新的外层字典，但其中的 `billing` 和
`payment` 仍来自 session 级 YAML 数据，因此普通测试不应原地修改它们。JPay 失败场景
需要替换卡数据时先使用 `deepcopy()`，避免污染后续用例。

项目中的主要 fixture 依赖关系：

```text
test_data ───────────────┐
test_info ───────────────┼→ checkout_data → payment_method
request.module → payment ┘                    ├→ ensure_payment_method
                                              └→ screenshot_context
```

`payment` 通过 `request.module` 读取测试模块声明的 `PAYMENT_KEY`。例如：

```python
PAYMENT_KEY = "jpay_card"
```

pytest 调用 `payment` fixture 时，输入是当前测试模块；输出是字符串
`"jpay_card"`，后续 fixture 用它从 YAML 中选择对应支付数据。

fixture 还可以返回一个函数。`ensure_payment_method` 返回 `_ensure`，而不是在
fixture 创建阶段立即检查页面：

```python
@pytest.fixture
def ensure_payment_method(payment_method, checkout_data):
    def _ensure(checkout_page):
        checkout_page.payment_method_item(payment_method).wait_for(
            state="visible"
        )

    return _ensure
```

因此真正的页面检查发生在测试打开 checkout 并显式调用
`ensure_payment_method(checkout_page)` 时。返回函数适合“准备好配置，但必须等页面进入某个阶段后才能执行”的操作。

```ini

python_files = test_*.py
addopts = -ra
strict_config = true
strict_markers = true
```

当前配置的作用：

| `python_files = test_*.py` | 只收集符合命名规则的测试模块 |

浏览器、headed、trace、video 等运行方式没有写死在 `pytest.ini` 中，可以由命令行或
`run.py` 按场景传入。`skip_browser` 是 pytest-playwright 插件注册的 mark，
因此不需要重复写进项目的 `markers` 列表。

### 7.4 参数化

```python
import pytest


@pytest.mark.parametrize(
    "username,password",
    [
        ("admin", "123456"),
        ("test01", "123456"),
    ],
)
def test_login(page, username, password):
    page.goto("https://example.com/login")
    page.get_by_label("用户名").fill(username)
    page.get_by_label("密码").fill(password)
    page.get_by_role("button", name="登录").click()
```

装饰器参数化适合参数直接写在测试代码中的情况。当前项目的 Unit 测试用它验证多组
URL 和无效 YAML 数据：

```python
@pytest.mark.parametrize(
    ("url", "message"),
    [
        ("https://example.test/checkout/complete/1", "Unexpected"),
        ("https://example.test/checkout/order-received/1?key=", "non-empty"),
    ],
)
def test_parse_order_received_url_rejects_invalid_results(url, message):
    with pytest.raises(AssertionError, match=message):
        parse_order_received_url(url)
```

多币种列表来自 YAML，参数只有在测试收集阶段才能确定，因此项目使用
`pytest_generate_tests()`：

```python
def pytest_generate_tests(metafunc):
    if "checkout_currency" not in metafunc.fixturenames:
        return

    payment_key = getattr(metafunc.module, "PAYMENT_KEY")
    data = YamlReader.load(DATA_DIR / "test_data.yaml")
    currencies = data[payment_key]["currency_tests"]["cases"]
    metafunc.parametrize("checkout_currency", currencies, ids=currencies)
```

执行过程：

```text
step 1：pytest 收集一个带 checkout_currency 参数的测试函数
step 2：pytest 调用 pytest_generate_tests(metafunc)
step 3：hook 从当前模块取得 PAYMENT_KEY
step 4：根据 PAYMENT_KEY 读取 YAML 中的币种列表
step 5：metafunc.parametrize() 生成多条测试实例
step 6：EUR、JPY 等 ids 出现在测试名称和报告中
```

两种参数化方式的边界：

| 方式 | 参数来源 | 生成时间 | 当前项目用途 |
| --- | --- | --- | --- |
| `@pytest.mark.parametrize` | 测试代码中的固定列表 | 收集阶段 | Unit 测试的输入组合 |
| `pytest_generate_tests` | YAML 和测试模块上下文 | 收集阶段 | 支付方式对应的多币种 UI 用例 |

### 7.5 当前项目中的 pytest 执行链

一条 checkout UI 测试从收集到报告的完整过程：

```text
pytest 收集 test_*.py
→ 读取模块 PAYMENT_KEY
→ 必要时生成多币种参数
→ 创建 session 级配置和测试数据
→ 创建 function 级 checkout_data、page 和截图上下文
→ 执行 Page Object 操作与 expect() 断言
→ pytest 生成每个测试阶段的 TestReport
→ 失败时 hook 附加截图、URL、上下文和页面 HTML
→ page fixture 关闭页面
```

失败证据由 `pytest_runtest_makereport` hook wrapper 触发：

```python
@pytest.hookimpl(hookwrapper=True)
def pytest_runtest_makereport(item, call):
    outcome = yield
    report = outcome.get_result()

    if report.when != "call" or not report.failed:
        return

    page = item.funcargs.get("page")
    ...
```

执行过程：

```text
step 1：pytest 进入项目的 hook wrapper
step 2：代码执行到 yield，wrapper 暂停
step 3：pytest 和其他插件生成正常 TestReport
step 4：pytest 把 outcome 交回 wrapper
step 5：outcome.get_result() 取得真实 report
step 6：只在 call 阶段失败时读取 page 并收集证据
```

fixture 和 hook wrapper 中都出现 `yield`，但含义不同：

| 场景 | `yield` 前 | `yield` 交出的内容 | `yield` 后 |
| --- | --- | --- | --- |
| `page` fixture | 创建并配置页面 | 把 `Page` 传给测试 | 测试结束后关闭页面 |
| `hookwrapper=True` | 进入报告 hook | 暂停，让 pytest 生成报告 | 取得 `outcome` 并检查报告 |

`item.funcargs` 保存 pytest 已经为当前测试创建的 fixture 值，所以 hook 可以取得
`page`、`checkout_data` 和 `screenshot_context`。证据采集的具体内容见 10.5。

## 八、常用操作

### 8.1 表单填写、提交和断言

```python
from playwright.sync_api import Page, expect


def test_submit_form(page: Page):
    page.goto("https://example.com/register")

    page.get_by_label("邮箱").fill("test@example.com")
    page.get_by_label("密码").fill("123456")
    page.get_by_role("combobox", name="城市").select_option("shanghai")
    page.get_by_role("radio", name="企业用户").check()
    page.get_by_role("checkbox", name="同意协议").check()

    page.get_by_role("button", name="提交").click()

    expect(page.get_by_text("提交成功")).to_be_visible()
```

说明：

+ `fill()`：输入文本，会先清空原有内容。
+ `select_option()`：选择下拉框选项。
+ `check()`：勾选 checkbox 或 radio。
+ `expect()`：等待提交后的页面结果。

`select_option()` 只适用于真正的 `<select>`。当前 checkout 的国家、州和币种是由
`div`、`ul`、`li` 组成的自定义下拉框，所以项目使用“点击控件，再点击列表项”：

```python
def fill_billing_info(self, billing: dict) -> None:
    self.country_select.click()
    self.page.locator(
        f'.country-ul li[data-value="{billing["country"]["code"]}"]'
    ).click()

    self.state_select.click()
    self.page.locator(
        f'.state-ul li[data-value="{billing["state"]["code"]}"]'
    ).click()
```

选择方法取决于真实 DOM：

| 页面控件 | 推荐动作 |
| --- | --- |
| `<select>` | `select_option()` |
| `<input>` | `fill()` |
| checkbox / radio | `check()` |
| 自定义下拉框 | 先 `click()` 展开，再点击具有稳定业务属性的选项 |

当前 checkout 用例的职责顺序是：

```text
Page Object 打开页面并填写表单
→ 测试用 expect() 校验支付方式、币种或按钮状态
→ Page Object 提交订单
→ 测试或共享断言校验成功/失败结果
```

输入、点击等机械动作放在 Page Object；用户可见的业务结果放在测试中。

### 8.2 截图

截图：把页面当前状态保存成图片。

能解决什么问题：

+ 用例失败后保留现场
+ CI 环境看不到浏览器时，辅助排查页面状态
+ 对页面样式、弹窗、错误提示做人工确认

**整页截图**

```python
page.screenshot(path="screenshots/home.png", full_page=True)
```

**元素截图**

```python
page.locator(".goods-card").screenshot(path="screenshots/goods-card.png")
```

说明：

+ `full_page=True`：截取完整页面，不只是当前可视区域。
+ 元素截图适合只保留某个模块，比如商品卡片、订单详情、错误提示。
+ 截图目录需要提前存在，否则可能报路径错误。

当前项目有两条截图路径：

| 截图方式 | 保存位置 | 使用场景 |
| --- | --- | --- |
| `page.screenshot(path=...)` | `screenshots/日期/唯一文件名.png` | 测试失败后保存本地文件 |
| `page.screenshot()` | 返回 PNG bytes，直接交给 Allure | 表单填写完成和支付成功证据 |

本地截图使用 `ScreenshotContext` 组合测试名、支付方式、商品场景、执行阶段、
时间和随机后缀，避免重复执行或并行执行时覆盖文件：

```text
test_name__payment_method__checkout_case__stage__time_uuid.png
```

失败截图使用安全包装：

```python
def try_take_checkout_screenshot(page, context):
    try:
        return take_checkout_screenshot(page, context)
    except Exception as error:
        LOGGER.warning("Failed to capture checkout screenshot: %s", error)
        return None
```

截图属于诊断证据，不是被测业务结果。即使浏览器已经关闭、页面崩溃或截图本身失败，
也不能覆盖测试最初的失败原因。

checkout 截图可能包含测试邮箱和沙箱卡信息，只能作为本地或受控报告产物，
不应提交到源码仓库。

### 8.5 iframe

iframe：页面中嵌入的另一个页面。

能解决什么问题：

+ 支付页面、富文本编辑器、第三方登录常放在 iframe 中
+ 直接用 `page.get_by_xxx()` 找不到 iframe 内部元素
+ 需要进入 iframe 后再操作里面的输入框和按钮

使用 `frame_locator()` 定位 iframe：

```python
frame = page.frame_locator("#pay-frame")

frame.get_by_label("银行卡号").fill("6222000000000000")
frame.get_by_role("button", name="确认支付").click()
```

说明：

+ `page` 只能直接定位主页面元素。
+ `frame_locator()` 用来进入 iframe。
+ iframe 内的元素继续使用 `get_by_label()`、`get_by_role()` 等定位方式。
+ 不能使用 `page.locator("iframe input")` 跨过 iframe 的文档边界。

当前支付项目同时使用 `Locator` 和 `FrameLocator`，两者用途不同：

| 对象 | 定位范围 | 项目中的用途 |
| --- | --- | --- |
| `Locator` | 主页面里的 `<iframe>` 元素本身 | 等待 iframe 可见、判断 iframe 是否存在 |
| `FrameLocator` | iframe 内部的页面 | 定位并操作 iframe 内的输入框和按钮 |

项目中有两种进入 iframe 的定位链：

```text
方式一：已经取得 iframe Locator
Page → iframe Locator → content_frame → 内部 Locator

方式二：iframe 选择器可以直接表达
Page → frame_locator(...) → 内部 Locator
```

**当前项目示例：Adyen**

Adyen 的卡号、有效期和安全码可能分别位于不同 iframe 中。项目先在 Adyen 容器内根据 `data-cse` 找到字段对应的 iframe，再通过 `content_frame` 进入：

```python
def _card_field_iframe(self, field_type: str) -> Locator:
    return self.adyen_card_container.locator(
        f'[data-cse="{field_type}"] iframe'
    )

def _card_field_frame(self, field_type: str) -> FrameLocator:
    return self._card_field_iframe(field_type).content_frame

def _card_field_input(self, field_type: str) -> Locator:
    return self._card_field_frame(field_type).locator(
        f'input[data-fieldtype="{field_type}"]'
    )
```

例如填写安全码时，实际定位过程是：

```text
#card-container
└── [data-cse="encryptedSecurityCode"] iframe
    └── content_frame
        └── input[data-fieldtype="encryptedSecurityCode"]
```

`content_frame` 适合已经通过外层容器和动态属性拿到 iframe `Locator` 的情况。项目还会先对 iframe `Locator` 调用 `wait_for(state="visible")`，确认第三方支付组件已经加载，再操作内部字段。

**当前项目示例：Airwallex**

Airwallex 的卡号、有效期和 CVC 也位于不同 iframe。区别是它使用 iframe 的
`title` 区分字段：

```python
def _card_field_iframe(self, field: str) -> Locator:
    return self.airwallex_card_form.locator(
        f'iframe[title="Airwallex {field} element iframe"]'
    )

def _card_field_input(self, field: str, input_name: str) -> Locator:
    return self._card_field_iframe(field).content_frame.locator(
        f'input[name="{input_name}"]'
    )
```

Adyen 和 Airwallex 都属于“先定位外层 iframe，再通过 `content_frame` 进入”的方式。

**当前项目示例：Onerway、Yuno 和 Stripe**

如果 iframe 本身有固定、唯一的选择器，可以直接保存 `FrameLocator`：

```python
@property
def onerway_card_frame(self) -> FrameLocator:
    return self.page.frame_locator('iframe[title="pacypay iframe"]')

@property
def onerway_pay_button(self) -> Locator:
    return self.onerway_card_frame.get_by_role(
        "button",
        name="Pay",
        exact=True,
    )
```

项目中不同支付组件的 iframe 策略：

| 支付组件 | iframe 形态 | 进入方式 | 内部定位方式 |
| --- | --- | --- | --- |
| Adyen | 卡字段可能分散在多个 iframe | iframe `Locator.content_frame` | `input[data-fieldtype=...]` |
| Airwallex | 卡号、有效期、CVC 分别一个 iframe | iframe `Locator.content_frame` | `input[name=...]` |
| Onerway | 整张卡表单位于一个 iframe | `page.frame_locator()` | placeholder、role |
| Yuno | 整张卡表单位于一个 iframe | `page.frame_locator()` | `input[name=...]` |
| Stripe | 开发工具和安全卡输入分别位于 iframe | `page.frame_locator()` | role、CSS id |

iframe 操作的执行过程：

```text
step 1：在主页面中确定具体 iframe
step 2：必要时等待 iframe 元素可见
step 3：取得 FrameLocator，进入 iframe 的文档上下文
step 4：在 FrameLocator 内创建输入框或按钮 Locator
step 5：对内部 Locator 执行 fill()、click() 或 expect()
```

等待外层 iframe 可见只说明 iframe 元素已经出现在主页面。第三方组件分阶段加载时，
项目还会等待内部关键输入框可见，确认表单真正可以填写。

当前项目的选择规则：

+ iframe 选择器固定且可以直接表达时，使用 `page.frame_locator(...)`。
+ 已经先定位到具体 iframe 元素时，使用 `iframe_locator.content_frame`。
+ 页面存在多个 iframe 时，根据业务含义分别定义 `FrameLocator`，不依赖 iframe 顺序。
+ iframe 本身的等待和可见性判断使用 `Locator`，内部元素操作使用 `FrameLocator`。
+ iframe 选择器和内部字段选择器统一封装在对应 Page Object 中，不放到测试用例里。

### 8.6 新窗口

新窗口：点击某个链接或按钮后，浏览器打开新的 tab 或 popup。

能解决什么问题：

+ 支付跳转新页面
+ 点击“帮助中心”“协议详情”打开新窗口
+ OAuth 登录跳转第三方页面

使用 `expect_popup()` 等待新页面：

```python
with page.expect_popup() as popup_info:
    page.get_by_text("打开新窗口").click()

new_page = popup_info.value
expect(new_page).to_have_title("新窗口")
```

说明：

+ `expect_popup()` 要包住触发新窗口的操作。
+ `popup_info.value` 才是新打开的页面对象。
+ 后续断言、点击、输入都要对 `new_page` 操作。

### 8.7 下载文件

下载文件：监听页面触发的浏览器下载事件，并保存到指定路径。

能解决什么问题：

+ 验证导出报表功能
+ 验证合同、发票、附件是否能下载
+ CI 环境中保存下载产物用于排查

使用 `expect_download()` 等待下载：

```python
with page.expect_download() as download_info:
    page.get_by_role("button", name="下载报表").click()

download = download_info.value
download.save_as("downloads/report.xlsx")
```

说明：

+ `expect_download()` 要包住触发下载的操作。
+ `save_as()` 可以把临时下载文件保存为指定文件名。
+ 下载后的文件是否正确，可以继续用文件读取、表格解析等方式断言。

## 九、登录态复用

登录态复用：先登录一次并保存 cookie、localStorage，后续用例直接使用。

本质上，登录态保存的是 `BrowserContext` 的 `storage_state`。恢复这个状态后，新页面就像已经登录过一样，可以直接访问登录后的业务页面。

它是什么：

+ Playwright 可以把当前浏览器上下文的登录信息保存成 JSON 文件。
+ JSON 文件里通常包含 cookie、localStorage 等状态。
+ 后续新建浏览器上下文时加载这个文件，就相当于已经登录。

能解决什么问题：

+ 减少重复登录
+ 提升执行速度
+ 避免登录页影响所有用例
+ 避免验证码、短信、人机校验阻塞自动化

### 9.1 保存登录态

怎么用：

1. 先写一条登录用例。
2. 登录成功后，确认已经进入登录后页面。
3. 调用 `storage_state()` 保存状态。

```python
from playwright.sync_api import Page, expect


def test_save_login_state(page: Page):
    page.goto("https://example.com/login")

    page.get_by_label("用户名").fill("admin")
    page.get_by_label("密码").fill("123456")
    page.get_by_role("button", name="登录").click()

    expect(page.get_by_text("个人中心")).to_be_visible()

    page.context.storage_state(path="auth/state.json")
```

说明：

+ `page.context` 表示当前浏览器上下文。
+ `storage_state(path=...)` 会把登录状态保存到文件。
+ 保存前必须先断言登录成功，否则可能保存的是未登录状态。

### 9.2 使用登录态

在 `conftest.py` 中配置：

```python
import pytest


@pytest.fixture(scope="session")
def browser_context_args(browser_context_args):
    return {
        **browser_context_args,
        "storage_state": "auth/state.json",
    }
```

用例中直接访问登录后的页面：

```python
from playwright.sync_api import expect


def test_user_center(page):
    page.goto("https://example.com/user")

    expect(page.get_by_text("个人中心")).to_be_visible()
```

### 9.3 使用注意

登录态不是永久有效的，需要考虑有效期。

常见做法：

+ 登录态过期后，重新运行保存登录态的用例。
+ 登录用例单独放在 `test_login.py` 或初始化脚本中。
+ 业务用例默认复用 `auth/state.json`。
+ 不同角色可以保存不同文件，例如 `admin.json`、`user.json`。

示例：

```text
auth/
├── admin_state.json
└── user_state.json
```

备注：

> `auth/state.json` 不建议提交到公共仓库，可以加入 `.gitignore`。

## 十、调试和报告

调试和报告：用来定位失败原因、保留执行现场、给团队查看结果。

能解决什么问题：

+ 本地能过，CI 失败
+ 页面失败时不知道实际停在哪里
+ 失败日志只有断言信息，不知道前面发生了什么
+ 团队需要查看测试结果和失败截图

常用工具：

| 工具 | 作用 | 适合场景 |
| --- | --- | --- |
| `--headed` | 显示浏览器 | 本地观察执行过程 |
| `--slowmo` | 放慢操作 | 学习、演示、排查交互 |
| `PWDEBUG=1` | 打开 Inspector | 调试 locator 和单步执行 |
| `--tracing` | 生成 trace | 失败回放、网络和 DOM 排查 |
| `--screenshot` | 保存截图 | 查看失败瞬间页面 |
| `--video` | 保存视频 | 排查动画、跳转、闪现问题 |

### 10.1 调试命令

**显示浏览器**

```shell
pytest -v --headed
```

`--headed` 适合观察浏览器真实执行过程，排查“页面实际长什么样”“是不是点错了元素”这类问题。

**慢速运行**

```shell
pytest -v --headed --slowmo 500
```

`--slowmo 500` 表示每个 Playwright 操作之间放慢 500ms，适合学习、演示和肉眼观察流程。正式回归测试一般不建议长期打开。

**Playwright Inspector**

```shell
PWDEBUG=1 pytest -v tests/test_login.py
```

`PWDEBUG=1` 会打开 Playwright Inspector，可以逐步执行、查看 locator、暂停页面，适合定位复杂交互问题。

### 10.2 trace 追踪

trace：Playwright 的执行回放文件。

它能看到：

+ 每一步操作
+ 操作前后的页面快照
+ 网络请求
+ 控制台日志
+ 失败截图

适合解决：

+ 不知道哪一步点错了
+ 页面状态和预期不一致
+ 接口返回慢导致页面没渲染出来
+ CI 失败但本地不复现

**失败时保留 trace**

```shell
pytest -v --tracing retain-on-failure
```

**始终保留 trace**

```shell
pytest -v --tracing on
```

**查看 trace**

```shell
playwright show-trace test-results/**/trace.zip
```

注意：

> `pytest-playwright` 生成 Playwright trace 的参数是 `--tracing`。`pytest` 自带的 `--trace` 是进入 Python 调试器，不是 Playwright trace 文件。

### 10.3 截图和视频

截图和视频：比日志更直观地保留失败现场。

能解决什么问题：

+ 失败时页面跳到了哪里
+ 是否出现了错误提示、遮罩、弹窗
+ 是否有动画、跳转、新窗口导致操作时机不对

怎么用：

```shell
pytest -v --screenshot only-on-failure
pytest -v --video retain-on-failure
```

| 工具 | 适合排查什么 |
| --- | --- |
| trace | 操作步骤、DOM 快照、网络请求、console 日志 |
| screenshot | 失败瞬间页面状态、弹窗、错误提示 |
| video | 动画、跳转、新窗口、偶发闪现问题 |

一般排查优先级：

1. 先看失败日志和断言信息。
2. 再看截图确认页面状态。
3. 如果还不清楚，打开 trace 回放完整过程。
4. 对动画或偶发问题，再结合 video。

当前项目可以组合插件能力和自定义证据：

+ `--screenshot only-on-failure`、`--video retain-on-failure`：需要时通过命令行开启，由 pytest-playwright 管理产物。
+ `pytest_runtest_makereport`：在测试 call 阶段失败时保存项目命名规则的截图。
+ `allure_evidence.py`：在表单填写完成和支付成功时，把截图直接附加到 Allure。

插件产物适合统一保留执行现场；项目自定义证据可以带上支付方式、商品场景、订单号等业务上下文。

### 10.4 HTML 报告

HTML 报告：把 pytest 执行结果生成网页文件。

能解决什么问题：

+ 方便把测试结果发给别人看
+ 比终端输出更容易查看失败用例
+ 适合本地练习和轻量级项目

安装：

```shell
pip install pytest-html
```

运行：

```shell
pytest -v --html=report.html --self-contained-html
```

说明：

+ `--html=report.html`：生成报告文件。
+ `--self-contained-html`：把样式资源放进一个 HTML 文件里，方便发送。
+ 企业项目如果需要更完整的趋势、附件、分类，可以再接 Allure。

### 10.5 当前项目的 Allure 与失败证据

当前项目使用 `allure-pytest` 生成结果数据，再由 Allure CLI 按需生成静态报告。
Allure 不只展示“通过或失败”，还负责组织支付测试、展示执行步骤和保存诊断证据。

**报告层级**

```python
@allure.epic("JPay")
@allure.feature("Card")
@allure.story("Checkout success")
@allure.title("JPay Card 卡支付")
def test_jpay_card(page, checkout_data):
    ...
```

| Allure 字段 | 当前项目含义 | 示例 |
| --- | --- | --- |
| `epic` | 支付渠道 | JPay、Adyen、Stripe |
| `feature` | 支付产品或方式 | Card、Apple、Google |
| `story` | 业务场景 | Checkout success、Checkout failure、多币种 |
| `title` | 报告中的用例名称 | JPay Card 卡支付 |
| `dynamic.title` | 根据运行参数生成名称 | `Adyen EUR 卡支付验证` |

pytest mark 控制执行筛选，Allure 层级控制报告导航。一个用例可以同时具有
`@pytest.mark.card` 和 `@allure.feature("Card")`，但两者不是同一套机制。

**测试步骤**

```python
with allure.step("填写 JPay Card checkout 表单"):
    checkout_page.fill_checkout(checkout_data)

with allure.step("提交 JPay Card 订单"):
    checkout_page.submit_order()
```

`allure.step()` 包住一个有业务意义的代码块。报告按时间顺序显示每一步的状态和耗时，
可以直接看出失败发生在打开页面、填写表单、第三方验证还是成功页断言。

**成功证据与失败证据**

| 触发时机 | 证据 | 采集位置 |
| --- | --- | --- |
| checkout 填写完成 | 商品 checkout URL、整页截图 | `attach_filled_checkout_evidence()` |
| 订单成功 | 订单号、成功页截图 | `attach_order_success_evidence()` |
| 测试 call 阶段失败 | 失败截图、当前 URL、checkout 上下文、页面 HTML | `pytest_runtest_makereport` |

失败证据的执行过程：

```text
step 1：测试在 call 阶段失败
step 2：pytest 先生成正常 TestReport
step 3：hook wrapper 检查 report.when 和 report.failed
step 4：从 item.funcargs 取得 page 和 screenshot_context
step 5：保存本地失败截图
step 6：把截图、URL、上下文 JSON 和 HTML 附加到 Allure
step 7：page fixture 继续 teardown 并关闭页面
```

`checkout-context` 只附加支付方式、商品 ID、优惠券、测试邮箱等诊断字段，
不会主动把 Card 字段复制进去。但失败截图和原始页面 HTML 仍可能包含沙箱卡、测试邮箱、
订单 key 或 token，因此 `screenshots/`、`reports/` 和 Allure 结果都属于受控测试产物，不能提交到源码仓库或公开分享。

**证据失败不能覆盖业务失败**

截图和 Allure 附件都使用 `try/except` 包装：

```python
try:
    screenshot = page.screenshot(full_page=True)
    allure.attach(screenshot, attachment_type=AttachmentType.PNG)
except Exception as error:
    LOGGER.warning("Allure 截图证据附加失败: %s", error)
```

被测支付结果是主流程；报告和截图是辅助证据。如果附加证据失败，项目只记录 warning，
不能把原来的断言失败改成另一个报告异常，也不能让支付用例因此假通过。

**`run.py` 的执行边界**

当前 wrapper 的运行过程：

```text
清理上一轮 allure-results
→ pytest.main() 运行默认 UI 目标并接收额外命令行参数
→ 失败用例最多重跑 1 次，间隔 2 秒
→ 结果写入 reports/allure-results
→ Allure CLI 存在时生成单文件静态报告
→ 用 pytest_exit_code 作为进程退出码
```

Allure CLI 缺失、没有结果文件或静态报告生成失败时，只跳过报告生成，不替换 pytest 的退出结果。
因此自动化命令是否成功始终由测试结果决定，而不是由可选报告工具决定。

## 十一、UI + API 混合测试

UI + API 混合测试：用 UI 完成用户操作，用 API 校验后台结果。

它是什么：

+ UI 负责模拟真实用户操作。
+ API 负责验证服务端状态。
+ 两者结合，既能验证前端流程，也能验证业务结果。

能解决什么问题：

+ 页面显示成功，但后台数据没有真正保存
+ 只靠 UI 很难验证订单、库存、积分等隐藏状态
+ 页面列表刷新慢，不适合全靠 UI 查找结果
+ 复杂业务断言写在 UI 上会很长、很脆弱

适合场景：

+ 页面提交订单后，接口校验订单状态
+ 页面创建用户后，接口查询用户信息
+ 页面支付后，接口校验支付结果

### 11.1 API 请求

Playwright 自带 API 请求能力，不一定要再安装 `requests`。

怎么用：

1. 通过 `playwright.request.new_context()` 创建请求上下文。
2. 调用 `get()`、`post()`、`put()`、`delete()` 等方法。
3. 用 `status`、`ok`、`json()` 断言响应。
4. 请求结束后调用 `dispose()` 释放资源。

```python
def test_api_request(playwright):
    api = playwright.request.new_context(base_url="https://api.example.com")

    response = api.get("/users/1")

    assert response.ok
    assert response.json()["id"] == 1

    api.dispose()
```

说明：

+ `base_url` 可以减少重复写域名。
+ `response.ok` 表示状态码在 200-299。
+ API 测试适合校验业务状态，不适合替代所有页面断言。

### 11.2 UI 操作 + API 校验

典型流程：

1. UI 打开页面。
2. UI 完成用户操作。
3. 页面断言用户能看到成功提示。
4. 从页面、接口或测试数据中拿到业务 ID。
5. API 查询后台状态并断言。

```python
from playwright.sync_api import Page, expect


def test_create_order(page: Page, playwright):
    api = playwright.request.new_context(base_url="https://api.example.com")

    page.goto("https://example.com/shop")
    page.get_by_text("测试商品").click()
    page.get_by_role("button", name="提交订单").click()

    expect(page.get_by_text("下单成功")).to_be_visible()

    order_id = page.get_by_test_id("order-id").inner_text()
    response = api.get(f"/orders/{order_id}")

    assert response.ok
    assert response.json()["status"] == "created"

    api.dispose()
```

备注：

> 页面只验证用户看到的结果，业务数据建议通过 API 再校验一次。

### 11.3 Mock 接口响应

Mock 接口：拦截浏览器发出的请求，并返回自己准备的数据。

能解决什么问题：

+ 后端接口还没开发完，前端页面需要先测
+ 真实接口数据不稳定，影响 UI 用例
+ 很难构造异常场景，例如余额不足、库存为 0、权限不足
+ 不想让测试环境产生真实订单或真实支付

有时只想验证前端页面展示，不想依赖真实后端返回，可以用 `page.route()` 拦截接口并返回模拟数据。

```python
from playwright.sync_api import Page, expect


def test_mock_user_api(page: Page):
    page.route(
        "**/api/user",
        lambda route: route.fulfill(
            status=200,
            content_type="application/json",
            body='{"name": "Test User"}',
        ),
    )

    page.goto("https://example.com/profile")

    expect(page.get_by_text("Test User")).to_be_visible()
```

说明：

+ `page.route()` 要尽量写在触发请求之前。
+ `route.fulfill()` 表示直接返回模拟响应。
+ `route.continue_()` 表示放行真实请求。
+ Mock 适合验证前端展示逻辑，但会绕过真实后端，不适合替代完整端到端测试。

简单放行并观察请求：

```python
def log_order_request(route):
    request = route.request
    print(request.method, request.url)
    route.continue_()


page.route("**/api/orders", log_order_request)
page.get_by_role("button", name="提交订单").click()
```

### 12.1 pytest.ini

`pytest.ini` 用来放默认运行参数和 mark 注册。

```ini
[pytest]
testpaths = tests
python_files = test_*.py
addopts = -ra
strict_config = true
strict_markers = true
markers =
    smoke: stable checkout smoke coverage
    card: card payment coverage
    apple: Apple payment entry coverage
    google: Google payment entry coverage
    negative: negative checkout scenarios
    slow: long-running checkout scenarios
    currency: multi-currency checkout coverage
```

解决的问题：

+ 固定测试发现目录和文件命名规则
+ 未注册 mark 或错误配置立即失败
+ 为冒烟、支付类型、失败场景和多币种建立统一筛选入口
+ 保留浏览器、headed、trace 等参数由具体运行场景决定

### 12.2 conftest.py

`conftest.py` 是 pytest 自动发现的项目级测试支持模块。测试文件不需要导入其中的 fixture 和 hook。

当前项目中的职责：

| 职责 | 当前实现 | 输出或影响 |
| --- | --- | --- |
| 动态参数化 | `pytest_generate_tests()` | 从 YAML 生成币种测试实例 |
| 页面生命周期 | `page` fixture | 创建页面、设置超时、测试后关闭 |
| 配置和数据 | `settings`、`test_data`、`test_info` | session 级共享输入 |
| 用例选择 | `payment` | 从模块 `PAYMENT_KEY` 取得支付 key |
| 数据构建 | `checkout_data` | 合并并校验支付、客户和账单数据 |
| 支付方式策略 | `ensure_payment_method` | 必需方式缺失则失败，可选方式缺失则跳过 |
| 截图命名 | `screenshot_context` | 描述测试名、支付方式、商品和阶段 |
| 失败报告 | `pytest_runtest_makereport` | 附加截图、URL、上下文和 HTML |

`conftest.py` 适合放跨多个测试模块共享、并且确实属于 pytest 生命周期的能力。
支付页面的选择器和点击动作不放在这里，而是放在 Page Object；某一条支付用例的业务断言也不放在 fixture 中。

### 12.3 tests 目录

`tests/` 按执行成本和测试目标分成 UI 与 Unit：

```text
tests/
├── ui/
│   ├── test_adyen.py
│   ├── test_airwallex.py
│   ├── test_jpay_card.py
│   ├── test_jpay_card_failure.py
│   └── ...
└── unit/
    ├── test_checkout_data_builder.py
    ├── test_order_assertions.py
    └── test_evidence_redaction.py
```

UI 测试负责：

+ 打开真实 checkout 页面
+ 选择币种和支付方式
+ 填写客户、账单、卡和 3DS 数据
+ 验证成功页、失败提示或支付入口
+ 通过 Allure step 表达业务执行顺序

Unit 测试负责：

+ checkout 数据必填字段和支付 key 一致性
+ order-received URL 的解析规则
+ 失败证据需要保留的测试环境内容

两层测试的边界：

| 类型 | 是否启动浏览器 | 失败说明什么 |
| --- | --- | --- |
| UI | 是 | 用户 checkout 流程、第三方组件或页面结果不符合预期 |
| Unit | 否 | 数据构建、解析或诊断规则本身有错误 |

纯 Python 规则优先用 Unit 测试快速覆盖，不需要为了验证字符串解析或字典校验而打开浏览器。

### 12.4 当前支付项目的分层结构

当前项目的运行输入来自三类 YAML：

| 输入文件 | 控制内容 |
| --- | --- |
| `config/test_sites.yaml` | checkout `base_url`、`path`、`source` |
| `data/test_data.yaml` | 商品、优惠券、支付方式、沙箱卡、3DS、多币种和必需/可选策略 |
| `data/test_info.yaml` | 测试邮箱、姓名、国家和州 |

从配置到 UI 断言的执行链：

```text
test_sites.yaml ───────────────────────────→ Settings.build_checkout_url()
                                                   ↓
test_data.yaml ─┐                         checkout URL
                ├→ CheckoutDataBuilder ─→ checkout_data
test_info.yaml ─┘                                 ↓
                                      支付专属 Page Object
                                                   ↓
                                  UI 测试 expect()/普通 assert
                                                   ↓
                             order_assertions / Allure evidence
```

每一层的输入和输出：

| 层 | 输入 | 输出 | 不负责什么 |
| --- | --- | --- | --- |
| YAML | 可维护的环境和测试值 | 原始字典 | 不操作浏览器 |
| `CheckoutDataBuilder` | 支付数据和账单数据 | 经过校验的 `checkout_data` | 不构造页面选择器 |
| `Settings` | site 配置和 `checkout_data` | 编码完成的 checkout URL | 不填写表单 |
| Page Object | `Page` 和 `checkout_data` | 页面动作及 Locator | 不隐藏当前测试独有的业务断言 |
| UI 测试 | URL、Page Object、fixture | 用户流程和断言结果 | 不重复定义选择器 |
| `utils` | 页面、订单号、截图上下文 | 共享断言和报告证据 | 不决定支付用例步骤 |

Page Object 的继承关系：

```text
CheckoutPage
├── AdyenPage
├── AirwallexCardPage
├── AntomCardPage
├── JPayCardPage
├── JPayApplePage
├── JPayGooglePage
├── OnerwayCardPage
├── StripePage
└── YunoPage
```

`CheckoutPage` 提供打开页面、选择语言和币种、填写邮箱和账单、成功页 Locator 等共享能力。
支付专属子类只增加对应支付方式的选择器、卡组件、3DS 和提交动作。

这种分层解决了三个问题：

1. 环境、测试数据和测试流程可以分别修改。
2. 相同 checkout 动作不在每个支付类中重复实现。
3. 测试保持“准备数据 → 调用页面动作 → 断言用户结果”的可读结构。

## 十三、常见问题

### 13.1 元素定位不到

现象：

+ 报错提示元素不存在
+ 本地能找到，CI 找不到
+ 页面上肉眼看到了，但 Playwright 找不到

常见原因：

+ 元素还没加载出来
+ 元素在 iframe 里
+ 元素文本和预期不一致
+ 定位器依赖样式，前端改版后失效
+ 当前页面不是预期页面

排查：

+ 页面是否打开正确
+ 元素是否在 iframe 中
+ 元素是否需要等待接口返回
+ 定位器是否过于依赖样式

```python
page.pause()
print(page.content())
```

解决思路：

```python
expect(page.get_by_text("用户管理")).to_be_visible()
page.get_by_role("button", name="新增用户").click()
```

如果元素在 iframe 中：

```python
frame = page.frame_locator("#main-frame")
frame.get_by_role("button", name="新增用户").click()
```

当前支付项目的定位失败还要区分三种情况：

| 情况 | 先检查什么 | 处理方向 |
| --- | --- | --- |
| checkout 支付方式没有出现 | 当前 URL、商品 ID、支付 method、`payment_method_required` | 判断是业务不可用还是选择器失效 |
| 第三方卡字段找不到 | iframe 元素、iframe 的 title/属性、内部真实 DOM | 确认是否进入正确 FrameLocator |
| 相同元素有隐藏副本 | 元素数量、可见性、所属容器 | 使用容器限制或 `filter(visible=True)` |

`ensure_payment_method` 已经把支付方式不可用分成两种业务结果：必需方式缺失时失败，
可选方式缺失时跳过。因此出现 TimeoutError 时，不能一律认定为“等待不够长”，也可能是当前商品本来没有该支付方式。

项目中的推荐排查顺序：

```text
step 1：查看失败报告中的 current-url、截图和 page-html
step 2：确认页面、商品和支付方式是否正确
step 3：检查元素是在主页面还是第三方 iframe
step 4：用真实 DOM 对比 Page Object 中的选择器
step 5：只修改发生差异的最小选择器或定位范围
step 6：重新运行受影响的真实 UI 用例
```

如果页面结构已经变化，应修复 Page Object。增加 `sleep()` 只能推迟报错，不能修复错误的 DOM 路径。

### 13.2 点击没有效果

现象：

+ 点击后页面没有跳转
+ 按钮看起来存在，但没有触发事件
+ 偶尔成功，偶尔失败

常见原因：

+ 元素被遮挡
+ 按钮还没变成可点击状态
+ 点到了相同文本的另一个元素
+ 前端点击后需要等待接口或页面结果

先确认元素状态：

```python
locator = page.get_by_role("button", name="提交")

expect(locator).to_be_visible()
expect(locator).to_be_enabled()

locator.click()
```

再等待明确结果：

```python
locator.click()
expect(page.get_by_text("提交成功")).to_be_visible()
```

当前项目曾遇到 Billing 自定义下拉框保持展开、遮挡 Continue 或支付按钮的情况。
Adyen 和 Airwallex 在完成账单选择后使用：

```python
# Billing 下拉偶发保持展开，避免其遮挡后续按钮。
page.keyboard.press("Escape")
```

这里修复的是页面真实交互状态：先关闭已经完成选择的浮层，再点击后续按钮。
如果直接使用 `click(force=True)`，虽然可能绕过“接收点击事件”的检查，但点击可能落在错误状态下，
也会掩盖浮层没有关闭的问题。

点击问题的判断顺序：

1. Locator 是否只匹配一个目标。
2. 目标是否可见、启用并且没有被浮层遮挡。
3. 是否需要先关闭菜单、mask 或第三方工具面板。
4. 点击后应该等待哪个 URL、表单、提示或按钮状态。

多数时候不需要在每次点击前重复 `to_be_visible()` 和 `to_be_enabled()`，因为 `click()`
已经执行相应的可操作性检查。只有可见或启用状态本身就是测试结果时，才单独写断言。

### 13.3 用例偶发失败

偶发失败：同一条用例有时通过，有时失败。

这类问题通常不是断言本身，而是等待、数据、环境、定位器不稳定。

优先处理：

+ 不使用 `time.sleep`
+ 使用 `expect()` 断言
+ 使用稳定定位器
+ 失败时打开 trace
+ 测试数据保持独立，避免用例之间互相影响

```shell
pytest -v --tracing retain-on-failure --screenshot only-on-failure
```

例子：

```python
# 不推荐
page.get_by_role("button", name="保存").click()
assert page.get_by_text("保存成功").is_visible()

# 推荐
page.get_by_role("button", name="保存").click()
expect(page.get_by_text("保存成功")).to_be_visible()
```

当前项目中的偶发风险和处理方式：

| 风险 | 项目处理方式 |
| --- | --- |
| checkout 基础 DOM 已完成，但业务控件还没出现 | `DOMContentLoaded` 后等待语言或支付控件 |
| 第三方卡组件分阶段加载 | 等 iframe 和内部关键字段，而不是固定等待 |
| 3DS、Thread 或渠道回跳较慢 | 对明确的 URL 或元素使用局部 15/30 秒超时 |
| 支付失败回调明显更慢 | 只把失败 toast 的单次断言放宽到 60 秒 |
| 重复节点或隐藏模板 | 容器内定位、`exact=True`、`filter(visible=True)` |
| YAML 数据缺字段或支付 key 不一致 | `CheckoutDataBuilder` 校验并由 Unit 测试覆盖 |
| 失败现场难以复现 | 自动保存截图、当前 URL、上下文和页面 HTML |

`run.py` 当前配置失败用例最多重跑一次，并在重跑前等待 2 秒。rerun 的边界是：

+ 可以缓解一次性的网络或测试环境波动。
+ 第一次失败仍然说明流程存在不稳定信号，应结合 Allure、截图和 trace 排查。
+ 如果选择器、数据或等待条件本身错误，重跑可能持续失败，也可能偶然通过并掩盖问题。
+ 不能用不断增加重跑次数代替修复根因。

偶发失败的诊断过程：

```text
先确认失败步骤
→ 查看 current-url 和截图
→ 检查 page-html 或 trace 中的真实 DOM
→ 判断是定位、等待、数据还是环境问题
→ 做最小修复
→ 复跑原失败用例验证
```

### 13.4 每条用例都要登录

现象：

+ 每条 UI 用例开头都写一遍登录流程
+ 执行速度很慢
+ 登录页一失败，所有业务用例都失败
+ 登录涉及验证码或短信，无法稳定自动化

解决：

+ 单独保存登录态
+ 在 `conftest.py` 中复用 `storage_state`
+ 登录相关用例和业务用例分开维护

推荐流程：

1. 登录用例只负责验证登录功能。
2. 初始化脚本或单独用例负责生成 `auth/state.json`。
3. 业务用例默认复用登录态。
4. 如果状态过期，重新生成登录态。

### 13.5 断言应该写页面还是接口

原则：

+ 用户能看到的结果，用页面断言。
+ 后台业务状态，用 API 断言。
+ 不要为了验证数据库状态，在页面上绕很多步。

例子：

```python
expect(page.get_by_text("下单成功")).to_be_visible()

response = api.get(f"/orders/{order_id}")
assert response.json()["status"] == "created"
```

解决的问题：

+ UI 用例更短
+ 业务断言更可靠
+ 页面改版时，用例维护成本更低
