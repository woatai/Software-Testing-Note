# CI/CD 学习笔记：从接口自动化项目理解 CI/CD

> 适用场景：接口自动化测试项目、测试开发学习、面试复习  
> 核心目标：先理解 CI/CD 是什么，再把接口自动化项目接入 CI/CD。

---

# 1. 一句话理解 CI/CD

最简单的记法：

> **CI = 自动验证代码**  
> **CD = 自动交付 / 部署代码**

可以把完整流程理解为：

```text
代码提交
   ↓
CI
   ↓
自动检查 / 构建 / 测试
   ↓
验证通过
   ↓
CD
   ↓
部署到对应环境
```

---

# 2. 什么是 CI？

CI 的英文是：

**Continuous Integration**

中文：

**持续集成**

## 2.1 用接口自动化项目理解 CI

假设开发修改了支付接口，然后提交代码：

```text
开发修改代码
    ↓
git push
    ↓
CI 自动触发
    ↓
拉取最新代码
    ↓
安装项目依赖
    ↓
执行自动化测试
    ↓
判断成功 / 失败
```

对于我的接口自动化项目，可以先简单理解成：

> **提交代码后，CI 自动帮我跑接口回归测试，并告诉我这次代码有没有问题。**

这个理解是正确的。

但更准确地说：

> CI 不只是“自动跑回归测试”，而是代码发生变化后，自动完成构建、检查、测试等验证工作。

CI 中可能包含：

- 代码检查
- 编译 / 构建
- 单元测试
- 接口自动化测试
- UI 自动化测试
- 安全扫描
- 测试报告
- 质量门禁

所以：

```text
CI ≠ 只有自动化测试

CI = 一套自动验证代码质量的流程
```

---

# 3. 为什么叫“持续集成”？

假设团队中：

```text
开发 A → 修改订单模块
开发 B → 修改支付模块
开发 C → 修改库存模块
```

每个人单独开发时可能都没有问题。

但是代码合并后：

```text
订单
 +
支付
 +
库存
 ↓
整个系统
```

可能出现新的问题。

因此 CI 的核心思想之一就是：

> 开发人员频繁提交代码，并通过自动化手段持续验证“代码合并到一起以后是否仍然正常”。

这就是“Integration（集成）”。

---

# 4. 什么是 CD？

CD 常见有两层含义：

## 4.1 Continuous Delivery

中文：

**持续交付**

意思是：

> CI 验证通过以后，代码已经具备发布条件，但最终发布生产环境可能仍然需要人工确认。

例如：

```text
代码提交
   ↓
CI
   ↓
构建
   ↓
自动化测试
   ↓
全部通过
   ↓
生成可发布版本
   ↓
人工点击发布
   ↓
生产环境
```

---

## 4.2 Continuous Deployment

中文：

**持续部署**

相比持续交付更加自动化：

```text
代码提交
   ↓
CI 自动验证
   ↓
测试通过
   ↓
自动部署
   ↓
生产环境
```

不需要人工点击发布。

---

# 5. CI 和 CD 的区别

最容易记的一句话：

> **CI 负责验证代码，CD 负责发布代码。**

例如：

```text
                CI
代码提交
   ↓
构建
   ↓
代码检查
   ↓
自动化测试
   ↓
验证通过
----------------------
                CD
   ↓
部署测试环境
   ↓
部署预发布环境
   ↓
部署生产环境
```

注意：

> **编译 / 构建通常可以属于 CI，而不是把“编译”理解成 CD 的核心。**

所以不要简单记成：

```text
CI = 测试
CD = 编译
```

更准确的是：

```text
CI = 自动验证
CD = 自动交付 / 部署
```

# 6. 一次 git push 之后发生了什么？

这是理解 CI 最重要的一条链路。

假设我执行：

```bash
git add .
git commit -m "add payment api test"
git push
```

之后可能发生：

```text
我的电脑
   ↓
git push
   ↓
GitHub / GitLab
   ↓
产生代码变化事件
   ↓
满足 CI 触发条件
   ↓
创建一条 CI 流水线
   ↓
找一台机器执行任务
   ↓
拉取代码
   ↓
准备运行环境
   ↓
安装依赖
   ↓
执行 pytest
   ↓
生成测试结果
   ↓
判断成功 / 失败
```

这就是一次 CI 的基本执行过程。

---

# 7. Git 和 CI 不是一回事

Git 的主要作用：

> **代码版本管理**

例如：

```text
git add
git commit
git push
```

GitHub Actions、GitLab CI、Jenkins 等主要负责：

> **自动执行流水线**

所以：

```text
Git
负责管理代码

CI 平台
负责自动执行任务
```

不要把 Git 本身理解成 CI。

---

# 8. Trigger：什么时候自动执行？

CI 不会无缘无故运行。

它需要一个触发条件。

这个触发条件叫：

**Trigger**

常见触发方式：

- git push
- 创建 Pull Request
- 创建 Merge Request
- 合并代码
- 创建 Tag
- 定时执行
- 手动执行

例如：

```text
main 分支发生 push
        ↓
触发 CI
```

也可以设计成：

```text
开发提交代码
        ↓
自动执行冒烟接口测试
```

或者：

```text
每天凌晨
   ↓
执行完整接口回归
```

---

# 9. Runner / Agent 是什么？

这是 CI 中非常重要的概念。

CI 平台虽然负责安排任务，但真正执行命令的是一台机器。

例如真正执行：

```bash
pip install -r requirements.txt
pytest
```

的是：

> **Runner / Agent**

可以这样理解：

```text
CI 平台
负责安排任务

Runner / Agent
负责真正干活
```

类比工作：

```text
测试负责人：
“把接口回归跑一下”

        ↓

测试工程师：
真正执行 pytest
```

所以：

```text
CI 平台 ≈ 负责人

Runner / Agent ≈ 真正执行任务的人
```

不同平台名称略有不同：

- GitLab → GitLab Runner
- GitHub Actions → Runner
- Jenkins → Agent / Node

本质都是：

> **执行 CI 命令的机器或运行环境。**

---

# 10. 为什么本地能运行，CI 不一定能运行？

这是非常重要的工程化问题。

例如本地：

```text
Python 3.12
requests 已安装
已经配置 TEST_TOKEN
可以访问测试数据库
```

CI Runner 上可能：

```text
Python 3.10
缺少某些依赖
没有 TEST_TOKEN
无法访问数据库
```

于是：

```text
本地 pytest
→ PASS

CI pytest
→ FAIL
```

所以：

> **本地环境 ≠ CI 环境**

这也是为什么项目需要：

- requirements.txt
- 环境变量
- 配置文件
- Docker
- 固定依赖版本

目标是：

> **让项目运行环境尽可能可复现。**

---

# 11. requirements.txt 为什么重要？

Runner 拿到代码以后，并不知道项目需要哪些 Python 包。

因此需要通过：

```bash
pip install -r requirements.txt
```

安装依赖。

例如：

```text
pytest
requests
allure-pytest
PyYAML
```

项目应该尽量做到：

> 任何一台新机器拿到代码后，都可以根据项目配置把运行环境搭起来。

这是接口自动化项目工程化的重要能力。

---

# 12. pytest 是怎么让 CI 知道成功还是失败的？

假设执行：

```bash
pytest
```

结果：

```text
100 cases
100 passed
```

pytest 通常返回：

```text
Exit Code = 0
```

CI 认为：

```text
Success
```

如果：

```text
100 cases
98 passed
2 failed
```

pytest 返回非 0：

```text
Exit Code != 0
```

CI 通常认为：

```text
Failed
```

所以可以记：

```text
Exit Code = 0
→ 成功

Exit Code != 0
→ 失败
```

CI 平台不一定真正理解：

> “支付接口为什么失败？”

它只需要知道：

> pytest 这条命令最终执行成功还是失败。

---

# 13. Artifact 是什么？

接口自动化执行后会产生很多文件，例如：

```text
allure-results/
allure-report/
test_result.json
pytest.log
```

这些流水线执行过程中产生并需要保存的文件，可以叫：

**Artifact**

也就是：

> **流水线产物**

例如 CI 执行完成后，可以保存：

- Allure 测试报告
- pytest 日志
- JSON 测试结果
- 失败截图
- HTML 报告

以后排查 CI 失败时，就可以查看这些内容。

---

# 14. Quality Gate：质量门禁

Quality Gate 可以理解为：

> **如果测试不满足要求，就不允许代码继续进入后面的流程。**

例如：

```text
执行接口自动化
      ↓
100 条用例
      ↓
全部通过
      ↓
允许继续部署
```

如果：

```text
执行接口自动化
      ↓
有用例失败
      ↓
CI Failed
      ↓
停止流水线
      ↓
不允许部署
```

所以接口自动化不仅仅是：

> “帮我自动跑测试”

更重要的是可以成为：

> **研发流水线中的质量门禁。**

---

# 15. Pipeline 是什么？

Pipeline：

**流水线**

简单理解：

> 把原来需要人工执行的一系列步骤自动串起来。

比如：

```text
代码提交
   ↓
拉代码
   ↓
安装依赖
   ↓
执行测试
   ↓
生成报告
   ↓
判断结果
   ↓
部署
```

这一整条自动化流程就是：

> **Pipeline**

目前不需要急着记 Stage、Job、Step。

先理解：

```text
Pipeline
=
一整套自动执行流程
```

后面实际写 GitHub Actions / GitLab CI / Jenkins 时再学习如何拆任务。

> 提交代码后，自动跑接口回归，并自动判断成功还是失败。

---

```text
Merge Request

```

# 20. 面试时怎么回答 CI/CD？

如果面试官问：

> 你怎么理解 CI/CD？

可以回答：

> CI 是持续集成，核心是代码发生变更后，通过流水线自动完成构建、代码检查和自动化测试等验证工作，尽早发现代码变更引入的问题。
>
> CD 是持续交付或持续部署，在 CI 验证通过以后，将符合质量要求的代码交付或者自动部署到测试、预发布或生产环境。
>
> 在接口自动化项目中，我会把 pytest 接入 CI 流水线，当代码提交或合并时自动执行接口回归，生成测试报告，并根据测试结果设置质量门禁。测试失败时阻止后续部署，测试通过后再进入 CD 流程。

# 21. 当前学习结论

目前我对 CI/CD 的理解可以总结为：

```text
CI
=
提交代码后
自动帮我验证代码有没有问题

CD
=
CI 验证通过以后
自动帮我把代码交付 / 部署出去
```

对于接口自动化：

```text
接口自动化
          ↓
接入 CI
          ↓
从“手动执行 pytest”
变成
“提交代码后自动执行 pytest”
          ↓
进一步成为质量门禁
          ↓
决定代码是否允许进入 CD
```

```text

        ↓

        ↓
配置 CI
        ↓

        ↓
自动执行 pytest
        ↓

        ↓
```

实践过程中再逐步学习：

1. Pipeline
2. Job
3. Step
4. Stage
5. YAML 配置

7. Artifact
8. Quality Gate
9. CD 部署流程

原则：

> **先通过实际项目理解概念，再去记 CI/CD 的抽象名词。**
