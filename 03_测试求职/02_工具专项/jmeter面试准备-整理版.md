# JMeter 面试准备整理版

## 一句话定位

JMeter 我主要掌握接口级基础压测。比如登录接口和商品列表接口，我会先用 Apifox 确认接口能正常请求，再在 JMeter 里配置线程组、HTTP 请求默认值、请求头、状态码断言、业务断言和聚合报告，通过错误率、响应时间和吞吐量判断接口在小并发下是否稳定。

这份笔记的面试口径是：

- 会用 JMeter 做接口级基础压测。
- 会配置线程组、HTTP 请求、请求头、断言和聚合报告。
- 会看响应时间、错误率、吞吐量。
- 会通过查看结果树定位失败原因。
- 知道正式压测前要确认环境、数据隔离和监控指标。
- 不把自己包装成性能测试专家，重点讲功能测试、接口测试里的基础性能验证能力。

## JMeter 基础概念

### 线程组是什么？

思路：

- 线程组代表一组虚拟用户。
- 线程数可以理解为并发用户数。
- 在线程组里配置启动速度和执行次数。

回答：

> 线程组可以理解为一组虚拟用户，用来模拟多个用户同时向服务器发起请求。在线程组里可以设置线程数、Ramp-Up 时间和循环次数。线程数代表模拟多少个用户，Ramp-Up 代表这些用户在多长时间内启动完成，循环次数代表每个用户执行几轮。

### 线程数、Ramp-Up、循环次数是什么意思？

思路：

- 线程数：模拟用户数。
- Ramp-Up：启动这些用户的时间。
- 循环次数：每个用户执行几轮。

回答：

> 线程数可以理解为模拟多少个并发用户，Ramp-Up 是这些用户在多少秒内启动完成，循环次数是每个线程执行几轮。比如设置 10 个线程、Ramp-Up 10 秒、循环 3 次，总请求数大概是 30 次，而且不是一下子全部打上去，而是在 10 秒内逐步启动。

### HTTP 请求默认值有什么用？

思路：

- 抽取公共配置。
- 减少重复填写。
- 环境切换方便。

回答：

> HTTP 请求默认值主要用来维护公共配置，比如协议、服务器 IP、端口和统一路径前缀。这样单个接口只需要写自己的路径，比如登录写 `/login`，商品列表写 `/home/products`。如果环境地址变了，只需要改一处，维护起来更方便。

### HTTP 信息头管理器有什么用？

思路：

- 统一配置请求头。
- 常见请求头包括 Content-Type、Authorization。
- 避免每个接口重复配置。

回答：

> HTTP 信息头管理器用来统一配置请求头。比如 JSON 请求会配置 `Content-Type: application/json`。如果接口需要登录态，也可以在请求头里加 token，比如 `Authorization: Bearer ${token}`。这样不用每个接口重复配置请求头，后续维护也方便。

### 断言是什么？

思路：

- 用来验证响应是否符合预期。
- 常见是响应断言。
- 不只看 HTTP 200，还要看业务字段。

回答：

> 断言是用来验证响应数据是否符合预期的组件。JMeter 里比较常用的是响应断言，比如判断响应码是不是 200，或者响应体里是否包含 `token`、`success`、`list` 这类关键字段。这样可以避免请求 HTTP 成功，但业务实际失败的情况。

### 定时器有什么用？

思路：

- 控制请求节奏。
- 固定定时器用于请求间隔。
- 同步定时器用于集合并发。

回答：

> 定时器主要用来控制请求发送节奏。固定定时器可以让请求之间等待固定时间，更接近真实用户操作间隔。同步定时器可以让多个线程等到同一个点再一起发请求，用来模拟瞬时并发。

### Cookie 管理器有什么用？

思路：

- 维护用户会话。
- 模拟浏览器行为。
- 可以自动保存和发送 Cookie。

回答：

> Cookie 管理器主要用来维护用户会话，模拟浏览器处理 Cookie 的行为。比如登录后服务端返回 Cookie，后续请求需要带上这个 Cookie 才能保持登录态。使用 Cookie 管理器可以让脚本更接近真实用户访问场景。

### 前置处理器和后置处理器有什么区别？

思路：

- 前置处理器在请求前执行。
- 后置处理器在请求后执行。
- 一个准备数据，一个提取数据。

回答：

> 前置处理器是在请求发出前执行，常用于准备请求参数或动态构造数据。后置处理器是在请求完成后执行，常用于从响应里提取字段，比如用 JSON 提取器提取 token、商品 ID、订单号，再给后续接口使用。

### 变量和属性有什么区别？

思路：

- 变量通常是线程内或局部使用。
- 属性是全局共享。
- 多线程组共享数据时要注意作用域。

回答：

> JMeter 变量一般是局部作用域，常在线程或线程组内使用，不同线程之间通常互不影响。属性是全局作用域，所有线程组都可以访问。日常接口压测里，我更多使用变量，比如 `${token}`、`${product_id}`，如果要跨线程组共享数据，才会考虑属性。

## 接口压测基本流程

1. 先在 Apifox 里确认接口能调通，记录请求方式、路径、参数、请求头和返回字段。
2. 在 JMeter 里创建线程组，设置线程数、Ramp-Up 和循环次数。
3. 用 HTTP 请求默认值维护公共配置，比如协议、服务器 IP、端口和 `/api`。
4. 用 HTTP 信息头管理器维护公共请求头，比如 `Content-Type: application/json`。
5. 添加 HTTP 请求，先用 1 个线程、1 次循环确认能跑通。
6. 添加状态码断言和业务断言，避免只看 HTTP 200。
7. 小并发逐步加压，比如 5、10、20 线程。
8. 查看聚合报告，重点看平均响应时间、最大响应时间、错误率和吞吐量。
9. 如果失败，回到查看结果树看请求参数、响应体和断言失败原因。

## 高频面试题

### 1. 你用 JMeter 做过什么？

思路：

- 接口级基础压测。
- 登录和商品列表。
- 配置项。
- 看报告。

回答：

> 我用 JMeter 做过接口级基础压测，主要是登录接口和商品列表接口。流程是先在 Apifox 里确认接口能调通，然后在 JMeter 里配置线程组、HTTP 请求默认值、HTTP 信息头管理器、请求参数、状态码断言和业务断言，最后通过查看结果树定位失败原因，通过聚合报告看平均响应时间、最大响应时间、错误率和吞吐量。

### 2. JMeter 做接口压测的流程是什么？

思路：

- Apifox 先确认。
- JMeter 搭脚本。
- 单线程跑通。
- 加断言。
- 逐步加压。
- 看报告。

回答：

> 我一般先用 Apifox 确认接口请求方式、路径、参数和返回字段。然后在 JMeter 里创建线程组，配置 HTTP 请求默认值、请求头和 HTTP 请求。单接口先用 1 个线程跑通，再加状态码断言和业务断言，确认没有问题后再逐步增加线程数。最后看查看结果树和聚合报告，重点关注错误率、响应时间和吞吐量。

### 3. 你怎么做 JMeter 断言？

思路：

- 状态码断言。
- 业务断言。
- 不只看 200。

回答：

> 我不会只判断 HTTP 200，一般会加两类断言。第一类是状态码断言，比如响应码等于 200。第二类是业务断言，比如登录接口响应里必须包含 `token`，商品列表接口响应里必须包含 `success`、`list`、`store_name`。这样可以避免 HTTP 请求成功但业务实际失败的情况。

### 4. 查看结果树主要看什么？

思路：

- 请求参数。
- 响应码。
- 响应体。
- 断言失败原因。

回答：

> 查看结果树主要用于调试和定位问题。我会看请求路径、请求参数、请求头是否正确，再看响应码和响应体。如果请求是红色失败，我会重点看是状态码失败，还是业务断言失败。比如响应码是 200 但没有 token，就说明 HTTP 成功了，但登录业务没有真正成功。

### 5. 聚合报告怎么看？

思路：

- 样本数。
- 响应时间。
- 错误率。
- 吞吐量。

回答：

> 聚合报告我主要看四类指标：样本数、响应时间、错误率和吞吐量。响应时间会看平均值、最大值、90% 和 95% 分位；错误率看接口有没有失败；吞吐量看每秒能处理多少请求。比如登录接口跑 30 次请求，平均响应大概 220ms，错误率 0%，就可以说明小并发下接口比较稳定。

### 6. 如果聚合报告里错误率很高，你怎么排查？

思路：

- 先看失败请求。
- 区分 HTTP 失败和业务断言失败。
- 检查参数、请求头、账号和并发。

回答：

> 我会先到查看结果树里找到失败请求，看响应码、响应体和断言结果。如果响应码不是 200，比如 500、502、403，可能是服务端异常、权限问题或网关问题。如果响应码是 200，但业务断言失败，比如没有返回 token，那就是业务失败或断言字段不稳定。然后我会检查参数、请求头、账号数据，再降低并发重新验证。

### 7. 为什么不能一上来就把并发压很高？

思路：

- 先验证脚本。
- 保护测试环境。
- 避免数据污染。
- 逐步加压。

回答：

> 我不会一开始就猛压，尤其是自己的练习服务器或测试环境。因为脚本、参数、断言还没确认时，直接加大并发可能把服务打挂，也可能产生脏数据。我的做法是先 1 个线程跑通，再用 5、10、20 这种方式逐步加压，同时观察错误率和响应时间变化。正式压测前还要确认压测环境、测试数据和监控指标。

### 8. JMeter 怎么录制脚本？

思路：

- 添加 HTTP(S) 测试脚本记录器。
- 配置浏览器代理。
- 导入证书。
- 开始录制并整理脚本。

回答：

> JMeter 可以通过 HTTP(S) 测试脚本记录器录制请求。大致流程是先在线程组或测试计划下添加记录器，设置代理端口；然后在浏览器里配置同样的代理地址和端口；如果是 HTTPS 请求，需要导入 JMeter 生成的证书，避免安全警告；最后开始录制操作流程，录完后再整理请求、参数、断言和无关资源。

### 9. 性能测试、压力测试、稳定性测试有什么区别？

思路：

- 性能测试看指标是否达标。
- 压力测试看系统承压上限。
- 稳定性测试看长时间运行是否稳定。

回答：

> 性能测试主要关注系统在指定并发和业务量下，响应时间、吞吐量、错误率是否达到预期。压力测试更关注不断增加压力后系统的极限和瓶颈。稳定性测试一般是较长时间运行，观察系统是否出现内存泄漏、响应变慢、错误率升高等问题。

## 加分追问题

### 10. 单接口压测和链路压测有什么区别？

思路：

- 单接口看某个接口。
- 链路压测模拟真实业务流程。
- 链路需要参数传递。

回答：

> 单接口压测是单独压一个接口，比如登录接口或商品列表接口，适合先验证接口本身是否稳定。链路压测是按照真实业务流程串起来，比如登录、商品列表、商品详情、确认订单、提交订单。链路压测里上一个接口返回的数据要传给下一个接口，比如 token、商品 ID、订单 key，一般用 JSON 提取器提取变量，再在后续请求中引用。

### 11. JMeter 里怎么做接口关联？

思路：

- 上个接口提取。
- 下个接口引用。
- token、商品 ID、订单号。

回答：

> 接口关联就是上一个接口返回的数据要给后面的接口用。比如登录接口返回 token，后续个人中心或下单接口要带 token；商品列表返回商品 ID，商品详情接口要用商品 ID。JMeter 里可以用 JSON 提取器把字段提取成变量，比如 `${token}`、`${product_id}`，再在后续请求里引用。

### 12. CSV Data Set Config 是做什么的？

思路：

- 参数化。
- 多组测试数据。
- 登录账号、商品 ID。

回答：

> CSV Data Set Config 主要用于参数化。比如登录接口如果要用多组账号压测，可以把账号和密码放到 CSV 文件里，然后在请求体里用 `${account}`、`${password}` 引用。这样不用在 JMeter 里写死一组数据，也更接近多个用户请求的场景。

### 13. 如果面试官问性能瓶颈怎么定位，你怎么答？

思路：

- 测试岗口径。
- 先从报告看现象。
- 再结合日志、数据库和监控。

回答：

> 我目前主要掌握接口级基础压测。遇到响应慢或错误率高，我会先从 JMeter 报告判断是整体变慢还是部分请求失败，再看查看结果树里的失败响应。如果是公司正式环境，我会结合服务日志、数据库慢 SQL、CPU、内存、网络和接口错误日志一起排查。作为测试，我会先把现象、并发配置、错误率、响应时间和复现步骤整理清楚，再推动开发一起定位。

## 性能测试流程与指标

### 性能测试一般怎么规划？

思路：

- 先确认目标和指标。
- 再准备环境、脚本、数据、监控。
- 最后执行并分析结果。

回答：

> 性能测试前我会先确认测试目标和指标，比如响应时间、吞吐量、并发用户数和错误率。然后确认测试环境是否独立、测试数据是否准备好，再开发 JMeter 脚本，配置参数化、断言和监听器。正式执行时会逐步加压，同时关注应用日志、数据库、CPU、内存、网络等监控。执行后根据报告分析响应时间、吞吐量、错误率和失败原因。

常见流程：

1. 确定性能测试目标和指标，比如响应时间、吞吐量、并发用户数、错误率。
2. 选择和确认测试环境，尽量避免影响生产环境。
3. 准备测试数据，比如账号、商品、订单相关数据。
4. 开发和调试 JMeter 脚本。
5. 配置断言、参数化、关联和监听器。
6. 设置服务端监控，比如 CPU、内存、数据库、接口日志。
7. 从小并发开始逐步执行。
8. 分析结果，输出问题现象、复现条件和优化建议。

### 常见指标怎么看？

思路：

- 响应时间看用户等待多久。
- 吞吐量看单位时间处理能力。
- 并发用户数看同时模拟多少用户。
- 错误率看失败占比。

回答：

> 我主要看响应时间、吞吐量、并发用户数和错误率。响应时间代表接口从请求到返回用了多久；吞吐量代表单位时间内系统处理了多少请求；并发用户数代表同一时间模拟多少用户访问；错误率代表失败请求占比。面试里我会重点结合聚合报告说明平均响应时间、最大响应时间、90% 和 95% 分位、吞吐量和错误率。

### 怎么让压测更接近真实场景？

思路：

- 使用真实业务链路。
- 参数化测试数据。
- 控制请求节奏。
- 不只压单个接口。

回答：

> 要更接近真实场景，不能只机械地重复请求一个接口。可以按真实业务流程设计链路，比如登录、浏览商品、查看详情、下单；使用 CSV 参数化模拟不同用户和不同数据；通过定时器控制用户操作间隔；并且根据实际业务比例分配接口请求量。这样压测结果会比单纯循环请求更有参考价值。

你的岗位定位是：
