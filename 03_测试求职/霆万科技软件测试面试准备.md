# 霆万科技软件测试面试准备

这份笔记按技术面试官的真实提问顺序整理：先看你的表达和项目背景，再问测试基础、Web 基础、业务场景、接口定位、性能兼容、Linux / SQL、Bug 管理，最后问自动化和个人匹配度。

准备时记住你的定位：

> 功能测试基础扎实，熟悉 Web 测试、接口测试、抓包定位、兼容性测试和基础性能测试，能快速上手独立站 / 官网 / 后台系统测试；接口自动化作为加分项讲，不包装成高级自动化测试。

回答格式建议：

思路：

> 按测试闭环答：需求分析、测试点、用例、评审、执行、缺陷、回归、总结。

答案：

> 我会先阅读需求文档和原型，理解业务背景、用户角色、核心流程和边界规则。然后从正常流程、异常流程、输入校验、权限、状态流转、数据一致性、兼容性等角度拆测试点。
>
> 接着编写测试用例，并和产品、开发进行用例评审，确认是否有遗漏或理解偏差。执行阶段按优先级先测主流程和高风险场景，发现问题后提交 Bug，写清楚复现步骤、实际结果、预期结果、截图或抓包信息。开发修复后再做回归验证，最后根据执行情况输出测试结论。

### 2. Web 测试流程一般是什么？

答案：

## 3. Web / B-S / HTTP 基础

### 1. 什么是 B/S 架构？和 C/S 架构有什么区别？

思路：

> 从部署、升级、测试角度回答。

答案：

> B/S 是 Browser / Server，用户通过浏览器访问系统，系统主要部署在服务器端。C/S 是 Client / Server，需要安装客户端程序。
>
> 从部署看，B/S 主要部署服务器，用户有浏览器就能访问；C/S 要安装客户端。从升级看，B/S 更新服务器后用户刷新页面即可，C/S 往往要升级客户端。从测试看，B/S 要重点测页面交互、浏览器兼容性、接口、前后端数据交互和网络异常。

### 2. 用户在浏览器点击“提交订单”后，系统内部大概发生了什么？

思路：

> 按前端校验、HTTP 请求、后端校验、订单生成、支付回调、数据库、页面展示来答。

答案：

> 用户点击提交订单后，前端会先做基础校验，比如地址、商品数量、库存状态、优惠券、支付方式是否完整。校验通过后，浏览器会通过 HTTP 请求把订单参数发送给后端。
>
> 后端收到请求后，会校验用户登录态、商品库存、商品价格、优惠券、运费、税费、汇率等业务规则。校验通过后生成订单并写入数据库。如果涉及支付，会调用第三方支付接口。支付成功后，第三方支付会回调系统，系统再更新订单支付状态、库存状态，并把结果返回给前端展示。
>
> 如果是跨境电商，我会特别关注币种、汇率、税费、物流方式、支付回调和订单状态流转是否正确。

### 3. 简述 Web 工作原理，以及 HTTP 请求和响应的大致流程。

思路：

> 讲浏览器、DNS / 连接、请求、服务端处理、响应、浏览器渲染。

答案：

> 用户在浏览器输入 URL 后，浏览器会解析地址并和服务器建立连接，然后发送 HTTP 请求。请求里一般包含请求方法、URL、请求头和请求体。
>
> 服务器收到请求后处理业务逻辑，比如查询数据库或调用接口，然后返回 HTTP 响应，响应里包含状态码、响应头和响应体，响应体可能是 HTML、JSON、图片等。浏览器拿到响应后进行解析和渲染，最终展示页面给用户。

### 4. GET 和 POST 有什么区别？

思路：

> 讲用途、参数位置、幂等和敏感数据。

答案：

> GET 一般用于查询数据，参数通常放在 URL 后面，比如商品列表、订单查询。POST 一般用于提交或新增数据，参数通常放在请求体里，比如登录、提交订单、提交表单。
>
> 测试时我会关注请求方式是否符合接口文档，参数位置是否正确，敏感数据是否不应该放在 URL 中。

### 5. 常见 HTTP 状态码有哪些？

思路：

> 说测试常见的几个，不用背太偏。

答案：

> 200 表示请求成功；301 / 302 是重定向；400 通常是请求参数错误；401 是未登录或认证失败；403 是无权限；404 是资源不存在；500 是服务器内部错误。
>
> 测试时遇到接口或页面异常，我会先看状态码，再结合响应内容和请求参数判断问题方向。

## 4. Web 页面与表单测试

### 1. H5 页面怎么测试？

思路：

> 按移动端特点答：功能、适配、兼容、交互、弱网、键盘遮挡。

答案：

> H5 页面我会从功能、适配、兼容性、交互、性能和异常场景几个方面测试。
>
> 功能上看按钮、链接、表单、支付、提交等流程是否正常；适配上看不同屏幕尺寸下页面是否错位、图片是否变形、文字是否重叠；兼容性上关注 Android、iOS、微信内置浏览器、手机浏览器等环境。
>
> 交互上看返回、刷新、滑动、弹窗、输入框键盘弹起是否正常。异常场景会测弱网、断网、接口超时、重复点击、页面加载失败等情况。如果是表单页面，我会特别关注键盘弹出后是否遮挡输入框或提交按钮。

### 2. 怎么做 Web 表单测试？

思路：

> 按字段、流程、接口、数据、安全来答。

答案：

> Web 表单测试我会从字段校验、提交流程、接口请求、数据保存和异常安全几个方面测试。
>
> 字段上会测必填、非必填、默认值、空值、超长字符、特殊字符、中文英文、邮箱、手机号、日期等格式。流程上会测正常提交、取消、返回、重复提交、刷新后提交。接口上会抓包看请求参数是否正确，响应结果是否符合预期。
>
> 数据上要确认后台是否能收到，数据库是否正确保存。异常方面会测网络中断、接口失败、提交超时、无权限提交。安全方面会简单关注 SQL 注入字符和 XSS 脚本输入。

### 3. 官网 Contact Us 表单你会怎么测试？

思路：

> 联系霆万业务：表单是线索入口，要测前台提交、接口、后台线索、邮件通知。

答案：

> 我会先看表单有哪些字段，比如姓名、邮箱、公司、国家、产品类型、留言内容。正常场景会验证填写完整信息后能提交成功，后台或邮件能收到线索。
>
> 异常场景会测必填为空、邮箱格式错误、手机号或国家区号异常、超长字符、特殊字符、重复提交、网络异常等。还会抓包看请求参数是否正确，接口返回是否符合预期，页面提示是否友好。

### 4. 表单提交成功但后台没有收到线索，你怎么排查？

思路：

> 按前台提示、接口请求、接口响应、后端入库、后台筛选、邮件通知来排查。

答案：

> 我会先确认前台是否真的提交成功，再用抓包工具看接口请求和响应。如果接口没有发出去，可能是前端事件或校验问题；如果接口返回失败，就根据错误码定位后端或参数问题。
>
> 如果接口返回成功但后台没有数据，就需要看后端是否入库失败、后台筛选条件是否不对、数据是否进入了其他状态，必要时结合日志或数据库继续确认。

### 5. 如何防止表单重复提交？你会怎么测？

思路：

> 讲前端按钮置灰、loading、后端幂等，再讲重复点击测试。

答案：

> 我会测试用户连续点击提交按钮、网络慢时重复点击、刷新页面后重复提交、浏览器返回后再次提交等场景。
>
> 预期上可以通过按钮置灰、loading 状态、后端幂等校验或验证码限制来避免重复提交。测试时我会看前端是否重复发请求，后台是否生成重复线索，接口是否能识别重复提交。

## 5. 霆万业务场景：独立站 / 官网 / SEO

### 1. 如果让你测试一个海外软件品牌独立站，你会从哪些方面设计测试用例？

思路：

> 按独立站核心：页面功能、表单转化、兼容性、SEO、性能、上线检查。

答案：

> 我会从功能、兼容性、接口、内容、SEO、性能和上线检查几个方面设计。功能上关注首页、产品页、价格页、博客页、联系我们页、按钮跳转、表单提交是否正常；兼容性上关注 Chrome、Edge、Safari 以及 PC 和移动端展示；接口上关注表单提交、内容加载、状态码和返回数据。
>
> 内容上关注英文文案、图片、链接、产品信息是否正确；SEO 上关注标题、描述、URL、图片 alt、404 和死链；性能上关注页面加载速度、图片资源和接口响应。上线前还会做一轮核心链路冒烟测试。

### 2. 官网首页、产品页、价格页、博客页、联系我们页，测试重点分别是什么？

思路：

> 每个页面按它的业务目的讲：展示、转化、内容、线索。

答案：

> 首页重点看导航、Banner、核心按钮、产品入口和页面加载；产品页重点看产品介绍、功能模块、下载或购买入口、图片和视频展示；价格页重点看套餐价格、功能对比、购买按钮和币种展示。
>
> 博客页重点看文章列表、详情页、分类、搜索、上一篇下一篇和分享链接；联系我们页重点看表单字段、必填校验、邮箱格式、提交成功提示和后台是否能收到线索。

### 3. WordPress 后台发布一篇文章，前台没有显示，你怎么排查？

思路：

> 按文章状态、发布时间、分类、缓存、固定链接、模板查询来排查。

答案：

> 我会先确认文章状态是不是已发布，而不是草稿或待审核；再看发布时间是否设置到未来，分类或标签是否正确，前台列表有没有筛选条件。
>
> 然后检查缓存或静态页面是否未刷新。如果文章详情页能打开但列表不显示，可能是列表查询、分类配置或模板问题；如果详情页也打不开，就要看固定链接、路由或权限配置。

### 4. SEO 页面测试要关注哪些内容？

思路：

> 明确自己不是 SEO 专家，只做测试基础检查。

答案：

> 我不是 SEO 专家，但从测试角度会做基础检查，比如页面 title、description、H1 是否正确，URL 是否规范，图片 alt 是否配置，页面是否能正常访问，是否存在 404 或死链，移动端是否适配，页面加载速度是否明显过慢，站点地图和 robots 配置是否符合要求。

### 5. 广告投放落地页测试重点是什么？

### 6. 独立站上线前，你会准备哪些上线检查项？

## 6. CBEC 业务场景：跨境电商 Web 测试

### 1. 跨境电商系统与普通电商相比，测试重点有哪些不同？

思路：

> 对比普通电商，多讲跨境特有：多币种、汇率、税费、时区、支付、物流、清关、多语言。

答案：

> 跨境电商除了普通电商的商品、购物车、下单、支付、订单、退款，还要额外关注多币种、汇率、税费、时区、跨境支付、国际物流、清关状态和多语言。
>
> 比如不同国家显示的币种和支付方式可能不同，税费和运费规则不同，订单时间要考虑时区，物流会有国内段、国际段和清关状态。测试时要重点验证这些规则在商品页、下单页、支付页、订单页和后台是否一致。

### 2. 跨境电商商品详情页，你会怎么设计测试点？

思路：

> 按展示、规格、价格、库存、购买、跨境规则来答。

答案：

> 商品详情页我会先看商品标题、图片、视频、价格、币种、库存、规格 SKU、商品描述、运费、税费、物流说明是否展示正确。
>
> 功能上会测规格切换、数量加减、加入购物车、立即购买、收藏、分享、评价展示等。接口上会看商品详情接口返回的数据和页面展示是否一致，比如价格、库存、SKU、促销信息。
>
> 跨境场景下，我会重点关注不同国家是否显示不同币种、物流方式、税费规则和支付方式；多语言切换后商品文案是否完整，英文长文本是否排版正常。

### 3. 跨境电商下单页涉及多币种和汇率，你会重点测什么？

思路：

> 按金额链路答：商品页、购物车、下单页、支付页、订单页、退款页。

答案：

> 我会重点关注币种显示、汇率换算、金额精度、优惠券、运费、税费和最终实付金额。
>
> 首先看商品列表、商品详情、购物车、下单页、支付页的币种和金额是否一致。然后看汇率换算精度是否符合规则，比如是否保留两位小数，是否存在多次换算导致误差。
>
> 其次要看汇率变更后，是否影响已经生成的历史订单。正常情况下，历史订单金额不应该因为后续汇率变化而变化。支付成功后，还要确认前台订单金额、后台订单金额、支付平台金额是否一致。如果发生退款，要确认退款金额按业务规则处理，不能因为实时汇率变化导致金额异常。

### 4. 多币种、多语言场景下，你会重点关注哪些测试点？

思路：

> 语言看文案和布局，币种看金额和历史订单。

答案：

> 多语言方面，我会检查首页、商品页、购物车、下单页、支付页、订单页的文案是否切换完整，是否有中英文混用、乱码、文字截断、按钮溢出等问题。
>
> 多币种方面，我会检查商品价格、购物车金额、运费、税费、优惠金额、订单总价是否同步切换，币种符号和位置是否符合当地习惯。还要重点验证语言和币种切换是否影响下单流程，比如切换后商品金额是否正确、订单生成后币种是否固定、历史订单是否不受当前币种切换影响。

### 5. 跨境电商下单流程中，哪些环节最容易出问题？为什么？

思路：

> 重点讲汇率、支付、退款、物流，因为链路长、第三方多、规则复杂。

答案：

> 我觉得最容易出问题的是汇率计算、支付到账、退款和物流。
>
> 汇率计算容易出问题，是因为不同国家币种不同，汇率可能实时变化，还涉及精度和四舍五入。支付容易出问题，是因为跨境支付链路长，有第三方参与，可能出现支付成功但回调失败。退款也复杂，因为要考虑原币种、退款金额、部分退款和汇率规则。物流方面则涉及国内段、国际段、清关状态和异常状态展示，状态同步容易不一致。

### 6. 跨境电商订单列表页，你会怎么测？

思路：

> 按订单展示、筛选、状态、金额、物流、跨境特性来答。

答案：

> 订单列表页我会先测试订单是否能正常展示，包括订单号、商品信息、订单金额、币种、支付状态、发货状态、物流状态、下单时间等。
>
> 功能上会测订单筛选、搜索、分页、排序、订单详情跳转、取消订单、申请退款等入口。接口上会抓包确认列表接口返回的数据和页面展示一致。
>
> 跨境场景下，我会重点关注时区显示是否正确，不同国家的物流状态、清关状态是否展示正确，订单金额和币种是否和下单页、支付页一致。

### 7. 跨境电商支付成功，但订单状态还是未支付，你怎么排查？

思路：

> 围绕支付回调和订单状态流转答。

答案：

> 我会先确认用户支付平台是否真的扣款成功，然后看系统订单状态是否更新。
>
> 接口层面会检查支付发起接口和支付回调接口，确认回调是否到达系统，回调参数是否正确，签名校验是否通过。如果支付平台成功但系统没收到回调，可能是回调地址、网络或第三方通知问题；如果收到回调但订单没更新，可能是后端状态流转、订单号匹配、幂等处理或数据库更新失败。
>
> 跨境支付链路比较长，所以我会重点记录订单号、支付流水号、支付时间、回调日志和订单状态变化，方便开发定位。

## 7. 接口测试与抓包定位

### 1. 接口测试一般关注哪些内容？

思路：

> 从接口文档、请求、响应、业务、权限、数据一致性讲。

答案：

> 接口测试我会先看接口文档，确认请求方式、URL、请求头、参数位置、返回字段和业务规则。
>
> 测试点包括正常参数、必填参数缺失、参数类型错误、边界值、权限鉴权、业务状态校验、重复提交、异常返回、响应时间、返回字段是否符合文档。对于核心业务，还会结合数据库或后台页面验证数据是否正确。

### 2. 页面提交表单失败，你怎么通过 Fiddler 或 Charles 判断问题在哪？

思路：

> 先看有没有请求，再看请求参数，再看响应状态码和响应体。

答案：

> 我会先看点击提交后有没有发请求。如果没有请求，可能是前端校验或按钮事件问题；如果有请求，就看 URL、请求方式、请求头、请求体是否正确。
>
> 再看响应状态码和响应内容，如果是 400 可能是参数问题，401 或 403 可能是权限问题，500 可能是服务端异常。如果接口返回成功但页面提示失败，就要继续看前端对响应字段的判断逻辑。

### 3. 接口返回 200，但页面没有展示数据，你怎么分析？

思路：

> 区分 HTTP 200 和业务成功，再看响应体、前端渲染、字段映射、缓存。

答案：

> 我会先看接口响应体里是否真的有业务数据。如果响应体没有数据，说明问题可能在后端逻辑、查询条件或数据源。
>
> 如果响应体有数据但页面不展示，就重点看前端字段映射、渲染逻辑、缓存或权限控制。还会对比页面请求参数和接口文档，确认前端传的查询条件是否正确。

### 4. 页面显示金额和接口返回金额不一致，你怎么定位？

思路：

> 按接口返回、前端展示、后端计算、数据库数据四步定位。

答案：

> 我会先用浏览器 Network 或 Fiddler 抓包，看接口返回的金额是多少，再看页面展示的金额是否和接口一致。
>
> 如果接口返回正确，但页面展示错误，可能是前端格式化、币种符号、汇率换算、字段映射或小数精度处理有问题。如果接口返回本身就不对，就要继续看后端金额计算逻辑，比如商品价格、优惠券、运费、税费、汇率是否计算正确。
>
> 对于订单金额这种核心数据，我还会结合后台订单数据或数据库查询，确认前台、接口、后台、数据库是否一致。

### 5. Web 测试中，如何判断是前端 Bug 还是后端 Bug？

思路：

> 按请求参数、接口响应、页面展示、数据库 / 后台数据判断。

答案：

> 我会先通过浏览器 Network 或 Fiddler 抓包，看前端实际发出的请求参数是否正确。
>
> 如果前端传给后端的参数就不对，比如字段缺失、金额传错、格式错误，那更偏前端问题。如果请求参数正确，但接口返回的数据、业务码或数据库数据不对，那更偏后端或数据问题。
>
> 如果接口返回正确，但是页面展示错误，比如金额格式化错、订单状态显示错、按钮状态不对，那一般是前端渲染或字段映射问题。对于订单、支付、库存这类核心业务，我还会结合后台或数据库一起确认。

### 6. 一个页面偶发加载不到内容，你会怎么结合抓包、日志和接口响应分析？

思路：

> 收集偶发条件，抓包看接口，再结合日志时间点定位。

答案：

> 我会先收集偶发条件，比如时间、网络、浏览器、账号、页面 URL。复现时抓包看内容接口是否请求成功，状态码和响应时间是否异常。
>
> 如果接口超时或 500，就让开发结合服务日志看异常；如果接口返回空数据，就看请求参数和数据源；如果接口正常但页面没渲染，就可能是前端异步处理、缓存或脚本报错。偶发问题要尽量保留时间点、请求信息和日志线索。

## 8. 兼容性与性能

### 1. 你怎么做 Web 兼容性测试？

思路：

> 覆盖浏览器、设备、分辨率、核心功能、页面展示。

答案：

> 我会优先覆盖用户常用浏览器，比如 Chrome、Edge、Safari，如果面向海外用户，也要特别关注 Safari 和移动端浏览器。设备上会覆盖 PC 常见分辨率、iPhone 尺寸、Android 主流尺寸。
>
> 测试重点是页面布局、按钮点击、表单输入、弹窗、导航菜单、图片视频展示和接口请求是否正常。对于响应式页面，还要调整不同宽度，观察是否出现元素重叠、按钮不可点、文字溢出或内容被遮挡。

### 2. Safari 上样式异常，但 Chrome 正常，你怎么提交这个 Bug？

思路：

> 说明环境、页面、复现步骤、对比图，定位为兼容性问题。

答案：

> 我会写清楚问题只在 Safari 出现，附上 Safari 版本、系统版本、页面 URL、复现步骤、异常截图和 Chrome 正常对比图。
>
> 实际结果描述具体异常，比如按钮错位、文字溢出、图片拉伸；预期结果说明应该和 Chrome 或设计稿保持一致。这样前端能更快判断是不是 CSS 兼容性问题。

### 3. 海外用户反馈访问网站慢，你作为测试会怎么协助定位？

思路：

> 收集地区、设备、网络，记录加载耗时和慢资源，不直接下结论。

答案：

> 我会先收集用户所在国家、网络、设备、浏览器和具体慢的页面。然后自己在不同网络或工具下复现，记录页面加载时间、接口响应时间和慢资源。
>
> 重点看图片视频是否过大、第三方脚本是否慢、CDN 是否生效、接口是否超时。作为测试，我不会直接下结论，而是把复现环境、耗时数据、Network 记录和慢资源整理出来，协助开发或运维定位。

### 4. 图片很多的营销页面，你会怎么测试加载性能？

思路：

> 看首屏、图片大小、懒加载、弱网、移动端。

答案：

> 我会关注首屏加载时间、图片大小、是否懒加载、移动端流量消耗、弱网下展示效果，以及图片加载失败时页面是否有明显错位。
>
> 测试时可以用浏览器 Network 看图片资源大小和加载耗时，也可以在移动端或弱网环境下观察页面是否长时间空白。如果图片过大导致页面慢，会记录具体图片 URL、大小和影响页面。

### 5. 如何使用 JMeter 对下单接口做性能测试？

思路：

> 讲准备数据、线程组、请求、参数化、断言、聚合报告、业务风险。

答案：

> 我会先准备测试环境和测试数据，比如测试账号、token、商品 ID、地址 ID、库存数据。然后在 JMeter 里配置线程组，设置线程数、Ramp-Up 和循环次数，再配置 HTTP 请求、请求头、请求参数。
>
> 如果下单接口依赖登录和商品数据，会用变量或前置接口处理参数传递。执行时会加状态码断言和业务断言，比如订单号是否返回。结果主要看响应时间、TPS、吞吐量、错误率。
>
> 对下单接口还要关注是否出现重复下单、库存超卖、订单状态异常、支付状态异常等业务问题。

### 6. JMeter 线程数、Ramp-Up、循环次数是什么意思？

思路：

> 用简单例子讲清楚。

答案：

> 线程数可以理解为模拟多少个并发用户；Ramp-Up 是这些用户在多长时间内逐步启动，避免瞬间全部压上去；循环次数是每个线程执行请求的次数。
>
> 比如线程数 10、Ramp-Up 5 秒、循环次数 3，就表示 10 个用户在 5 秒内逐步启动，每个用户执行 3 次请求。

## 9. Linux / SQL / 日志定位

### 1. 线上用户反馈下单失败，你登录 Linux 服务器，如何快速定位问题？

思路：

> 按用户信息、时间点、日志、接口、订单号、错误关键字来定位。

答案：

> 我会先收集用户账号、下单时间、商品、订单号或截图。然后在服务器上查看对应时间段的应用日志，比如用 `tail -n 50 app.log` 查看最近日志，用 `grep -n "ERROR" app.log` 过滤错误。
>
> 如果知道订单号或用户 ID，可以用关键字过滤相关日志。重点看接口是否报错、参数是否异常、支付或库存服务是否异常。必要时再结合数据库确认订单是否生成、库存是否扣减、支付状态是否更新。

### 2. 常用 Linux 日志命令有哪些？

思路：

> 说最实用的几个，不背偏命令。

答案：

```shell
tail -n 50 app.log
tail -f app.log
grep -n "ERROR" app.log
ps -ef | grep java
netstat -ano | findstr 8080
df -h
```

> 我主要用这些命令看日志末尾、实时日志、过滤错误、查看进程、查看端口和磁盘空间。面试里我会结合具体问题说，比如线上下单失败，就按时间点和订单号去过滤日志。

### 3. MySQL 在 Web 测试中通常用来做什么？

思路：

> 讲数据校验、造数、清理、问题定位。

答案：

> MySQL 在 Web 测试中主要用于数据校验、准备测试数据、清理脏数据和辅助问题定位。
>
> 比如下单后，我可以查订单表确认订单是否落库，订单状态和金额是否正确；支付后查支付状态是否更新；退款后查退款记录是否生成。遇到页面和接口数据不一致时，也可以通过数据库判断底层数据是否正确。

### 4. 查询订单金额大于 1000 美元，且状态为已支付的订单号和用户 ID。

select
    id,
    user_id
from orders
where amount > 1000
  and currency = 'USD'
  and status = 'PAID';

### 5. 如果支付成功但订单状态没更新，你会查哪些数据？

思路：

> 查订单、支付流水、回调日志、状态流转。

答案：

> 我会先查订单表，看订单当前状态、订单金额、支付方式和更新时间。然后查支付流水表，看是否有支付成功记录、第三方流水号和回调时间。
>
> 如果支付流水成功但订单没更新，就要看支付回调日志、订单号匹配、状态流转逻辑和数据库更新是否失败。这个问题不能只看页面，要把支付平台、接口响应、回调日志和数据库数据结合起来看。

## 10. Bug 管理与沟通

### 1. 一个完整的 Bug 单应该包含什么？

思路：

> 讲开发能复现和定位所需的信息。

答案：

> 一个完整的 Bug 单应该包含标题、所属模块、测试环境、前置条件、复现步骤、实际结果、预期结果、严重程度、优先级、截图或录屏、接口请求响应或日志信息。
>
> 如果是接口或数据问题，还可以补充请求参数、响应内容、账号信息和相关数据记录，方便开发快速定位。

### 2. 严重程度和优先级有什么区别？

思路：

> 严重程度看影响，优先级看修复顺序。

答案：

> 严重程度主要看 Bug 对系统功能和用户的影响，比如系统崩溃、主流程阻塞、金额错误就比较严重。优先级主要看修复的紧急程度，比如某个问题虽然不严重，但马上要上线或影响客户演示，也可能优先级较高。

### 3. 如果开发说这不是 Bug，你怎么处理？

思路：

> 不争论，回到需求、原型、产品确认。

答案：

> 我不会直接争论，会先回到需求文档、原型图或产品规则确认预期。如果需求里有明确说明，我会把依据发给开发；如果需求不清楚，我会拉产品一起确认。
>
> 确认是 Bug 就继续跟进修复，如果确认是需求设计如此，我会关闭或转成需求建议。重点是基于依据沟通，而不是主观判断。

### 4. Bug 修复后，你怎么做回归验证？

思路：

> 先验证原问题，再验证关联影响。

答案：

> 我会先按照 Bug 单里的复现步骤验证原问题是否修复，然后再验证相关功能有没有受到影响。
>
> 比如下单金额问题修复后，我不仅会测原来的优惠券场景，还会回归商品金额、运费、税费、支付金额、订单详情和退款金额，避免修复一个问题引入新的问题。

### 5. 你用过禅道、TAPD、Jira 吗？缺陷流转流程是什么？

思路：

> 工具可以说熟悉流程，重点讲状态流转。

答案：

> 我了解这类 Bug 管理工具的基本流程。一般是测试提交缺陷，填写模块、环境、复现步骤、实际结果、预期结果和附件，然后指派给开发。
>
> 开发确认后修复并流转给测试，测试回归通过后关闭；如果没修好或又复现，就重新打开。过程中会根据严重程度和优先级推动处理，保证问题闭环。

## 11. 自动化加分项

### 1. 你有自动化测试或测试脚本编写经验吗？

思路：

> 明确是加分项，不把自己说成高级自动化。

答案：

> 我这块不是把自己定位成专门的自动化测试工程师，而是作为接口测试能力的补充。我自己基于 Pytest + Requests + YAML 搭过一个接口自动化练习框架，主要覆盖登录、商品、购物车、下单这类主流程。
>
> 框架里做了 YAML 数据驱动、统一请求封装、断言封装、响应字段提取和上下文参数传递。比如登录后提取 token，商品接口提取商品 ID，后续加入购物车和下单接口直接引用这些变量。

### 2. 你这个接口自动化框架是怎么设计的？

思路：

> 讲目标、技术栈、分层、执行流程。

答案：

> 这个框架目标是把稳定接口用例沉淀下来，减少重复手工调接口，提高回归效率。技术栈是 Pytest + Requests + YAML。
>
> 分层上，YAML 放接口用例数据，Pytest 负责组织和执行测试，Requests 负责发送 HTTP 请求，请求封装层统一处理 method、url、headers、params、json，断言层处理状态码和业务字段，提取层负责从响应中提取 token、商品 ID、订单号，上下文负责接口之间传参。

### 3. 一条接口自动化用例是怎么执行的？

思路：

> 读 YAML、替换变量、发请求、断言、提取。

答案：

> 一条用例执行时，先读取 YAML 里的接口信息，比如请求方式、路径、请求头、参数、断言和提取规则。发送请求前会替换上下文变量，比如 token、商品 ID。
>
> 然后通过统一请求封装发送 HTTP 请求，拿到响应后执行状态码和业务字段断言。最后根据提取规则把后续接口需要的字段保存到上下文里，给下一条接口继续使用。

### 4. 多接口依赖，比如 token、商品 ID、订单号，你怎么处理？

思路：

> 上游提取，下游引用。

答案：

> 我会用上下文变量处理接口依赖。比如登录接口返回 token 后，把 token 提取到上下文；商品接口返回商品 ID 后，也提取到上下文。后面的购物车、确认订单、创建订单接口，就可以通过占位符引用这些值。
>
> 这样不需要手动复制参数，也能让接口形成一条完整业务链路。

### 5. 自动化断言你会怎么设计？

思路：

> 不只断言 200，分三层。

答案：

> 我一般分三层断言。第一层是 HTTP 状态码，比如是不是 200；第二层是业务码和返回结构，比如 code、message、data 是否符合预期；第三层是关键业务字段，比如登录是否返回 token、下单是否返回订单号。
>
> 这样可以避免 HTTP 请求成功但业务实际失败的情况。

### 6. 这个框架目前还有哪些不足？

思路：

> 主动说不足，显得真实。

答案：

> 目前这个框架主要是练习和主流程回归，还不算完整平台。后续还可以增强数据库断言、测试数据自动清理、失败重试、日志报告展示、多环境配置和 CI 集成。
>
> 所以我面试里不会把它说成很成熟的平台，而是作为我理解接口自动化核心流程的实践项目。
