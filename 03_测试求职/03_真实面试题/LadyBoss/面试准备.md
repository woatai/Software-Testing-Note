# LadyBoss 测试开发工程师（QA）面试准备

## 这份笔记怎么用

这份材料参考“伊智 AI 赋能测试工程师面试准备”的组织方式，但内容完全按照 LadyBoss 的女性成长教育业务、微信生态、CRM、数据回收和接口自动化 JD 重新设计。

这次面试的基础盘不是 AI，也不是只展示自动化框架，而是让面试官相信：

1. 能独立完成需求评审、测试计划、用例、执行、缺陷、回归和上线结论；
2. 能理解内容、课程、学员、员工、企业微信、CRM 和后台之间的业务链路；
3. 能验证“内容发得出去、用户看得到、数据回得来、报表算得对”；
4. 能通过接口、日志、SQL 和报表逐层定位数据差异；
5. 能把稳定、高频、高价值的接口沉淀成自动化回归；
6. 能在小团队快速迭代中按风险取舍，并把未测范围和上线风险说清楚；
7. 会用 AI 辅助需求、用例、代码和日志分析，但不把 AI 输出直接当正确结果。

统一回答结构：

> 先说结论 → 分 3～5 步说方法 → 结合自己的工作或项目举例 → 最后补充验证闭环和风险边界。

回答时主动区分：

- **工作中做过**：生活服务平台的小程序、H5、管理后台；订单、支付、退款、会员、结算和分佣；需求、用例、功能/接口测试、缺陷跟踪、回归和上线验证；
- **个人项目做过**：`pytest_auto_api_my` 接口自动化、Playwright SaaS Checkout UI 自动化、AI 测试用例生成与评审平台；
- **当前项目已验证**：接口框架实际收集 6 条测试，5 条离线基础测试通过；
- **理解方法但尚未在该项目落地**：数据库断言、埋点自动校验、报表自动对账、CRM 全业务、并发上下文隔离和生产级数据清理；
- **LadyBoss 待确认**：内部字段、实际系统架构、数据规模、统计口径、团队配置和各系统完成度。

> [!warning] 面试表达底线
> `pytest_auto_api_my` 是个人商城接口自动化练习项目，不是 LadyBoss 项目，也不是完整 CRM。真实远程九步下单本轮没有执行，不能说“当前全部跑通”。SQL、埋点和报表对账是岗位迁移方案，不是框架现成功能。

## 1. 准备依据

### 1.1 岗位核心

[[岗位职责|完整 JD]] 可以压缩成五条主线：

1. **全流程质量保障**：需求评审、计划、方案、用例、执行、缺陷、报告和追溯；
2. **微信生态多端测试**：小程序、H5、APP、企业微信应用和真机兼容；
3. **全链路数据测试**：内容上传、分享转发、埋点、漏斗、数据回收和报表；
4. **接口自动化**：建设稳定、可重复、可定位的 API 回归；
5. **小团队协作与 AI 提效**：能快速学习、按风险取舍并验证 AI 产物。

岗位最强匹配口径：

> 我有小程序、H5 和管理后台的业务测试经验，也做过接口测试、SQL 数据核对和独立质量闭环；个人项目进一步验证了 Pytest、Requests、YAML、接口关联、断言、Allure 和 Jenkins。进入 LadyBoss 后，我会先理解内容、客户和数据口径，再把稳定接口逐步自动化，不会把练习项目包装成已经覆盖公司业务。

### 1.2 公司与业务理解

根据当前 ChatGPT 会话整理的公开信息，LadyBoss 的主要业务可概括为：

- 女性成长教育：课程、演讲、影响力、商业思维和个人成长；
- 创业赋能与商业服务：咨询、陪跑、社群、人脉和资源链接；
- 青少年素质教育：7～18 岁成长和素质教育相关服务。

结合 JD，测试岗位保障的不是单一课程页面，而是支撑业务运营的数字化平台：

`内容/课程 → 小程序触达 → 企业微信运营 → 分享传播 → 行为采集 → CRM 跟进 → 数据报表`

### 1.3 五条待验证业务链路

1. **内容与课程**：创建、审核、发布、访问、更新、下架和权限；
2. **学员与员工协作**：身份、课程/服务关联、跟进、记录、权限和并发更新；
3. **企业微信传播**：分享链接、场景参数、用户身份、渠道归因和异常链接；
4. **CRM 客户管理**：建档、去重、分配、跟进、标签、状态、转化和审计；
5. **数据回收与报表**：事件、上报、存储、清洗、去重、聚合、筛选和对账。

这些是根据 JD 建立的测试模型，实际模块名称和流程必须在面试或入职后确认。

## 2. 面试前优先背的 5 道题

### 1. 请用 60 秒介绍你的接口自动化项目。

**答题思路：** 讲清项目性质、目标、技术栈、执行链、真实结果和能力边界。

> **参考回答：** 这是我个人搭建的轻量接口自动化练习框架，使用 Pytest、Requests、YAML、JSONPath 和 Allure，通过商城的登录、商品、购物车、地址和下单接口验证框架能力。YAML 管理请求、断言和字段提取，`run_case()` 统一执行，上下文传递 token 和业务 ID，Python 负责编排九步主流程。目前实际收集 6 条测试，5 条离线基础测试通过，远程九步流程本轮没有执行。这个项目证明我具备接口自动化基础，但数据库断言、业务数据清理和生产级并发隔离仍需要继续完善。

### 2. 框架如何分层，一条 YAML 用例如何执行？

**答题思路：** 先讲各层职责，再按用例读取、变量解析、请求、断言、提取和报告说明执行链。

> **参考回答：** 框架按用例数据、请求执行、断言提取、上下文、Pytest 编排和报告 CI 分层。执行时，`run_case()` 根据 case ID 读取 YAML，与公共配置合并，解析上下文占位符；`RequestControl` 拼接 URL、合并 Header、注入 token 并发送请求；随后校验 HTTP 状态码和 JSONPath 业务字段，再把响应中的变量写入上下文。Fixture 管理环境、Session 和流程前后的上下文清理，Allure 记录步骤，Jenkins 执行离线回归基线。

### 3. 项目当前有哪些不足，如何接入 CI 并迁移到 LadyBoss？

**答题思路：** 主动说不足，再讲修复顺序、CI 准入和业务迁移，不把计划包装成现成功能。

> **参考回答：** 当前需要补强业务断言、离线完整流程、数据清理、并发上下文隔离和错误分类，并修复登录用例收集、多环境基线及 `run.py` 未返回测试退出码的问题。现在 Jenkins 只执行 5 条离线基础测试并归档 Allure 结果，远程九步流程没有进入 CI。迁移到 LadyBoss 时，我会先选择稳定、高频、结果可判断的登录鉴权、内容权限、客户查询、事件写入和报表查询接口，再增加 SQL 对账、异步等待、幂等和数据清理；小程序分享和真机兼容仍以人工测试为主。

### 4. 如何测试内容分享、数据回收和后台报表的完整链路？

**答题思路：** 先确认规则和唯一标识，再按业务、事件、存储、报表四层验证，最后补异常和补偿。

> **参考回答：** 我会先确认内容状态、分享入口、用户身份、渠道参数、事件定义和统计口径。功能层验证发布、展示、权限、分享跳转和下架；采集层检查分享、打开和访问事件是否触发，内容 ID、用户 ID、渠道、事件 ID 和时间是否正确；数据层核对接口、日志和数据库原始记录；报表层按相同时间、渠道和去重规则核对 PV、UV 和转化。异常覆盖断网补报、重复点击、参数缺失、匿名转登录、跨天和数据延迟。

### 5. 如果你是唯一测试，怎么保障整个产品质量？

**答题思路：** 不承诺全测，而是建立可持续的风险控制系统。

> **参考回答：** 我会先和产品、开发建立需求准入、冒烟清单、缺陷等级和上线准出标准；根据业务风险维护核心链路地图，每次迭代做影响分析。稳定接口和高频流程逐步进自动化，客户端真机和探索性场景保留人工。测试过程持续同步进度、未测范围和风险，上线后关注错误、关键事件和报表异常。重大问题复盘后进入回归用例、监控或自动化，形成闭环。

## 4. 全流程质量保障

### 1. 拿到一个新需求，你怎么开展测试？

**答案：**

> 我会先阅读需求、原型、接口说明和验收标准，确认业务目标、角色、主流程、状态、权限、字段、数据口径和影响范围。评审后按风险制定测试范围、优先级、环境、账号、数据和排期。
>
> 用例覆盖正常、异常、边界、权限、状态、接口、数据一致性、兼容和必要的性能场景。执行时先冒烟和主流程，再覆盖高风险异常。缺陷修复后验证原问题并做影响范围回归；上线前输出已测、未测、遗留问题和上线建议；上线后验证核心链路并沉淀回归资产。

### 2. 需求评审时你重点看什么？

**答案：**

> 我重点看目标是否明确、角色和权限是否完整、正向与逆向流程是否闭环、状态能否合法转换、字段和边界是否定义、异常与补偿如何处理、接口和数据口径是否一致，以及需求是否可测试。
>
> 例如内容分享需求，我会确认内容下架后旧链接怎么处理、匿名和登录用户怎样识别、一次分享多次打开怎样统计、PV/UV 和渠道归因怎样定义。如果这些不明确，测试无法判断结果对错，应在开发前确认。

### 3. 平时怎样设计测试用例？

**答案：**

> 我先确定测试对象、角色、输入、规则、状态和输出，再沿主流程逐节点展开正常、异常、边界、权限、组合、并发、安全和数据一致性。方法上结合等价类、边界值、场景法、状态迁移、判定表和错误推测。
>
> 对数据链路不能只写“页面显示正确”，还要明确事件是否上报、字段是否正确、是否落库、去重与聚合是否符合口径，以及报表怎样核对。

### 4. 测试时间不足时怎么保证质量？

**答案：**

> 我不会平均压缩所有测试，而会按业务影响、发生概率、改动范围、历史缺陷和可恢复性排序。优先覆盖登录、内容发布与访问、客户权限、数据回收和核心报表；先跑冒烟和 P0/P1，再做变更影响回归。
>
> 同时明确同步未测范围和风险，必要时建议灰度、开关、监控或延期。稳定的接口和主链路通过自动化节省重复回归时间。

### 5. 怎么判断一个版本能否上线？

**答案：**

> 我会检查核心链路是否通过、阻塞和严重缺陷是否关闭、修改范围是否完成关联回归、多端和数据结果是否一致、遗留问题是否可接受，以及监控和回滚是否准备好。
>
> 如果用户权限、客户数据、内容访问或关键报表仍有无法解释的差异，我会明确不建议上线。业务决定带风险上线时，也要记录影响、临时方案、负责人和回滚条件。

## 5. LadyBoss 业务场景测试

### 1. 内容从创建到下架，怎么设计测试？

**思路：** 用内容状态机组织，不只测新增、编辑和删除按钮。

**答案：**

> 我会先确认草稿、待审核、已发布、已下架和已删除等实际状态及允许的转换。创建时测标题、正文、封面、分类、资源、必填、长度和特殊字符；审核和发布测角色权限、定时发布、重复提交和失败重试；用户端验证展示、排序、搜索、详情、分享和访问权限；更新后检查缓存与多端一致性；下架或删除后检查列表、详情、历史分享链接和统计数据怎样处理。

### 2. 学员端和员工端的数据一致性怎么测？

**答案：**

> 先列出两端共享的业务对象，例如学员资料、课程、服务记录、标签和跟进状态，明确谁可读、谁可写、写后多久同步。用同一业务 ID 在两端和后台核对字段、状态、更新时间和操作人。
>
> 覆盖员工修改后学员端刷新、学员更新资料后员工端同步、账号切换、缓存、并发修改和接口失败。冲突时应按明确规则处理，不能出现静默覆盖或不同端长期不一致。

### 3. 企业微信内容分享链路怎么测？

**答案：**

> 先确认分享主体是员工、学员还是企业应用，入口是会话、群、朋友圈还是二维码，以及需要携带的内容 ID、渠道、员工、客户和场景参数。功能上验证标题、封面、落地页、授权登录和目标内容；权限上验证不同员工和客户能看到的内容；数据上检查分享、打开、访问和转化事件的关联。
>
> 异常覆盖链接被转发、多次打开、参数被篡改、员工离职、内容下架、用户未授权、微信版本差异和弱网恢复。企业微信接口权限及频率限制以实际文档为准。

### 4. CRM 客户生命周期怎么测？

**答案：**

> 我会先画出线索、潜在客户、已分配、跟进中、已转化、流失、回收等实际状态，确认每个状态的进入条件、可执行操作、责任人和退出路径。按正常转化、失联、拒绝、重新激活和回收流程覆盖。
>
> 每次状态变化检查页面、接口、数据库、操作日志和报表，异常覆盖非法跳转、重复操作、越权修改、批量任务失败和并发跟进。状态名称及规则必须以公司系统为准。

### 5. 员工只能查看自己负责的客户，怎么测权限？

**答案：**

> 建立“角色—组织—资源—操作—数据范围”矩阵，覆盖普通员工、主管、跨部门协作、管理员和离职员工。页面层检查菜单、按钮和字段；接口层用其他客户 ID 直接请求；数据层验证查询条件和导出范围。
>
> 同时覆盖搜索、批量操作、消息链接、浏览器缓存、分享 URL、导出和历史记录，防止只限制列表但详情或接口仍可越权。

## 6. 小程序、H5、APP 与企业微信

### 1. 小程序测试要覆盖哪些方面？

**答案：**

> 我会从业务功能、微信能力、兼容、网络、性能和数据六层覆盖。业务包括登录、内容、课程、分享和个人信息；微信能力包括授权、拒绝授权、扫码、分享、场景值、返回和缓存；兼容覆盖 iOS/Android、主流机型、微信版本和屏幕；网络覆盖弱网、断网、恢复和超时；性能关注首屏、长列表和多媒体；最后核对接口、后台和数据一致性。

### 2. 微信登录和授权怎么测？

**答案：**

> 覆盖首次授权、拒绝、取消、重新授权、授权过期、账号切换、微信切换、手机号绑定和已有账号合并。检查 code 只能使用一次、服务端会话和 token 生命周期、退出登录、异地登录和敏感权限最小化。
>
> 直接调用接口时也要验证未登录、过期 token、错误用户和越权访问，不能只看前端登录页面。

### 3. 小程序分享和场景值怎么测？

**答案：**

> 我会覆盖分享给个人、群、二维码或其他实际入口，检查标题、封面、路径、内容 ID、渠道、员工和场景参数。接收方分别以未登录、已登录、无权限和不同微信版本打开，验证跳转、授权和归因。
>
> 对参数缺失、重复、篡改、超长、过期和二次转发做异常测试，并检查同一分享多次打开的 PV、UV 和渠道规则。

### 4. 弱网和断网场景怎么测？

**答案：**

> 对加载、提交、上传、分享和事件上报分别模拟高延迟、丢包、断网和网络切换。检查加载提示、超时、取消、重试、重复点击、数据缓存和恢复后补报。
>
> 重点验证请求是否产生重复业务数据、埋点是否漏报或重复、页面是否显示旧数据，以及用户能否明确知道操作结果。涉及创建或修改的接口必须结合幂等设计。

### 5. 企业微信应用重点测什么？

**答案：**

> 重点是企业成员身份、部门和角色、应用可见范围、外部联系人、客户归属、授权范围、链接跳转和员工离职继承。接口层关注 access token、权限、频率限制、回调验签、重复回调和失败重试。
>
> 还要验证员工只能访问授权客户，外部客户不能看到内部信息，消息或链接中的客户、内容和渠道参数正确。

## 7. 埋点、数据回收、SQL 与报表对账

### 1. 一个埋点事件至少应该包含哪些字段？

**答案：**

> 通常需要事件名称、事件唯一 ID、发生时间、上报时间、用户或匿名设备标识、会话、内容/课程/客户等业务对象 ID、页面、入口、渠道、应用版本和环境。具体字段以事件字典为准。
>
> 测试不仅看字段存在，还要验证触发时机、类型、取值、必填、枚举、跨端一致性和敏感信息是否符合最小采集原则。

### 2. PV 和 UV 怎么理解和测试？

**答案：**

> PV 通常是符合口径的访问次数，UV 是在时间范围内按约定身份标识去重后的访问用户数。测试前必须确认页面/内容范围、时间和时区、用户标识、匿名与登录合并、机器人或测试数据过滤等规则。
>
> 我会用多个用户、多次访问、跨设备、匿名转登录和跨天场景构造可预测数据，再核对原始事件、SQL 和报表。不能默认 `COUNT(*)` 就是 PV、`DISTINCT user_id` 就一定是最终 UV。

### 3. 怎样验证事件是否漏报或重复上报？

**答案：**

> 为每次测试操作记录业务对象、事件 ID、用户、时间和预期次数，通过抓包或客户端日志确认产生，再在服务日志或原始事件表查询。漏报时定位是否未触发、请求失败、队列丢失或落库失败；重复时检查前端监听、重试、重复点击和服务端幂等。
>
> 事件唯一 ID 或等价幂等键能帮助判断同一事件是否被重复消费，但具体去重规则要与数据团队确认。

### 4. SQL 怎样核对 PV、UV？

**答案：**

> 下面只是示例字段，实际需使用公司数据字典：

```sql
select
    count(*) as pv,
    count(distinct user_id) as uv
from event_log
where event_name = 'content_view'
  and event_time >= '2026-10-27 00:00:00'
  and event_time <  '2026-10-28 00:00:00'
  and content_id = 'demo_content';
```

> 执行前要确认是否按 `event_id` 去重、匿名用户用哪个字段、是否排除测试数据、时间按事件时间还是入库时间，以及报表是否有延迟。

### 5. 页面、导出文件和数据库不一致怎么查？

**答案：**

> 先确认三者的筛选条件、权限、时区、刷新时间、分页、状态映射和统计粒度一致。再固定小时间窗和单个内容/客户，用唯一键比较明细，分别找页面有数据库无、数据库有导出无和字段不同。
>
> 如果数据库正确，继续查查询 SQL、缓存、分页和导出任务；如果原始数据就缺失，向前查上报和落库。总金额或总量一致也不能证明明细一致。

## 8. `pytest_auto_api_my` 接口自动化项目

### 1. 请用 60 秒介绍你的接口自动化项目。

**思路：** 先定位为个人练习框架，再讲技术栈、运行链、业务流、验证结果和不足。

**答案：**

> 这是我自己搭建的轻量接口自动化练习项目，技术栈是 Pytest、Requests、YAML、JSONPath 和 Allure，使用商城的登录、商品、购物车、地址和下单接口验证框架能力。
>
> YAML 管理单接口请求、断言和字段提取；`run_case()` 统一读取用例、解析上下文占位符、发送请求、执行断言并提取响应；`ContextManager` 在顺序流程中传递 token、商品 ID、规格和购物车 ID；Python 测试负责九步流程顺序和选择有库存规格等业务判断。当前实际收集 6 条测试，5 条离线基础测试通过，远程主流程本轮未执行。

### 2. 框架如何分层，一条 YAML 用例怎样执行？

**答案：**

> 框架按用例数据、请求执行、断言提取、上下文、流程编排和报告 CI 分层。YAML 管理接口路径、方法、参数、Header、断言和提取；`RequestControl` 负责请求；`AssertControl` 和 `ExtractControl` 负责校验与变量提取；`ContextManager` 保存流程变量；Pytest 负责用例发现、Fixture 和业务流程编排；Allure 与 Jenkins 负责结果展示和离线基线。
>
> 执行时，`run_case(yaml_name, case_id)` 先通过 `get_case_by_id()` 读取目标 case，并与 `case_common` 做一层浅合并；再通过 `resolve_placeholders()` 替换上下文变量；`RequestControl` 拼接 URL、合并 Header、注入 token 并发送请求；随后校验 HTTP 状态码和 JSONPath 业务字段，提取结果写入上下文，最后返回标准响应。`active_env`、`api_client`、`flow_context` 和 `case_context` 等 Fixture 分别管理环境、Session 和上下文生命周期。

### 3. Token、接口依赖、测试数据和隔离怎样处理？

**答案：**

> 登录接口用 JSONPath 提取 token，商品列表提取 `product_id`，商品详情后由 Python 选择有库存的 `unique`，购物车接口提取 `cartId`。后续 YAML 通过 `${{变量名}}` 引用。
>
> 直接响应字段使用通用提取器，带业务条件的选择留在流程代码。流程开始和结束由 `flow_context` 清理上下文，独立用例使用 `case_context` 隔离，Session 由 `api_client` 统一管理。当前 `ContextManager` 是进程内类字典，适合顺序流程，不支持真正的并发隔离；框架也只完成上下文清理，还没有生产级业务数据创建和回收能力。
>
> 迁移真实项目后，应为每条流程创建独立上下文，通过 API 或 Fixture 构造带唯一标识的测试数据，并在结束后按业务规则删除、失效或回滚；写接口还要结合幂等键，避免超时重试制造重复数据。

### 4. HTTP、业务字段、数据库断言和失败定位怎样设计？

**答案：**

> 断言层先检查 HTTP 状态码，再按 JSONPath 提取业务字段，当前支持 `eq/==/equals`、`ne/!=`、`in`、`contains` 和 `exists`。登录和商品接口既有状态码，也有业务字段断言。
>
> 当前后半段多个接口只断言 HTTP 200，这是已知不足；应该补业务码、关键字段、状态不变量和最终订单结果。真实项目还应根据风险增加数据库或查询接口校验，并对异步任务使用有上限的轮询等待。数据库断言、埋点自动校验和报表自动对账目前尚未在该框架实现，属于迁移后的增强方向。
>
> 失败时先确认请求是否发出、参数和鉴权是否正确，再核对响应业务码、服务日志、数据库状态和下游报表，定位差异第一次出现的层，不能把 HTTP 200 等同于业务成功。

### 5. 怎样让接口自动化真正落地、接入 CI 并迁移到 LadyBoss？

**答案：**

> 我会优先自动化稳定、高频、业务价值高、结果可判断且数据可清理的接口，不追求接口数量。当前 Jenkinsfile 会创建独立虚拟环境、安装依赖、执行 5 条离线基础测试并归档 Allure 结果；远程九步主流程没有进入 CI。`run.py` 还存在未把 Pytest 退出码返回给 shell 的风险，必须修复，否则测试失败可能没有正确阻断流水线。
>
> 第一，补齐默认地址、订单确认和最终订单结果的业务验证；第二，把九步成功、无库存和关联参数传递固化为 fake client 离线测试并加入 Jenkins；第三，修复登录用例收集、多环境基线和 `run.py` 退出码；第四，增加 YAML Schema、错误分类、日志脱敏和凭据外置；第五，再根据真实需求扩展数据库断言、并发隔离和数据清理。重试不是第一优先级，因为盲目重试下单或写接口可能制造重复业务数据。
>
> 迁移到 LadyBoss 时保留 YAML、请求、断言、提取、上下文和 CI 骨架，替换业务模块和数据。优先覆盖登录鉴权、内容查询与权限、客户查询、分享记录写入和报表查询；再补事件和报表业务断言、SQL 对账、异步等待、幂等检查和数据清理。小程序分享、真机兼容和探索性场景仍以人工为主。迁移方案属于计划中，不能说当前框架已覆盖 LadyBoss。

## 9. 缺陷定位、稳定性与安全

### 1. 怎么判断是前端还是后端问题？

**答案：**

> 先复现并查看 Network：如果前端未发请求、参数组装错误或渲染错误，倾向前端；请求正确但响应业务错误，继续查后端日志和数据；响应正确但页面错误，查前端状态和映射；数据库正确、报表错误时再查查询、聚合和缓存。
>
> 这只是定位方向，最终要以请求、日志、代码和数据证据确认，不能根据页面现象直接分责任。

### 2. 接口超时但后台可能已成功，怎么处理？

**答案：**

> 不能直接重发写请求。先通过业务唯一键或查询接口确认实际状态；服务端应使用幂等键或唯一约束，使同一业务请求重复到达不会重复创建。客户端重试要有次数、退避和可重试错误范围。
>
> 对内容创建、客户建档和事件上报分别定义幂等语义；超时后的未知状态需要查询或补偿，而不是默认失败。

### 3. 怎样测试幂等性？

**答案：**

> 对同一业务请求使用相同幂等键连续、并发和超时后重放，检查只产生一条业务记录，返回结果一致或明确表示重放。再用相同幂等键配不同请求内容，应该冲突而不是静默复用。
>
> 还要核对数据库唯一约束、日志、消息和下游副作用，不能只看接口都返回 200。

### 4. 接口返回 200，但数据库没有数据，怎么查？

**答案：**

> 先确认 200 对应的业务码和响应含义，是否只是接收任务而非完成写入。再按服务日志、事务提交、异步消息、消费者、数据库连接和查询条件逐层检查。
>
> 若是异步链路，要确认允许延迟和最终状态；若接口声称成功但事务回滚，则是严重一致性问题。不能把 HTTP 200 自动等同于持久化成功。

### 5. 自动化用例偶发失败，怎么治理？

**答案：**

> 先分类真实缺陷、环境、第三方、数据和脚本问题，统计失败率而不是直接重跑。检查共享数据、执行顺序、异步等待、时间边界、网络、依赖服务和并发污染。
>
> 修复根因后再决定是否保留有限重试。重跑只能处理已知瞬时错误，不能掩盖不稳定断言或真实业务问题。

## 10. AI 协同开发与测试

### 1. 你怎样用 GPT 或 Codex 辅助测试？

**答案：**

> 我会用它辅助整理需求流程、补充候选测试点、构造边界数据、生成脚本初稿、解释错误和整理文档。输入会包含需求原文、角色、规则、接口契约、项目结构和输出格式。
>
> AI 只负责提供候选，业务正确性由需求、接口、代码和实际系统验证。修改代码时看 diff、运行测试并保留证据，不直接接受大段生成结果。

### 2. 一个好的测试用例生成 Prompt 包含什么？

**答案：**

> 包含角色与目标、业务背景、用户角色、流程和状态、字段与数据口径、历史缺陷、测试范围和不在范围、覆盖维度、输出格式及禁止猜测规则。信息不足时要求输出待确认问题。

```text
你是软件测试工程师。依据下列需求和已确认规则生成候选用例。
必须覆盖：正常、异常、边界、权限、状态、接口和数据一致性。
每条用例输出：规则来源、标题、前置条件、步骤、预期、优先级。
未提供的业务规则不得自行补充，统一标记“待确认”。
```

### 3. 怎样判断 AI 生成的用例质量？

**答案：**

> 至少看需求和高风险规则覆盖率、业务准确性、幻觉、边界异常、重复率、可执行性和人工修改量。准备一组人工确认的基准需求和参考测试点，对不同 Prompt 或流程版本重复评估。
>
> 不能以生成条数多或语言流畅判断质量；遗漏关键权限或统计口径比少生成几条更严重。

### 4. AI 生成代码后怎么验收？

**答案：**

> 先确认改动范围和设计是否符合项目约束，再逐段检查 diff、依赖、错误处理和敏感信息；运行格式/静态检查、单元测试、框架测试和目标业务场景；最后检查失败路径和回滚。
>
> 对写接口、数据脚本和删除操作要额外审查副作用。AI 说“测试通过”不算证据，必须看到实际命令和结果。

### 5. 怎样防止 AI 泄露公司数据？

**答案：**

> 先遵循公司批准的工具、账号、模型和数据策略；敏感需求、代码、客户信息、Token、日志和生产数据不得直接输入未授权服务。必要时脱敏、最小化上下文或使用企业隔离环境。
>
> 生成结果也要检查是否回显秘密、真实客户或受限制代码，聊天记录和导出物同样需要权限和保留策略。

## 11. 高频压力题与行为题

### 1. 你只有一年左右经验，为什么觉得能胜任？

**答案：**

> 我的年限不长，但已经参与过完整测试流程，并负责过订单、支付、退款等高风险模块。我能从业务、接口和数据多个层面验证结果，也会持续把稳定场景沉淀成自动化。
>
> 对 LadyBoss 的内容、CRM 和埋点业务我不会假装熟悉全部细节，但我有建立流程、状态、权限和数据模型的方法，也会通过文档、历史缺陷和团队评审快速补齐。

### 2. 接口自动化是公司项目还是个人项目？

**答案：**

> `pytest_auto_api_my` 是我个人搭建的练习框架，不是上一家公司生产框架。它的价值是让我实际理解 YAML 数据驱动、请求封装、断言、提取、上下文、Fixture、报告和 CI。
>
> 工作中如果公司已有框架，我会遵循现有规范补业务用例和能力，不会为了展示技术重复造轮子。

### 3. 你能独立负责整个产品吗？

**答案：**

> 我可以独立推进测试工作，但“独立”不等于脱离产品和开发，也不等于一个人保证零缺陷。我会建立需求评审、风险优先级、冒烟、回归、缺陷和上线标准，并持续同步未测范围和风险。
>
> 如果范围或时间超过单人能力，会用数据说明影响，请团队共同调整范围、排期或上线策略。

### 4. 时间很紧，产品坚持今天上线怎么办？

**答案：**

> 我会快速确认改动和高风险链路，先执行冒烟、核心权限、关键数据和历史高风险用例；同时说明哪些场景未测、可能影响和回滚条件。
>
> 如果是轻微展示问题，可在监控和回滚准备下评估上线；如果存在数据丢失、越权、客户信息泄露或关键报表不可解释，我会明确不建议上线，并提供证据，而不是只说“测试不同意”。

### 5. 为什么离开上一家公司？

**答案：**

> 我希望在继续做好功能和业务测试的基础上，进一步提升接口自动化、数据质量和 AI 辅助测试能力，接触更完整的质量体系。离职原因会聚焦职业发展和岗位匹配，不评价原公司和同事。

## 12. 入职计划与反问

### 1. 如果入职，第一周做什么？

**答案：**

> 第一周先熟悉产品、用户角色、内容和客户主链路，确认测试环境、账号、发布流程、缺陷工具、接口文档、事件字典和报表口径。跟着一个真实需求走完评审到上线，并阅读历史高风险缺陷。
>
> 输出系统链路图、角色权限表、核心冒烟清单和待确认问题，不急着先改框架。

### 2. 入职第一个月希望做到什么？

**答案：**

> 能独立接住一个模块或迭代，建立可复用的用例和回归清单；对内容、分享、CRM 和数据链路形成风险模型；把一小批稳定接口接入现有自动化或做出最小回归基线。
>
> 同时统计缺陷、报表差异和重复回归，提出一个有证据的小改进，而不是一开始大规模重构。

### 3. 当前各系统分别处于什么阶段？

**反问方式：**

> 目前学员端、员工端、内容后台、CRM 和数据报表分别处于已上线、持续迭代还是建设阶段？近期最核心的业务链路是什么？

### 4. 当前测试基础和最高优先级是什么？

**反问方式：**

> 目前是否有独立测试环境、接口文档、事件字典、自动化、CI 和统一报表口径？现阶段最希望测试优先解决功能稳定性、数据准确性还是回归效率？

### 5. 入职前三个月的衡量标准是什么？

**反问方式：**

> 团队希望这个岗位在前三个月交付哪些可衡量结果？例如独立承接迭代、建立核心回归清单、降低线上问题，或者落地一批接口自动化。

> [!note] 反问原则
> 技术面优先了解系统阶段、团队配置、质量痛点和岗位目标；薪资、假期等可在 HR 阶段确认。

## 最后速背

### 个人定位

> 一年左右测试经验 + OPPO 实习 + 小程序/H5/后台 + 订单支付与多端一致性 + 接口/SQL + Pytest 接口自动化个人项目 + AI 辅助测试。

### LadyBoss 业务主线

> 女性成长教育与创业赋能 → 内容/课程 → 学员与员工 → 企业微信传播 → CRM 跟进 → 数据回收与报表。

### 全链路数据关键词

> 事件定义、唯一 ID、用户/内容/渠道、触发、上报、落库、去重、聚合、延迟、时区、筛选、SQL 对账。

### 小程序关键词

> 登录授权、场景值、分享扫码、真机兼容、微信版本、弱网、缓存、返回栈、多端一致性。

### CRM 关键词

> 建档、唯一性、合并、分配、跟进、标签、状态、转化、权限、审计、导入导出、数据隔离。

### 接口自动化关键词

> Pytest、Requests、YAML、JSONPath、`run_case()`、token、上下文、断言、提取、Fixture、Allure、Jenkins、数据清理、幂等、脱敏。

### 当前项目真实数字

> 实际收集 6 条：5 条离线框架测试通过 + 1 条远程九步主流程本轮未执行。

### 四句风险口径

1. `pytest_auto_api_my` 是个人商城接口练习框架，不是 LadyBoss 或完整 CRM 项目。
2. 数据库断言、埋点自动校验和报表自动对账尚未在该框架实现。
3. LadyBoss 内部架构、字段、规模和统计口径需要面试确认。
4. AI 只生成候选结果，最终质量由需求、代码、测试结果和人工审核负责。

### 万能场景题结构

> 确认范围和口径 → 画正向主链路 → 按节点检查输入、规则、状态和输出 → 扩展异常、边界、权限、并发、安全和兼容 → 用接口、日志、SQL 和报表验证 → 补回归、监控和风险闭环。
