## 二、SQL、并发与问题定位

### 4. SQL 中去重、分组、分组后过滤和左连接分别用什么？

#### 你的原回答

> 查询结果去重用 `DISTINCT`，分组用 `GROUP BY`，分组后过滤用 `HAVING`，左连接用 `LEFT JOIN ... ON ...`。

#### 原回答分析

- 四个关键词基本都答对，速度也快，这是本场较明确的得分项。
- 面试官反问“不是背的吗”，说明只报关键词不足以证明熟练；最好各补一个适用条件或简短例子。

#### 参考回答

> 去重使用 `SELECT DISTINCT`；分组统计使用 `GROUP BY`；对聚合后的组做过滤用 `HAVING`，行级条件仍用 `WHERE`；保留左表全部记录并关联右表时用 `LEFT JOIN ... ON ...`。例如查每个租户的重复手机号，可以按 `tenant_id, phone` 分组，再用 `HAVING COUNT(*) > 1` 过滤。

### 5. 库存只有 1，怎样验证 10 个用户同时下单时不会超卖？

#### 你的原回答

> 用 JMeter 之类的压测工具设置 10 个线程并发调用下单接口，查看接口返回、后台订单和商品库存，确认只卖出一个。为了模拟不同用户，可以先注册 10 个真实账号，让请求携带 10 个不同用户的 ID 或 Token。JMeter 有同步计时器，可以让线程尽量同时发出。

#### 原回答分析

- 已经答到并发工具、不同用户、同步发起和后台库存，主方向正确。
- 面试官连续追问“不同用户怎么做”和“如何保证同时”，说明第一遍答案没有把关键测试装置讲完整。

- 你随后承认这主要是个人练习而非生产实践，这个边界需要保留。

#### 参考回答

> 我会先准备一个库存为 1 的独立商品和 10 个有效账号，用 CSV Data Set Config 给每个线程分配不同 Token。线程组设置 10 个并发用户，在下单请求前加入 Synchronizing Timer，让 10 个线程到齐后同时释放。

### 6. 后台价格是 98.5 / 10 元，用户端却显示 99 / 9 元，怎样定位？

#### 你的原回答（两轮合并整理）

> 先在用户端用 F12 看接口响应。如果接口返回正确而页面显示错误，可能是前端渲染或缓存问题；如果接口也返回错误，初步怀疑后端。再查数据库：如果数据库正确而接口错误，可能是后端业务逻辑；如果数据库也错误，可能是保存落库过程出了问题。Web 页面看接口时，F12 会比 Fiddler 更快。

#### 原回答分析

- 两轮都遇到几乎相同的题，第二轮明显吸收了第一轮思路，能够按页面—接口—数据库分层，这是正向表现。

- 数据库正确、接口错误也不一定只是“业务逻辑”，还可能是缓存、搜索索引、同步消息、价格服务、精度与舍入规则。
- 定位前应先确认期望：是否存在优惠、会员价、币种换算或展示取整，避免把正确规则当缺陷。

> 我会先确认预期和复现范围：同一商品、租户、账号、币种和时间下是否存在促销、会员价、汇率或取整规则。确认确实应显示后台价格后，再沿数据链路定位。

### 7. 输入正确账号密码后点击登录没反应，可能有哪些前端或后端原因？怎样继续定位？

#### 你的原回答

> 先打开 F12，再点击登录，看请求和状态码。404 可能是前端网址问题；如果请求能发出，就检查请求字段是否符合接口文档，再看响应状态码和是否返回正确 Token。500 说明服务器异常，可以进一步查服务器日志是否收到用户信息。若完全没发请求，可能是前端 JavaScript 报错，可以在 Console 查看。

#### 原回答分析

- 最终覆盖了“没有请求—请求发出—响应异常—查日志”这条基本链路，但需要面试官多次提示才补全。
- 404 不应直接归为前端问题；它只能说明资源未找到，还要看 URL、路由、网关和部署配置。
- 返回 500 后只说“查日志”太泛，应结合 Trace ID、异常栈、服务调用、数据库和依赖定位。
- 还遗漏“接口成功但页面没有跳转”这一大类前端状态或路由问题。

#### 参考回答

> 我会先定义“没反应”是哪一种，再按请求链路分四类定位。
>
> 1. **没有发请求**：检查按钮是否被遮挡或禁用、表单校验是否拦截、点击事件是否绑定、Console 是否有 JavaScript 异常。
> 2. **请求发错或被浏览器拦截**：核对 URL、方法、Header、Content-Type、请求体、CORS、网络和网关路由。
> 3. **服务端返回失败**：401/403 查账号、认证、CSRF、权限或限流；4xx 查参数；5xx 用 Trace ID 查服务日志、异常栈、数据库和下游依赖。
> 4. **接口成功但页面不跳转**：检查响应解析、Token/Cookie 存储、登录状态更新、前端路由和权限菜单加载。
>
> 最后用同一账号在接口工具中直接请求，帮助隔离前端和服务端问题。

### 9. 一个 HTTP 请求通常包含哪些部分？Header 中常放什么？

#### 你的原回答

> 请求需要方法，例如 GET、POST、PUT、DELETE；还需要接口地址和请求参数。GET 参数通常在 URL 中，POST 通常放请求体，文件上传有单独的方式。Header 中会放请求格式、User-Agent 和 Token。

#### 原回答分析

- 方法、参数、请求体和部分 Header 答到了，但回答较乱，漏掉 URL、认证、Cookie 等基本组成。
- “GET 一定没有请求体、POST 参数一定只放请求体”不宜说得绝对，应以接口契约为准。

#### 参考回答

> 一个请求最基本包括方法、URL、Header 和可选的 Body。URL 又包含协议、主机、端口、路径与 Query 参数；鉴权可能放在 `Authorization`、Cookie 或签名参数中。
>
> 常见 Header 有 `Content-Type`、`Accept`、`Authorization`、`Cookie`、`User-Agent`，企业系统还可能有租户 ID、请求时间、签名、幂等键和 Trace ID。测试时除了值正确，还要覆盖缺失、过期、篡改和重复 Header。

### 13. 如果让你测试一个 Agent，你会考虑哪些方面？

#### 你的原回答

> 以客服 Agent 为例，会从业务取得评测集，再让大模型扩充，测试单轮和多轮回答质量；先做小规模基准，再跑约 500 条，用 DeepEval 之类的框架评分。还会看答非所问、工具调用和生成格式。提示词注入和 Token 消耗有所了解，但提示词注入没有真正实践过，需要加强。

#### 原回答分析

- 相比此前伊智面试，已经补上真实业务评测集、小样本基准、批量评测、工具调用、安全和成本，方向有进步。
- 主要问题是仍以“用户提问—模型回答—评价文本”为主，这更接近 LLM 或聊天机器人评测；Agent 还会规划、调用工具、改变业务状态并根据中间结果继续行动。
- 没有先定义任务的成功条件，也没有系统展开工具选择、参数、权限、幂等、异常恢复、业务落库和最终回答与真实状态的一致性。
- “跑 500 条、用 DeepEval 评分”属于执行手段。若没有明确每条 Case 的期望工具、参数、最终状态和失败类型，样本再多也难以定位问题。
- 提示词注入和 Token 成本是必要的横向测试维度，但不是这道题最核心的区分点。面试官更想听到你能否测试完整的执行链路。

#### 面试官真正想听什么

普通对话测试主要判断“回答得对不对”；Agent 测试需要判断“任务有没有被正确、安全地执行”。可以把一条任务拆成：

```text
用户任务 → 意图识别 → 任务规划 → 工具选择 → 参数构造
        → 工具执行 → 结果理解 → 状态更新 → 下一步决策 → 最终回答
```

因此，不能因为 Agent 回复“退款成功”就判定通过，还要查看 Trace，确认它调用了什么工具、传了什么参数、接口实际返回什么、数据库状态是否改变，以及回答是否与真实执行结果一致。

#### 七层测试模型

| 层级 | 核心检查点 | 退款 Agent 示例 |
| --- | --- | --- |
| 1. 意图与任务 | 是否理解目标；信息不足时是否澄清；停止条件是否正确 | 区分退款、取消订单和查询进度；缺订单号时先询问 |
| 2. 规划 | 是否拆出必要步骤；依赖关系是否合理 | 退款前先确认订单归属、订单状态和支付状态 |
| 3. 工具选择 | 是否调用正确工具；是否调用了不必要或危险工具 | 应调用退款工具，而不是取消订单或修改订单金额 |
| 4. 参数与约束 | 参数值、类型、必填项和业务约束是否正确 | `order_id`、退款金额、币种、用户身份是否正确 |
| 5. 执行与恢复 | 超时、500、空结果和业务失败时是否正确处理 | 超时先查询结果或使用幂等键，不能盲目再次退款 |
| 6. 系统状态 | 数据是否真正落库；状态流转和副作用是否正确 | `PAID → REFUNDING`，退款流水唯一，金额不超付 |
| 7. 最终回答 | 回答是否基于工具结果，并与真实状态一致 | 接口失败时不能告诉用户“退款成功” |

在这七层之外，还要横向覆盖：

- **RAG 与知识**：召回是否正确、引用是否有依据、知识版本和权限是否生效、无答案时是否拒答。
- **安全**：提示词注入、越权调用、敏感信息泄露、跨用户或跨租户访问、高风险动作是否需要确认。
- **多轮与状态**：上下文是否串线、参数是否被后续输入错误覆盖、任务中断后能否恢复、是否出现循环调用。
- **非功能**：并发、稳定性、时延、Token 和调用成本、限流，以及 Trace 是否完整可定位。

#### 用订单退款 Agent 落地

假设 Agent 可以调用 `get_order`、`get_payment`、`apply_refund` 和 `cancel_order`，测试时我不会只写“输入问题—期望回复”，而会为每条 Case 记录：

| 字段 | 内容 |
| --- | --- |
| Input | 用户任务和上下文 |
| Preconditions | 订单、支付、用户权限等前置状态 |
| Expected Tool / Arguments | 允许或必须调用的工具及关键参数 |
| Expected End State | 数据库状态、流水和外部副作用 |
| Actual Trace | 实际规划、工具、参数、返回值和重试过程 |
| Final Response | 最终回复及其依据 |
| Result | Pass / Fail 与失败所在层级 |

代表性用例至少包括：

1. 已支付订单正常全额退款，金额和状态正确。
2. 缺少订单号时先澄清，不自行猜测。
3. 订单不存在、未支付、已退款或状态不允许退款时不调用退款工具。
4. 用户无权操作他人订单时拒绝执行，不能泄露订单信息。
5. 部分退款、优惠分摊和退款上限正确，不能只按商品单价退款。
6. 退款接口返回 500、业务失败或空结果时，正确提示、降级或转人工。
7. 接口超时但后台已经退款成功时，先查真实状态；重试不得造成重复退款。
8. 工具返回失败时，最终回答不能编造成“已经成功”。
9. 多轮修改订单号或金额时，以确认后的有效参数执行，并保留审计记录。

#### 评价方法与指标

- 确定性结果用代码断言：工具名、关键参数、调用次数、Schema、数据库状态、退款流水和幂等性。
- 语义结果用明确的评分标准检查任务完成、事实依据、拒答和表达质量；LLM Judge 需要用人工 Gold Set 校准。
- 多轮任务按完整 Trace 评估，既要能判断是否成功，也要能定位失败发生在意图、规划、工具、参数、执行、状态还是回答层。
- 核心指标可包括任务成功率、工具选择正确率、参数正确率、最终状态正确率、异常恢复率、无依据成功声明率、时延和单任务成本。
- 不应为了评分把所有工具调用顺序限定得过死。Agent 可能存在多条合理路径，应重点验证必要前置条件、关键业务不变量和最终状态。

#### 最优回答（2–3 分钟）

> 我不会只验证 Agent 最终说了什么，而会先根据业务目标定义任务成功条件，再检查从用户任务到系统状态改变的完整 Trace。
>
> 我会把它分为七层：第一，意图是否识别正确，信息不足时会不会澄清；第二，任务规划和停止条件是否合理；第三，工具是否选对；第四，参数和业务约束是否正确；第五，工具超时、500、空结果或业务失败时能否正确恢复；第六，数据库和外部系统状态是否真正改变；第七，最终回答是否与真实执行结果一致。另外再横向覆盖 RAG、权限安全、多轮会话隔离、性能、Token 和成本。
>
> 例如测试退款 Agent，我不会因为它回复“已为您退款”就判定通过。我会查看它是否先确认订单归属、订单和支付状态，是否调用了正确退款工具，订单号、金额和币种是否正确，退款流水是否唯一，后台是否从 `PAID` 变成 `REFUNDING`。如果接口超时但实际已经退款，它再次调用可能造成重复退款，所以还要验证查询确认、幂等和重试策略；工具返回失败时，也不能向用户声称成功。
>
> 用例会从真实脱敏任务、SOP、边界组合和历史失败中构造，并保存 Input、前置状态、期望工具与参数、期望最终状态和实际 Trace。确定性的工具、参数、状态与调用次数用代码断言；语义部分用明确 Rubric 的模型评分，并用人工 Gold Set 校准。最后统计任务成功率、工具选择正确率、参数正确率、最终状态正确率、异常恢复率、时延和成本。Agent 可以有不同的合理执行路径，所以我不会机械限定每一步，而会重点校验必要前置条件、业务不变量和最终状态。

#### 一分钟精简口径

> 测试 Agent 不能只看最终回复，而要验证“意图—规划—工具—参数—执行—状态—回答”整条 Trace。比如退款 Agent 回复成功，我还要确认它是否校验了订单归属和支付状态，是否调用正确工具并传对订单号、金额和币种，数据库是否真正进入退款状态，以及超时重试有没有造成重复退款。工具失败时，回答也不能说成功。用例中我会同时记录期望工具、关键参数和最终状态，确定性结果用代码断言，语义结果用 Rubric 与人工 Gold Set 校准，再统计任务成功率、工具和参数正确率、最终状态正确率、异常恢复率、时延与成本。

#### 原回答分析

- 你实际想到了不少高风险点：金额公式、0 元、库存、余额不足、回调、幂等、下架、切换渠道和币种，这些并不是“没有经验”。

- 这道题是整场最明显的失分点，也是面试官最想传递的方法：**对象 → 数据特性 → 边界 → 对象组合 → 业务结果**。

#### 参考回答

> 我会先把六个元素拆成数据对象，再用等价类、边界值和决策表组合。优先级最高的是服务端最终金额、库存和支付幂等，因为它们直接造成资金或资产损失。
>
> **单价**：确认币种、精度、最小值、最大值、0、负数、超长值及舍入规则。金融金额应优先使用最小货币单位整数或 Decimal，避免二进制浮点误差。
>
> **数量**：必须是整数，覆盖 1、最大可购数、库存数、库存数 ±1，以及 0、负数、小数、超大数和并发抢购。
>
> **优惠券**：覆盖有效期、适用商品、门槛边界、满减或折扣、封顶、叠加/互斥、已使用、过期和优惠大于商品金额。确认最低应付金额能否为 0，不能出现负数。
>
> **总金额**：验证公式、计算顺序、每行与订单级舍入、前端展示、下单接口、支付单和数据库一致。对 `9.99 × 999`、多商品、折扣后多位小数等组合重点验证。
>
> **支付链路**：服务端重新计算金额，不能信任前端传值；覆盖金额篡改、双击、超时、重复回调、渠道切换、余额不足、支付中商品下架/改价/库存变化、0 元单、取消和退款。
>
> 用例不做全排列。我会按资金损失和发生概率选高风险组合，再用 Pairwise 补常规组合；最终以订单、支付流水、库存、优惠券状态和对账结果作为验收证据。

#### 面试官当场方法

面试官强调，测试设计不能只凭临场枚举正常流程，而要先识别每个对象的生活与数据特性：单价有整数/小数、精度、最小和最大；数量是整数，有最小、最大和库存边界；优惠券有门槛；这些对象组合后才得到最终金额与支付结果。少一分钱和少一百万元在资金正确性上属于同类问题。

### 16. 你怎样理解 AI 的原理？

#### 你的原回答

> AI 对测试来说是提效工具。使用时主要通过提示词驾驭大模型，也可以用 Skill 等手段。AI 工具会在用户提示词外加入自己的提示词，调用大模型，再操作本地文件、写代码或完成其他计算机任务。

#### 原回答分析

- 回答了“怎么使用 AI 工具”，没有回答面试官明确追问的“AI / 大模型原理”。
- “驾驭 AI”重复多次，但没有讲清 Token、上下文、概率生成、不确定性以及为何会产生幻觉。
- 可以从测试岗位需要的深度回答，不必讲完整模型训练数学。

#### 参考回答

> AI 是一个大类；我当前接触最多的是基于 Transformer 的大语言模型。输入会先被切成 Token，模型根据训练得到的参数和当前上下文，为下一个 Token 计算概率并逐步生成内容。因此它擅长语言理解和生成，但并不是事实数据库，输出具有概率性，也可能产生幻觉。
>
> RAG 是在生成前检索外部知识，把证据加入上下文；Agent 则进一步加入任务状态、工具调用和执行循环。对测试来说，这意味着不能只验证一句答案，要同时验证输入上下文、检索证据、工具轨迹、确定性业务结果和多次运行的稳定性。

## 七、这场面试的答题模板

以后遇到功能或场景题，统一使用：

> **先确认范围和期望 → 拆对象与数据特性 → 正常/异常/边界/状态/组合 → 接口、数据库和日志证据 → 按业务风险排序。**

遇到问题定位题，统一使用：

> **确认期望与复现范围 → 页面/Console → 请求参数 → 响应 → 服务日志/Trace → 数据库与缓存 → 下游依赖 → 对比定位结论。**

遇到 AI / Agent 题，统一使用：

> **业务任务 → 模型与 Prompt → RAG → 工具与状态 → 权限安全 → 稳定性/性能/成本 → Trace 与评测集。**
