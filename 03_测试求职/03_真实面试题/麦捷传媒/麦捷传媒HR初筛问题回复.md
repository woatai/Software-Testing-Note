## 使用说明

- “可直接发送版”适合通过微信回复 HR，内容尽量清楚但不过度展开。
- “面试展开版”用于技术面追问，不建议整段一次性发给 HR。
- 测试用例是根据本人实际负责过的订单、支付、退款业务重新构造的脱敏样例，不包含前公司的客户、接口、账号、订单号或生产数据。
- 不声称做过广告投放系统；回答的重点是展示现有交易业务经验如何迁移到广告和财务数据场景。

## 可直接发送版

您好，下面是我的回复：

### 1. 以前写过的测试用例

可以提供。由于原公司的完整用例包含内部业务规则和数据，我会提供一份按原工作思路重新构造、已经脱敏的订单/支付/退款测试用例样例。用例会包含模块、前置条件、操作步骤、预期结果、优先级，以及页面、接口和数据库的验证点，避免外发原公司的敏感信息。

### 2. 测试介入前后的工作顺序

测试介入前，我会先了解项目背景、用户角色、现有业务流程、历史缺陷和本次改动范围，提前准备环境、账号和基础测试数据。

正式介入后，我一般按下面的顺序开展：

1. 参加需求评审，梳理业务目标、主流程、状态、字段规则、权限、上下游接口和验收标准，把歧义、遗漏和冲突记录下来确认；
2. 做影响范围和风险分析，制定测试计划，明确测试范围、优先级、环境、数据、时间和准出标准；
3. 从正常、异常、边界、权限、状态流转、接口和数据一致性等维度设计用例，并进行评审；
4. 环境就绪后先做冒烟，再按风险执行功能、接口和数据测试，必要时通过抓包、日志和 SQL 辅助定位；
5. 提交并跟踪缺陷，修复后先验证原问题，再根据代码改动和影响范围做关联回归；
6. 上线前输出测试报告，说明已测范围、未测范围、遗留问题和上线风险；上线后验证核心链路，出现问题及时协助定位和回滚/补偿，典型问题沉淀到回归用例中。

### 3. 第三方接口数据完整性、一致性和单量差异排查

我不会只比较总金额，因为总金额相同不代表每条数据都正确。我会按以下步骤排查：

1. **先统一口径**：确认双方的时间范围、时区、订单状态、金额口径、数量单位、是否包含退款/取消单，以及数据粒度是订单还是订单明细；
2. **检查接口获取过程**：核对请求是否成功、分页是否全部拉完、总条数是否一致，检查超时重试、重复拉取、限流、漏页和字段缺失；
3. **做总量校验**：分别核对记录数、订单去重数、购买量合计和金额合计，不能只看金额一个指标；
4. **做明细校验**：以订单号为主键；如果一单多商品，则使用“订单号＋商品/明细 ID”作为联合键，找出第三方有但本地没有、本地有但第三方没有，以及两边都有但数量或金额不同的数据；
5. **分析差异原因**：重点排查重复数据、漏数、拆单/合单、赠品或零金额订单、部分退款、取消单、同步延迟、时间窗口边界和数量单位换算；
6. **修复后回归**：验证重试、补偿和幂等机制，重新核对总量与明细，并保留批次号、业务键和差异清单作为证据。

如果出现“总金额无误，但单量对不上”，我会优先找出差异订单明细，而不是根据总金额判断数据正确。比如一条 100 元订单被漏掉，同时另一条订单重复了 100 元，总金额仍然相同，但单量和明细已经错误。

以上是我的处理思路，下面也可以附一份脱敏用例样例。如果需要，我可以根据贵司广告投放或财务系统的具体口径进一步展开。

### 用例设计说明

这份样例不是简单罗列功能按钮，而是按以下风险设计：

- **正常链路**：创建订单、支付、退款；
- **边界和金额**：门槛、精度、累计退款上限；
- **幂等和并发**：重复提交、重复回调；
- **结果不确定**：客户端超时但渠道成功；
- **安全和服务端校验**：金额篡改；
- **数据一致性**：页面、接口、业务表、流水和报表共同核对。

## 第二题：面试展开版

### 测试介入前

> 如果测试能够提前介入，我会先了解业务目标和现有系统，而不是等开发提测后才开始看需求。我会阅读需求、原型、历史用例和线上缺陷，实际跑一遍旧流程，梳理角色、核心业务对象、状态机、上下游系统和关键数据；同时确认环境、账号、权限、第三方依赖和测试数据是否可准备。

### 需求评审与计划

> 评审阶段我重点检查需求是否完整、规则是否可执行和结果是否可验证。例如广告数据同步需求要明确数据来源、时间窗口、分页、唯一键、更新策略、延迟范围、失败重试和财务口径。之后根据业务影响、改动范围、历史缺陷和失败可恢复性做风险排序，形成测试范围、排期、人员依赖和准出标准。

### 用例设计与执行

> 用例从正常、异常、边界、权限、状态迁移、接口、数据一致性、兼容性和性能等维度展开。提测后先做冒烟，确保主链路可测，再按 P0、P1、P2 执行。发现问题时保存环境、账号、业务 ID、请求响应、日志时间点和 SQL 结果，让开发能够快速复现和定位。

### 缺陷、回归与上线

> 缺陷修复后先验证原问题，再根据修改点做关联回归。例如修复数据去重逻辑后，不只验证重复数据，还要回归正常新增、更新、补数、并发和报表聚合。上线前测试报告必须写明已测、未测、通过情况、遗留缺陷和风险建议；如果核心资金链路或数据口径仍不确定，我会明确不建议上线，而不是只写“测试通过”。

### 上线后

> 上线后验证核心链路和关键指标。如果出现线上异常，先控制影响，再根据业务 ID、批次、接口、日志和数据库定位，确认需要回滚、补偿还是人工修数。处理结束后补充根因、影响范围和预防措施，并把问题转成固定回归用例。

## 第三题：面试展开版

### 一、先确认“比较什么”

对账开始前必须确认：

- 数据粒度：一行是一笔订单、一件商品还是一次状态变更；
- 唯一键：`order_no`，或 `order_no + item_id`；
- 时间口径：创建时间、支付时间、完成时间还是第三方更新时间；
- 时间边界：是否统一时区，是否按左闭右开区间 `[start_time, end_time)`；
- 状态范围：是否包含待支付、取消、退款、赠品和测试订单；
- 金额口径：原价、应付、实付、退款后净额、是否含税或服务费；
- 数量口径：订单数、商品行数、件数或去重用户数。

### 二、检查接口获取过程

1. HTTP 状态和业务 code 是否成功；
2. `total`、`page_no`、`page_size` 和实际返回条数是否匹配；
3. 是否因为超时、限流、Token 失效导致中途停止；
4. 重试是否重复写入，是否使用稳定唯一键保证幂等；
5. 数据是否会延迟回补，更新时间窗口是否存在边界遗漏；
6. 必填字段、类型、金额精度和枚举值是否合法；
7. 是否保留拉取批次、原始响应或审计日志，便于追溯。

### 三、分层对账

1. **批次层**：请求批次、页数、接口返回总条数是否完整；
2. **汇总层**：总记录数、订单去重数、购买量合计、金额合计；
3. **明细层**：按唯一键检查缺失、冗余和字段差异；
4. **业务层**：状态变化、退款冲正、拆单/合单和报表口径是否合理。

### 四、总金额正确但单量不一致的典型原因

- 一笔相同金额的数据漏了，另一笔相同金额的数据重复了；
- 赠品或零金额订单会影响单量，但不影响总金额；
- 第三方按订单返回，本地按订单明细统计，或反过来；
- 一笔订单被拆成多条商品明细，或多笔业务单被合并结算；
- 取消单、退款单、测试单的过滤条件不同；
- 分页最后一页漏拉，重试又重复写入其他页；
- 同一时间边界在两边分别使用 `<=` 和 `<`，导致重复或遗漏；
- 购买量单位不同，例如“箱”和“件”未换算；
- 数据仍在延迟窗口内，本地与第三方快照时间不一致。

### 五、示例 SQL

以下表名和字段均为示例，实际以公司数据结构为准。

#### 1. 检查第三方批次的汇总指标

```sql
select
    count(*) as row_count,
    count(distinct order_no) as order_count,
    sum(quantity) as total_quantity,
    sum(amount) as total_amount
from third_party_order_detail
where batch_id = 'BATCH_001';
```

#### 2. 查找第三方重复的业务明细

```sql
select
    order_no,
    item_id,
    count(*) as duplicate_count
from third_party_order_detail
where batch_id = 'BATCH_001'
group by order_no, item_id
having count(*) > 1;
```

#### 3. 查找第三方有、本地没有的数据

```sql
select
    t.order_no,
    t.item_id,
    t.quantity,
    t.amount
from third_party_order_detail t
left join local_order_detail l
    on l.order_no = t.order_no
   and l.item_id = t.item_id
where t.batch_id = 'BATCH_001'
  and l.order_no is null;
```

#### 4. 查找本地有、第三方没有的数据

```sql
select
    l.order_no,
    l.item_id,
    l.quantity,
    l.amount
from local_order_detail l
left join third_party_order_detail t
    on t.order_no = l.order_no
   and t.item_id = l.item_id
   and t.batch_id = 'BATCH_001'
where l.biz_date = '2026-10-19'
  and t.order_no is null;
```

#### 5. 查找两边都有但数量或金额不一致的数据

```sql
select
    t.order_no,
    t.item_id,
    t.quantity as third_quantity,
    l.quantity as local_quantity,
    t.amount as third_amount,
    l.amount as local_amount
from third_party_order_detail t
inner join local_order_detail l
    on l.order_no = t.order_no
   and l.item_id = t.item_id
where t.batch_id = 'BATCH_001'
  and (
      t.quantity <> l.quantity
      or abs(t.amount - l.amount) >= 0.01
  );
```

#### 6. 先按订单聚合，再检查拆单/明细差异

```sql
select
    t.order_no,
    t.total_quantity as third_quantity,
    l.total_quantity as local_quantity,
    t.total_amount as third_amount,
    l.total_amount as local_amount
from (
    select
        order_no,
        sum(quantity) as total_quantity,
        sum(amount) as total_amount
    from third_party_order_detail
    where batch_id = 'BATCH_001'
    group by order_no
) t
inner join (
    select
        order_no,
        sum(quantity) as total_quantity,
        sum(amount) as total_amount
    from local_order_detail
    where biz_date = '2026-10-19'
    group by order_no
) l on l.order_no = t.order_no
where t.total_quantity <> l.total_quantity
   or abs(t.total_amount - l.total_amount) >= 0.01;
```

### 六、修复与回归标准

- 原差异批次经过补数、去重或规则修复后，总量和明细均一致；
- 同一批次重复执行不会产生重复数据；
- 中途失败后可以从安全位置续传或重新执行；
- 延迟到达的数据能够被补偿任务覆盖；
- 报表、财务汇总和业务明细口径一致；
- 日志能通过批次号、订单号和第三方流水号追溯全过程。

## HR 可能继续追问

### 为什么不能只比较 MD5 或总金额？

> MD5 或汇总指标适合快速发现“可能有差异”，但不能直接告诉我差异发生在哪一条、为什么发生。总金额相同还可能存在漏一条又重复一条的抵消情况，所以最终仍要使用业务唯一键进行明细比对。

### 数据量非常大，不能全表直接 JOIN 怎么办？

> 先按日期、账户、平台或批次分区，再比较每个分区的数量、金额和校验值，快速定位异常分区；之后只对异常分区做明细 JOIN。查询时确保唯一键、时间字段和关联字段有合适索引，避免在生产高峰直接执行大范围重查询。

### 第三方数据会延迟，怎样判断是真漏数还是未到达？

> 先确认第三方承诺的延迟窗口和数据最终更新时间，在窗口内标记为“待收敛”，窗口结束后再做最终对账。同时设计补偿拉取、延迟监控和告警，不能一发现短时差异就直接判定丢数。

### 如果没有权限直接查数据库怎么办？

> 可以通过内部查询接口、数据平台、审计报表或由有权限人员协助导出脱敏结果完成校验。测试重点是建立可追溯证据，不应该为了查数据绕过权限控制。
