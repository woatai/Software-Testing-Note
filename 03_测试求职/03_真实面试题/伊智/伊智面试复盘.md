# 伊智面试复盘

来源：[[规划纵一路.转写.简体|规划纵一路面试转写]]

## 一、结论先看

这场面试是一场非常典型的“有相关意识，但没有形成可验证的工程方法”型面试。

你不是完全不会。你能说出 Codex、Skill、Agent、RAG、裁判模型、人工审核、重试上限、Playwright 元素定位，也能从真实项目里想到多支付、退款、优惠券、分佣和金额篡改。问题是，这些点大多以“临场想到一个说一个”的方式出现，没有转化为数据集、指标、流程、存储结构、版本、追溯、质量门禁和人工介入点。

面试官的直接评价是：

- AI 和 Agent 测试有一些实践，但“不够深，也不够广”。
- 对 RAG 召回、智能体评测集、批量裁判和多轮测试缺少完整理解。
- 功能测试能想到一些容易遗漏的点，但用例设计缺少稳定框架。

### 通过率估计

基于录音内容，我估计这场技术面的通过率约为 **30% - 40%**，中位判断约 **35%**。

正向信号：

- 面试持续了约 1 小时 42 分，对方愿意深挖且给出大量具体方法。
- 你的业务项目、支付经验、UI 自动化和 AI 使用与岗位有关联。
- 面试官在结尾仍询问了期望薪资。

风险信号：

- 面试官不只是追问，而是用后半场详细讲解团队正在使用的方法，说明你当场没能独立给出他期望的方案。
- 核心要求正是 AI 智能体测试和工程化，而这两块被明确评价为深度、广度不足。
- 你的开场和支付答题过长、反复，会弱化“能独立推动复杂测试”的信心。

这只是录音推断，最终结果仍取决于同批候选人、团队对潜力的权重和薪资匹配。

## 二、你做得好的地方

### 1. 项目经历有真实业务感

你能讲出生活服务平台的：

- 用户端、服务人员端、门店端和管理后台。
- 下单、支付、退款、结算、分佣和状态流转。
- 页面、接口、后台和数据库的多端一致性。

这些内容与伊智美业 SaaS 的门店、会员、收银、分销和售后是可迁移的。

对应录音：`00:00:34 - 00:03:18`

### 2. AI 并不是只停留在“会聊天”

你能描述：

- 用 Codex 根据业务规则和用例规则生成用例。
- 用 AGENTS.md / Skill 约束代码生成。
- 先人工跑通小流程，再扩大自动化。
- 设置重试上限和人工介入。
- 用第二个模型做评审，并要求输出分数。

这些点说明你已有规则化、人在回路和多 Agent 意识，并非纯概念背诵。

对应录音：`00:04:23 - 00:06:57`、`00:28:54 - 00:30:54`、`00:39:19 - 00:45:44`

### 3. 支付业务细节实际上不差

你后续想到了不少有价值的场景：

- 一次性和订阅性商品。
- 多支付渠道和新增渠道后的全量回归。
- 0 元、0.01 元、组合支付、加钟、转单、分佣。
- 退款原路退回、优惠券返还和完成后退款的分佣规则。
- 通过抓包篡改金额，检查服务端校验。

这证明你有真实业务积累。你的主要问题不是“没点可说”，而是没有用框架将它们快速组织出来。

对应录音：`00:45:52 - 00:58:37`

### 4. 遇到不确定的问题时愿意确认和思考

你会请面试官复述问题，也会核对自己对“迭代”的理解。这比完全编答案好。但确认后必须先用一句话给出结论，否则会显得一直在试探。

## 三、主要失分点

### 1. 自我介绍严重超时

开场从 `00:00:00` 持续到约 `00:07:43`。内容先后展开了生活服务、接口自动化、支付 UI 自动化、AI 生成用例、AI 生成脚本、效率数据和公司匹配。

这会带来三个风险：

- 面试官不知道你最核心的能力是什么。
- 你主动抛出大量 AI 工程化概念，立刻把追问难度拉到了自己还未落地的层级。
- “6 秒 25 条、5 分钟一条脚本”等数据没有说测量方式和质量基准，容易被质疑。

改进：开场只说 60–90 秒，AI 细节等对方追问再讲。

### 2. 把“学过/打算做”和“已落地”混在一起

在知识库和智能体问题上，你多次说“正在开始搭”、“打算做”、“还没有落地实践”，但前面的表达又容易让人以为你已经具备 Agent/RAG 工程经验。

改进口径：

> 我已经做过 A 和 B；C 目前是学习项目；D 还没有真实生产经验。如果让我落地 D，我会按以下步骤做。

这样既诚实，又能展示迁移能力。

### 3. 评测集来源回答偏离真实业务

你首先想到从网上找大型客服数据集，或直接让 AI 生成 500 条。这类数据无法作为伊智美业客服的主评测集，因为它不包含某家商家的品牌事实、服务规则、会员政策和 SOP。

正确顺序应为：

1. 商家真实脱敏对话、FAQ、SOP 和知识库。
2. 历史失败、用户投诉和线上低分样本。
3. AI 扩充同义句、人格、情绪、错别字、安全与无答案问题。
4. 业务和客服审核，形成版本化 gold set。

对应录音：`00:10:25 - 00:15:55`、`01:01:45 - 01:04:08`

### 4. 不会用指标回答 RAG 召回评测

被问“怎样测试知识库召回正确率”时，你主要说了向量相似度和从输出报告定位，没有建立标注数据，也没有 Recall@K、Precision@K、MRR/nDCG、faithfulness 等可比较指标。

下次固定按两层答：

- 检索层：应命中什么片段，实际 Top-K 命中了什么，指标是什么。
- 生成层：答案是否忠于证据、相关、完整、引用正确和合理拒答。

对应录音：`00:17:43 - 00:20:14`

### 5. 裁判模型的回答是“模型审模型”，缺少校准闭环

你想到让另一个模型评分，方向是对的，但没有回答“怎样确保裁判模型自己判对”。“让它输出思路”只能增强可审核性，不能自动证明结论正确。

需要补全：

- 明确 rubric 和正反例。
- 人工标注 gold set。
- 裁判与人工的一致性和争议样本复审。
- 必查低分、临界分、高风险，同时抽样高分防止假阳性。
- 固定模型、Prompt、参数和版本，保证可重现。

### 6. 多轮 Agent 测试仍停留在手工聊天层面

你先按固定节点、手工与智能体对话来回答。面试官指出，这更像开发调试，不是可重复、可规模化的测试。

目标方案是：

- 用户模拟 Agent 根据人格、场景、目标和探索任务动态回答。
- 同一场景保持在同一 session/context 中。
- guard/evaluator 每轮检查是否跑偏、越界或达成结束条件。
- judge 最后根据整段 trajectory 和业务目标评分，输出理由。

对应录音：`01:06:11 - 01:19:00`

### 7. AI 生成用例还是“文件 + 提示词 + 覆盖”，工程闭环不足

原方案主要是：把需求和用例存在本地目录，需求变更后让 Codex 找到用例、修改并覆盖。它在规模变大后有明显风险：

- 无法证明哪些模块被完整召回。
- 需求、规则、用例和缺陷之间没有 ID 和追溯关系。
- 覆盖会丢失历史版本，无法回滚和说明修改原因。
- AI 自评无法保证业务真实性。
- 直接审 200 条用例没有真正减少人工工作量。

面试官给出的核心改进是：先生成并人工审“数量较少的业务规则与影响范围”，再用审核过的规则生成用例；规则带来源和版本，迭代后将旧规则标记失效，而不是无痕覆盖。

对应录音：`00:22:16 - 00:30:54`、`01:21:49 - 01:29:52`

### 8. UI 自动化答成了“定位方式枚举”，没有回答系统设计

面试官问的不是 CSS、文本、XPath 谁作备选，而是：如何设计一个工程，让 AI 从自然语言用例稳定生成可执行脚本。

你后续补了重试上限、人工介入、Skill 沉淀和多 Agent 评审，但仍缺少：

- DOM/accessibility tree 的结构化页面建模。
- 与开发建立 `data-testid` 契约。
- Page Object/元素库的复用与版本。
- 每步执行后的页面状态校验。
- 人工确认的 locator 如何受审核入库。
- 首次成功率、介入率、flaky 率等评价指标。

对应录音：`00:31:11 - 00:45:44`

### 9. 支付测试答得散，而且没有先确认范围

面试官说“列一下支付测试点”，你却先展开了一次性商品、订阅商品和自动化项目，后续反复用“还有”追加。最后虽然有不少好点，但给人的感受是没有用例设计方法论。

改进方法：

> 先确认只问支付节点，还是完整下单链路。若只问支付，就按“对象—渠道—金额—主流程—异常—幂等并发—安全—退款闭环—订阅”直接列。

对应录音：`00:45:52 - 00:58:37`、`01:33:26 - 01:41:29`

### 10. 表达中太多重复、停顿和弱结论

高频表现是：

- “我再想一想”后沉默较久。
- 先说一个方向，又用多个“还有”反复追加。
- 概念混用，例如脚本、Prompt、Skill、Agent、RAG 和数据库之间的边界不稳定。
- 先说自己怎么操作，没有先回答“我的方案是什么”。

固定答题结构：

> 结论一句话 → 3–5 个步骤 → 一个伊智业务例子 → 指标/验收标准。

## 四、面试官真正在考什么

| 表面问题 | 真正考察 | 你当场表现 |
| --- | --- | --- |
| 怎样测美容院客服智能体 | 能否从手工问答上升到批量评测体系 | 主要讲人工输入输出 |
| 500 条数据怎么来 | 是否知道私有业务评测集的数据源和标注 | 首先想到公开数据集和 AI 生成 |
| 怎样判答案 | 是否理解确定性断言、LLM-as-a-Judge 和人工校准 | 想到裁判 Agent，但无 gold set 和一致性验证 |

| 多轮对话怎么测 | 能否处理模型不确定性和 trajectory 评估 | 停留在固定对话和手工调试 |
| AI 怎样持续生成用例 | 是否有版本化、来源、影响分析和审批门禁 | 有目录和人工审核，但缺追溯、版本和质量门禁 |
| AI 怎样生成 UI 脚本 | 能否将 Agent 探索变成稳定工程 | 有重试与人工介入，但页面模型和状态校验不足 |
| 支付测试点 | 是否有可重用的用例设计方法 | 有业务点，无稳定框架 |

## 五、对这个岗位的重新定位

这不是“传统功能测试，AI 是加分项”的岗位。从面试内容看，更像：

> 美业 SaaS 功能测试 + 商家问题闭环 + AI 智能体评测 + AI 生成用例/UI 脚本的工程化实践。

因此下次不能只准备“会用 Codex”，而要能讲清：

- 评测数据从哪来，怎样标注和版本化。
- 怎样批量执行，记录哪些 Trace 和指标。
- 确定性规则、LLM 裁判和人工审核如何分工。
- RAG 检索、回答生成和 Agent 工具调用如何分层定位。
- 不确定的 AI 输出如何通过固定数据集、统计指标、抽样和高风险门禁管理。
- 用例、业务规则和自动化资产怎样可追溯、可审计、可回滚。

## 六、下一步最应该补的四件事

### 第一优先级：做出一个可演示的 AI 客服评测最小项目

最少包含：

- 30–50 条有来源、标准要点和风险等级的评测用例。
- Python 批量调用与 JSONL/CSV 结果。
- 确定性断言 + LLM-as-a-Judge + 人工抽样。
- 可见的通过率、分类得分、低分样本、延迟和版本对比。

面试时能展示输入、代码、报告和一个真实失败定位，说服力会远高于口述概念。

### 第二优先级：补 RAG 评测指标和定位链路

要能不思考地讲出：

> 文档解析 → 切片 → Embedding → 检索 → 重排 → 上下文 → 生成 → 引用。

对应指标至少熟悉：Recall@K、Precision@K、MRR/nDCG、faithfulness、answer relevancy、context precision/recall、拒答准确性和延迟。

### 第三优先级：将 AI 生成用例做成可追溯流程

不要只存 Markdown 文件并覆盖。至少要有：

- 需求 ID、规则 ID、用例 ID 和来源片段。
- 依赖模块与状态流转。
- 新增/修改/删除 diff。
- 业务规则审核门禁。
- 用例机器预检、人工审核和版本化入库。
- 历史版本、废弃标记、审批人和回滚。

### 第四优先级：把功能测试答题固定成框架

对任何流程题，统一用：

> 确认范围 → 画正向链路 → 按节点拆输入/规则/状态/输出 → 扩展异常、边界、权限、并发、安全和数据一致性 → 从终点逆向检查取消、退款、补偿和资产闭环。

## 七、下次面试的三条底线

1. 自我介绍不超过 90 秒，不主动展开没有落地的高阶方案。
2. 每道题先说结论和框架，不用“还有”无限追加。
3. 任何 AI 效果都要用“数据集 + 指标 + 版本 + 人工校准 + 高风险门禁”回答，不只说提示词和另一个 Agent。

## 八、最终判断

这场面试暴露的不是“你不适合 AI 测试”，而是你的 AI 能力目前更接近“会用工具提效、有工程意识的功能/自动化测试”，还没有到“能独立设计智能体评测体系”。

好消息是，面试官几乎已经在录音后半段把团队的目标方法讲出来了。如果你将其中一条做成可运行的小项目，并能用真实数据回答“怎么测、怎么判、怎么证明比之前好”，下一次同类岗位的通过率会有明显提升。
