# 广加技术负责人高频追问

## 这份笔记怎么用

这份笔记用于准备“测试团队暂时只有一个人”的技术负责人面试。技术负责人通常不会只问工具会不会用，而是会重点判断：

- 你能不能独立把测试流程跑起来。
- 你能不能理解本地生活 / 即时配送业务。
- 你能不能通过接口、抓包、SQL、日志辅助定位问题。
- 你能不能在时间紧、资源少的情况下抓住主流程和风险。
- 你能不能沉淀测试用例、回归清单、上线 checklist 和自动化候选场景。

回答时建议统一用：

> 先说思路，再说具体做法，最后结合配送 / 下单 / 支付 / 状态流转补一句。

## 技术负责人真正想看什么

如果这个岗位只招一个测试，技术负责人更关心的是你能不能独立负责，而不是只会执行别人安排的用例。

重点能力：

- 独立分析需求、拆测试点、设计用例。
- 主流程和高风险场景优先。
- 能通过抓包判断前端 / 后端 / 数据问题。
- 能用 SQL 辅助校验订单、支付、配送状态。
- 能推动 Bug 修复和回归闭环。
- 能把线上问题沉淀到回归清单。
- 知道哪些场景适合自动化，哪些暂时不适合。

## 高频追问 12 题

### 1. 你先介绍一下自己。

思路：

> 先讲背景，再讲测试能力，再讲项目，再贴广加业务，不要一开始讲太多自动化。

答案：

> 面试官您好，我叫梁家泰，有 1 年左右的软件测试经验，主要做功能测试、接口测试和部分接口自动化测试。
>
> 我之前主要参与生活服务类和电商类项目测试，比较熟悉下单、支付、退款、订单状态流转、后台管理、多端数据一致性这些业务场景。测试过程中，我会根据需求和原型梳理测试点，编写和执行测试用例，提交 Bug，并跟进修复和回归。
>
> 工具方面，我会使用 Postman / Apifox 做接口测试，使用 Fiddler 或浏览器 Network 抓包定位前后端问题，也会用 SQL 辅助校验订单、支付、状态等数据。自动化方面，我用 Python + pytest + requests + YAML 搭过接口自动化练习框架，主要覆盖登录、商品、下单、订单查询这些接口链路。
>
> 我了解到贵公司业务和本地生活、海外配送、电商服务相关，像 Flash Delivery 这种产品会涉及用户、商家、骑手、后台多端协同，也会涉及下单、支付、配送状态和数据一致性。我觉得这些和我之前准备的生活服务、电商测试经验比较贴近，所以希望有机会在这类业务方向继续发展。

### 2. 你做过哪些项目？主要负责什么？

思路：

> 重点讲生活服务 / 电商项目，突出自己做了测试点、用例、执行、Bug、接口、数据校验和回归。

答案：

> 我主要做过生活服务综合平台和电商类接口自动化练习项目。
>
> 生活服务平台这边，业务上涉及用户下单、服务人员接单、订单状态流转、支付、退款、结算、会员等模块。我主要负责根据需求文档和原型梳理测试点，编写和执行测试用例，提交 Bug，并跟进修复和回归。
>
> 测试时我会先跑通主流程，再覆盖异常流程和边界场景。比如下单流程，我会关注未登录、地址缺失、库存或服务不可用、重复提交、弱网、支付失败、退款状态异常等情况。对于核心数据，我会结合接口返回、后台页面和 SQL 查询确认订单、金额、状态是否一致。
>
> 接口自动化项目主要是自己练习，用 Python、pytest、requests、YAML 做接口用例组织，覆盖登录、商品、购物车、下单、订单查询等链路，用来理解请求封装、参数依赖、断言和报告。

### 3. 如果只有你一个测试，你怎么开展工作？

思路：

> 他想看你能不能独立把测试流程撑起来。按短期、中期、长期答。

答案：

> 如果只有我一个测试，我会先把测试流程跑顺，优先保证核心业务质量。
>
> 短期我会先熟悉业务、系统角色、核心流程和测试环境，重点跑通主流程，比如用户下单、支付、订单状态、后台处理、配送状态流转。拿到需求后，我会先拆测试点，按风险优先级设计用例，优先覆盖主流程和高风险场景。
>
> 中期我会沉淀测试用例、Bug 记录、上线 checklist 和回归清单。比如每次上线前固定检查登录、下单、支付、状态流转、后台查询、通知和核心接口。
>
> 长期我会把稳定、高频、每次都要回归的接口或流程逐步沉淀成接口自动化脚本，提高回归效率。只有一个测试时，我觉得最重要的是把风险透明化，及时同步已测范围、未测范围和遗留风险。

### 4. 拿到一个配送下单需求，你怎么设计测试点？

思路：

> 按角色 + 流程 + 状态 + 金额 + 异常 + 数据一致性答。

答案：

> 我会从用户端、商家端、骑手端、后台四个角色拆测试点。
>
> 用户端重点测选择商品或服务、填写地址、配送范围、配送费、优惠券、提交订单、支付、取消订单、查看配送状态。商家端或后台重点测接单、拒单、备货、出货、订单查询和异常处理。骑手端重点测接单、取货、配送中、送达、异常上报。
>
> 状态流转上，会覆盖待支付、待接单、待取货、配送中、已送达、已取消、退款中等状态。每个状态下，不同角色能看到的信息和能操作的按钮应该不同。
>
> 异常场景会测未登录、地址为空、超出配送范围、商品不可用、重复提交、弱网、支付失败、商家拒单、骑手取消、配送超时、退款。
>
> 数据一致性方面，我会对比用户端、商家端、骑手端、后台和数据库，确认订单状态、支付状态、配送状态、金额、配送费和优惠金额一致。

### 5. 支付成功但订单状态没更新，你怎么排查？

思路：

> 按支付平台、订单状态、支付回调、日志、数据库、前端缓存来排查。

答案：

> 我会先确认用户是否真的支付成功，比如支付截图、支付流水号、支付时间和支付方式。
>
> 然后看用户端订单详情接口和后台订单状态。如果支付平台显示成功，但订单还是待支付，我会重点查支付回调有没有到达业务系统，回调参数是否正确，订单号是否匹配，签名校验是否通过。
>
> 数据库层面会查订单表、支付流水表、回调记录表，确认支付流水是否生成，订单状态是否更新。如果数据库状态已经更新但页面没变，可能是前端缓存、接口返回或页面刷新问题；如果数据库也没更新，可能是回调失败、后端状态更新失败或数据库写入失败。
>
> 修复后我会回归正常支付、支付失败、支付取消、重复支付、回调延迟这些相关场景。

### 6. 页面提示失败，你怎么判断前端还是后端？

思路：

> 按请求参数、接口响应、页面展示、数据库 / 后台数据判断。

答案：

> 我会先通过浏览器 Network、Fiddler 或 Charles 抓包，看前端实际有没有发请求。
>
> 如果没有发请求，可能是前端校验、按钮事件或页面脚本问题。如果有请求，就看请求参数是否正确，比如地址 ID、商品 ID、支付方式、token 是否完整。
>
> 如果请求参数错误，比如字段缺失、格式不对、金额传错，那更偏前端问题。如果请求参数正确，但接口返回业务失败、数据错误或服务器异常，那更偏后端问题。
>
> 如果接口返回成功，但页面仍然提示失败，可能是前端字段映射、状态判断、缓存或页面渲染问题。核心业务我还会结合后台和数据库确认数据是否真的变化。

### 7. 你抓包主要看什么？

思路：

> 按请求和响应两部分讲，再结合订单业务。

答案：

> 抓包时我主要看请求 URL、请求方法、请求头、请求参数、响应状态码、响应体和接口耗时。
>
> 请求部分重点看前端有没有发请求，URL 是否正确，请求方式是 GET 还是 POST，token 或 Cookie 有没有带上，参数是否完整。比如下单时用户、商品、地址、配送费、优惠券、支付方式是否正确。
>
> 响应部分重点看 HTTP 状态码、业务 code、message、data。如果接口返回失败，就根据错误信息判断是参数、权限、业务规则还是后端异常。如果接口返回成功但页面显示失败，就要看前端对响应字段的判断逻辑。
>
> 对订单、支付、配送状态这类核心场景，我还会结合后台和数据库确认数据是否真的更新。

### 8. 你会用 SQL 查哪些数据？

思路：

> 讲订单、支付、退款、用户、配送状态，重点是辅助验证和定位。

答案：

> 我主要会用 SQL 辅助验证核心业务数据，比如订单、支付、退款、配送状态、用户信息这些。
>
> 比如下单后，我会查订单表确认订单是否生成，订单状态、金额、用户 ID、地址 ID 是否正确。支付后会查支付流水表，确认支付状态、支付金额、第三方流水号是否正确。退款时会查退款记录，确认退款状态和金额。配送场景下会查配送单或订单状态，确认骑手接单、取货、配送中、已送达这些状态是否更新。
>
> SQL 对测试来说主要是辅助判断页面、接口和数据库是否一致，也能帮助定位问题是在前端展示、后端接口还是数据层。

### 9. 如果明天上线但今天才提测，你怎么安排？

思路：

> 讲风险优先，不要说“全部测完”。重点是主流程、冒烟、风险同步。

答案：

> 如果时间很紧，我会先确认上线范围、影响模块和改动点，和产品开发确认哪些功能是必须上线的核心功能。
>
> 测试执行上，我会优先测主流程和高风险场景，比如登录、下单、支付、订单状态流转、后台处理、配送状态、退款或取消这些核心链路。其次测改动点相关的异常场景，比如重复提交、弱网、接口失败、权限校验。
>
> 如果来不及写完整用例，我会先用 checklist 做冒烟和核心回归，同时记录未覆盖的低优先级场景和风险点，并及时同步给负责人。上线前会明确告诉团队：已测哪些、未测哪些、还存在什么风险，而不是默认全部没问题。

### 10. 你怎么沉淀测试用例和回归清单？

思路：

> 讲模块化、历史 Bug、线上问题、上线 checklist、自动化候选。

答案：

> 我会按模块沉淀测试用例，比如用户端、商家端、骑手端、后台管理、订单、支付、配送、退款等模块。
>
> 每次新需求测试完，我会把新增功能的核心用例、异常场景、发现过的 Bug 补充到用例库里。线上问题或历史高频问题也会加入回归清单，避免下次重复漏测。
>
> 上线 checklist 会单独维护，包含登录、下单、支付、订单状态、后台查询、通知、核心接口、兼容性这些必测项。
>
> 对稳定、高频、每次都要回归的接口，比如登录、创建订单、订单查询、状态更新，可以作为接口自动化候选，后续逐步用脚本提高回归效率。

### 11. 你会自动化吗？哪些适合自动化？

思路：

> 先说明自己有接口自动化基础，再说适合自动化的场景，最后说不适合的场景。

答案：

> 我有接口自动化的学习和练习经验，主要用 Python + pytest + requests + YAML 做过接口自动化练习框架，覆盖登录、商品、购物车、下单、订单查询这些接口链路。
>
> 我认为适合自动化的场景一般是流程稳定、重复执行频率高、回归价值高的功能。比如登录、创建订单、查询订单、支付后状态查询、后台核心配置、配送状态查询这些接口，如果每次发布都要回归，就适合逐步沉淀成自动化。
>
> 但需求变化频繁、页面元素不稳定、只测一次的功能，不一定适合马上自动化，否则维护成本会比较高。我的理解是先把手工测试和业务流程跑稳，再把高频稳定场景逐步自动化。

### 12. 你能接受测试团队暂时只有你一个人吗？

思路：

> 回答可以接受，但要强调风险透明、流程沉淀、主动沟通，不要说自己一个人能扛所有。

答案：

> 我可以接受测试团队暂时只有我一个人，但我会比较重视流程和风险同步。
>
> 如果只有一个测试，我会优先保证核心功能和高风险场景，比如下单、支付、订单状态、配送状态、后台处理这些主链路。测试过程中我会把已测范围、未测范围、阻塞问题和遗留风险及时同步给技术负责人或产品，避免风险不透明。
>
> 同时我会逐步沉淀测试用例、回归清单、上线 checklist、常见问题定位方式。这样即使前期只有一个测试，也能让测试工作有记录、可复用、可追踪。
>
> 当然，我也会主动和开发、产品配合，在需求评审阶段提前识别风险，而不是等到最后才发现问题。

## 最后速背

> 如果只有我一个测试，我会先保证主流程和高风险功能测到位，再把测试用例、Bug、上线 checklist 和回归清单沉淀下来。短期保证上线质量，中期建立测试规范，长期把稳定高频的接口逐步自动化，提高回归效率。
>
> 技术负责人真正想听的不是“我会工具”，而是我能独立分析需求、设计测试点、定位问题、推动修复、同步风险，并把经验沉淀成后续可复用的测试资产。
