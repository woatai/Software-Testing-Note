## 笔试预测：最像真实笔试的 6 道题

### 1. 请为菲快送外卖下单功能设计测试点。

答题要点：

> 我会从用户、商家、骑手、后台四个角色拆。用户端重点测选店、选菜、规格数量、购物车、地址、配送费、优惠券、支付、订单状态；商家端重点测接单、拒单、备餐、出餐；骑手端重点测接单、取餐、配送、送达；后台重点测订单查询、状态流转、金额、支付流水和售后处理。
>
> 状态流转上，会覆盖待支付、待接单、备餐中、待取餐、配送中、已完成、已取消、退款中。每个状态下，不同角色能看到的信息和能操作的按钮应该不同。
>
> 异常场景会覆盖未登录、地址为空、超出配送范围、商家拒单、骑手取消、支付失败、重复支付、弱网重复提交、订单取消和退款。
>
> 数据一致性上，我会对比用户端、商家端、骑手端、后台和数据库，确认订单状态、支付状态、配送状态、订单金额和优惠金额一致。

### 2. 支付成功但订单仍显示待支付，怎么排查？

答题要点：

> 我会先收集用户账号、订单号、支付截图、支付时间和支付方式，确认第三方平台是否真的扣款成功。
>
> 然后看用户端订单详情接口和后台订单状态。如果支付流水成功但订单还是待支付，就继续查支付回调是否到达业务系统，订单号是否匹配，签名校验是否通过，后端日志是否报错。
>
> 数据库层面会查订单表、支付流水表和回调记录，确认是前端展示缓存问题、支付回调失败、后端状态更新失败，还是数据库更新失败。
>
> 修复后要回归同支付方式主流程，也要补测支付取消、支付失败、重复支付和回调延迟这些相关场景。

### 3. 接口返回 200，但页面提示失败，怎么定位？

答题要点：

> 我会先区分 HTTP 200 和业务成功。HTTP 200 只能说明请求成功到达服务端，不代表业务一定成功。
>
> 接着看响应体里的业务 code、message、data。如果业务 code 是失败，就检查请求参数、token、用户权限、业务状态是否符合规则。
>
> 如果接口业务成功但页面仍提示失败，就重点看前端字段映射、状态判断、缓存、页面渲染逻辑或接口返回字段是否和前端约定不一致。
>
> 对订单、支付、退款这类核心功能，我还会结合后台或数据库确认数据是否真正更新。

### 4. 写 SQL 查询已支付但未完成的订单。

答题要点：

```sql
select
    order_no,
    user_id,
    status,
    pay_status,
    amount,
    created_at
from orders
where pay_status = 'PAID'
  and status <> 'FINISHED'
order by created_at desc;
```

> 如果实际项目里的状态值不是 `PAID`、`FINISHED`，要以数据库字典或接口文档为准。面试时可以补一句：真实项目里我会先确认表结构、字段含义和状态枚举，避免查错字段。

### 5. 线上用户反馈下单失败，你怎么通过 Linux 日志定位？

答题要点：

```shell
tail -f app.log
grep "ERROR" app.log
grep "orderNo=xxx" app.log
grep "userId=xxx" app.log
ps -ef | grep java
df -h
```

> 我会先收集用户账号、操作时间、订单号、截图、设备和操作路径。然后按时间点、用户 ID、订单号去过滤日志，看下单接口是否报错、请求参数是否异常、支付或库存服务是否异常。
>
> 如果日志里有错误堆栈或第三方接口异常，我会把时间点、接口、请求参数、响应信息和订单号整理给开发。与此同时，也会结合后台和数据库确认订单是否已经生成，避免页面提示失败但后台实际生成订单。

### 6. APP / H5 / 小程序支付测试重点是什么？

答题要点：

> 支付测试我会重点覆盖支付唤起、取消支付、支付失败、支付成功返回、支付回调、订单状态同步、金额一致性和重复支付。
>
> 小程序和 H5 还要关注微信 / 支付宝容器里的授权、缓存、返回路径、页面刷新和弱网情况。比如支付成功后返回小程序，订单状态是否及时从待支付变为已支付。
>
> APP 还要关注系统兼容、后台切前台、网络切换、支付中断、重复点击支付按钮，以及不同机型上支付 SDK 唤起是否正常。
>
> 对多支付方式，比如微信、支付宝、银联、货到付款、GCash，我会分别验证正常支付、异常支付、支付流水、后台订单、数据库状态和退款链路。

### 3. 你怎么理解广加科技这种本地生活 / 海外配送业务的测试工作？

思路：

答案：

> 我理解这类业务的测试，不只是验证按钮能不能点，而是要保障用户、商家、骑手或配送团队、运营后台之间的数据流转稳定。
>
> 比如用户下单后，订单是否能正确生成，商家或后台是否能看到订单，配送状态是否正确更新，费用和距离计算是否准确，用户端、后台和配送端展示是否一致。对于海外业务，还要额外关注多语言、时区、地址格式、电话格式、币种、地图定位、移动端兼容和网络波动。
>
> 所以我会把测试重点放在功能流程、接口数据、状态流转、异常处理、性能稳定性和多端一致性上。

## 2. JD 匹配度与测试流程

### 1. 拿到一个新需求后，你会怎么开展测试工作？

思路：

> 按测试闭环答：需求分析、测试计划、测试点、用例、数据、执行、缺陷、回归、总结。

答案：

> 我会先阅读需求文档、原型和接口说明，理解业务目标、用户角色、核心流程、边界规则和上线范围。
>
> 然后根据功能模块和风险点制定测试计划，拆分测试范围、测试重点、测试数据和执行优先级。接着从正常流程、异常流程、输入校验、权限、状态流转、接口、数据一致性、兼容性、性能等角度设计测试用例。
>
> 执行阶段我会优先测主流程和高风险场景，发现问题后提交 Bug，写清楚环境、步骤、实际结果、预期结果、截图或抓包信息。开发修复后我会先回归原问题，再验证相关影响范围，最后根据测试结果输出测试汇总和风险说明。

### 2. 岗位写要遵循公司技术标准、测试规范、文档规范，你怎么理解？

思路：

> 讲流程意识，不要只说听安排。

答案：

> 我理解测试规范主要是为了保证测试过程可追溯、结果可复用、问题能闭环。比如用例要按统一模板写清楚前置条件、步骤、预期结果和优先级；Bug 单要有环境、复现步骤、截图、接口请求或日志信息；测试报告要说明测试范围、通过情况、遗留风险和上线建议。
>
> 如果公司已有测试规范，我会先按团队标准执行；如果发现一些高频问题没有沉淀，我也会整理成测试 checklist 或操作手册，后续回归时可以提高效率。

### 3. 你怎么制定测试计划？

思路：

> 从范围、资源、时间、风险、数据、环境、交付物讲。

答案：

> 我会先明确测试范围和不测范围，再确认测试环境、测试账号、测试数据、接口文档和上线时间。
>
> 然后按模块和风险拆优先级，比如订单、支付、配送状态、后台配置这类核心链路优先测；展示类、低频配置类可以后置。计划里还会包含用例设计时间、执行时间、Bug 回归时间、冒烟测试时间和测试总结输出。
>
> 如果时间比较紧，我会及时同步哪些场景必须测，哪些场景风险较低但还未覆盖，避免上线前风险不透明。

### 4. 你怎么设计测试数据？

思路：

> 按业务数据、边界数据、异常数据、权限数据、状态数据讲。

答案：

> 我会根据业务场景准备测试数据。比如配送或下单场景，需要准备不同用户、不同商家、不同商品或服务、不同地址、不同订单状态和不同支付状态。
>
> 正常数据用于跑通主流程，边界数据用于验证数量、金额、距离、时间、手机号、地址长度等规则，异常数据用于验证空值、格式错误、无效状态、库存不足或服务不可用。权限数据用于验证普通用户、商家、运营、管理员看到的数据是否不同。
>
> 对核心数据，我会记录测试账号、订单号、支付流水号、配送单号，方便后续通过接口、后台或数据库继续追踪。

### 5. 如果测试时间不够、用例很多，你会怎么安排优先级？

思路：

> 讲风险优先：主流程、高频功能、金额支付、配送状态、线上影响、历史 Bug。

答案：

> 我会先和产品、开发确认上线范围和核心链路，把用例按优先级拆分。优先覆盖用户下单、支付、订单状态、配送状态、后台处理、退款或取消这类主流程和高风险模块。
>
> 然后覆盖历史容易出问题的功能、金额和数据一致性场景、权限场景、接口异常场景。低频入口或纯展示类问题可以后置，但要把未测范围和风险同步出来。
>
> 如果发现阻塞问题，我会优先推动修复和回归，保证核心业务链路稳定。

## 3. 本地生活与即时配送业务场景

### 1. 如果让你测试 Flash Delivery 这种配送产品，你会从哪些方面入手？

思路：

> 按用户、商家、配送、后台、费用、状态、异常、数据一致性讲。

答案：

> 我会先拆角色和主流程。角色上可能有客户、商家或企业客户、骑手或配送人员、运营后台。主流程上是创建配送需求、分配配送人员、取货、配送中、送达、取消、异常处理和费用结算。
>
> 功能测试会关注下单入口、地址填写、联系方式、商品类型、配送时间、费用展示、订单状态、通知提醒、后台管理和数据查询。异常场景会关注地址无效、配送范围外、骑手不可用、订单取消、超时、网络中断、重复提交、状态更新失败。
>
> 另外我会重点验证多端数据一致性，比如用户端看到已送达，后台和配送端状态也应该同步；费用、距离、订单号、客户信息不能在不同端展示不一致。

### 2. 配送订单完整流程你怎么理解？

思路：

> 按创建订单、分配、取货、配送、签收、结算讲。

答案：

> 我理解配送订单一般从客户或商家创建配送需求开始，系统记录取货地址、收货地址、联系方式、商品类型、配送时间和费用信息。
>
> 订单生成后，系统或运营人员会分配骑手或配送资源。骑手接单后进入待取货、已取货、配送中、已送达等状态。完成配送后，系统会更新订单状态，并进入费用结算、评价或售后处理。
>
> 测试时我会重点看每个状态能不能按规则流转，不同角色看到的按钮和数据是否正确，异常状态比如取消、超时、拒单、配送失败能不能正确处理。

### 3. 配送状态流转怎么测？

思路：

> 正向流程、逆向限制、异常状态、多端同步。

答案：

> 我会先画出状态流转图，比如待分配、待取货、已取货、配送中、已送达、已取消、配送失败。
>
> 正向流程要验证每一步能正常流转，按钮和提示正确。逆向限制要验证已送达订单不能再取消，已取消订单不能继续配送，未接单订单不能直接变成已送达。异常状态要验证超时、拒单、无法联系用户、地址错误等情况。
>
> 最后要看多端同步，用户端、后台、配送端是否展示一致，接口返回和数据库状态是否一致。

### 4. 配送费用或距离计算异常，你会怎么测试和定位？

思路：

> 拆费用组成，再判断前端展示、接口返回、后端计算、配置数据。

答案：

> 我会先把费用组成拆开，比如基础配送费、距离费、服务费、优惠、夜间或高峰加价、特殊品类费用等。
>
> 测试时会准备不同距离、不同地址、不同服务类型和不同时间段的数据，手工核对预期费用，再对比页面展示、接口返回和后台订单金额。
>
> 如果接口返回正确但页面展示错误，可能是前端字段映射或格式化问题；如果接口返回本身就错，就要看后端费用计算规则、地图距离、价格配置或优惠规则。必要时结合数据库配置表和订单表确认。

### 5. 如果用户反馈订单已经送达，但页面还显示配送中，你怎么排查？

思路：

> 按用户信息、订单号、接口、后台、日志、数据库排查。

答案：

> 我会先收集用户账号、订单号、反馈时间、截图和设备信息。然后在后台查询订单当前状态，看系统底层是否已经更新为送达。
>
> 如果后台已经是送达但用户端还是配送中，可能是前端缓存、接口返回、消息推送或页面刷新问题。我会抓包看用户端订单详情接口返回什么状态。
>
> 如果后台也还是配送中，就要继续查配送端是否提交送达、接口是否调用成功、服务日志是否报错、数据库状态是否更新失败。这个问题要把用户端、配送端、后台、接口和数据库串起来看。

### 6. 配送类产品容易出现哪些线上问题？

思路：

> 结合业务讲，不要泛泛说 Bug。

答案：

> 配送类产品常见问题有订单状态不同步、地址定位错误、费用计算错误、重复下单、订单取消后仍被分配、骑手端状态提交失败、后台查不到订单、通知延迟、弱网下页面卡住等。
>
> 这些问题的影响比较直接，可能导致用户投诉、商家无法发货、配送效率下降或费用纠纷。所以测试时要重点覆盖主流程、异常流程、状态流转、多端一致性和弱网场景。

## 5. 网络协议 / HTTP / 抓包重点题

### 1. GET 和 POST 区别。

思路：

> 这题我会从用途、参数位置、安全性、数据长度、业务场景几个角度回答。

答案：

> GET 一般用于查询数据，比如商品列表、订单查询，参数通常放在 URL 后面。POST 一般用于提交数据，比如登录、提交订单、提交表单，参数通常放在请求体里。
>
> GET 的参数会直接显示在 URL 上，不适合放密码、token 这类敏感信息；POST 参数放在 body 里，相对更适合提交复杂数据。
>
> 从测试角度，我会关注接口文档要求的请求方式是否正确，参数位置是否正确。比如下单接口如果应该用 POST，但前端用了 GET，就可能存在参数暴露或接口不符合规范的问题。

### 2. HTTP 请求和响应包含什么。

思路：

> 这题我会按请求和响应分开说，再结合接口测试说明我重点看什么。

答案：

> HTTP 请求一般包含请求行、请求头和请求体。请求行里有请求方法、URL 和协议版本；请求头里有 Content-Type、Authorization、Cookie 等信息；请求体一般放 POST 请求的业务参数，比如登录账号密码、下单参数。
>
> HTTP 响应一般包含状态行、响应头和响应体。状态行里有状态码，比如 200、404、500；响应头里有响应类型、缓存等信息；响应体一般是后端返回的数据，比如 JSON 格式的 code、message、data。
>
> 接口测试时，我会重点看请求方式、URL、Headers、参数、状态码、业务 code、message、data，以及关键字段是否符合预期。

### 3. 常见 HTTP 状态码。

思路：

> 这题不用背太偏，重点说测试中常见的状态码，以及遇到时怎么判断问题方向。

答案：

> 200 表示请求成功；301、302 表示重定向；400 通常是请求参数错误；401 是未登录或认证失败；403 是没有权限；404 是资源不存在；500 是服务器内部错误。
>
> 测试时如果接口异常，我会先看状态码。比如 400 我会优先检查参数格式、必填字段；401、403 会检查 token、登录态和权限；404 会检查 URL 或路由；500 会结合响应信息和服务端日志让开发排查。
>
> 但要注意，HTTP 200 只代表请求成功到达服务端，不代表业务一定成功，还要继续看业务 code 和 message。

### 4. 抓包时主要看什么。

思路：

> 这题我会按请求和响应两部分回答，再补充怎么用于问题定位。

答案：

> 抓包时我主要看请求 URL、请求方法、请求头、请求参数、响应状态码、响应体和接口耗时。
>
> 请求部分重点看前端有没有发请求，URL 是否正确，请求方式是 GET 还是 POST，token 或 Cookie 有没有带上，参数是否完整，比如下单时用户、商品、地址、配送费、优惠券、支付方式是否正确。
>
> 响应部分重点看状态码、业务 code、message、data。如果接口返回失败，就根据错误信息判断是参数、权限、业务规则还是后端异常。如果接口返回成功但页面显示失败，就要看前端对响应字段的判断逻辑。
>
> 对订单、支付、配送状态这类核心场景，我还会结合后台和数据库确认数据是否真的更新。

### 5. 怎么判断前端 Bug 还是后端 Bug。

思路：

> 这题我会按“请求参数、接口响应、页面展示、数据库 / 后台数据”四步判断。

答案：

> 我会先用浏览器 Network、Fiddler 或 Charles 抓包，看前端实际发出的请求参数是否正确。
>
> 如果前端传给后端的参数就不对，比如字段缺失、金额传错、地址 ID 为空、token 没带，那更偏前端问题。
>
> 如果请求参数正确，但接口返回的数据、业务 code 或数据库数据不对，那更偏后端或数据问题。
>
> 如果接口返回正确，但是页面展示错误，比如订单状态文案显示错、金额格式化错、按钮状态不对，那一般是前端渲染或字段映射问题。
>
> 对广加这种下单、支付、配送状态类业务，我还会结合后台订单状态、支付流水和数据库一起确认。

### 6. Python + requests + pytest 怎么做接口自动化。

思路：

> 这题我会先说整体框架，再说一条用例怎么执行，最后说断言和接口依赖。

答案：

> 我会用 Python 的 requests 发送 HTTP 请求，用 pytest 组织和执行测试用例。一般会把接口地址、请求参数、预期结果放到 YAML 或测试数据文件里，把请求发送、断言、日志、参数提取做成公共封装。
>
> 一条接口自动化用例执行时，先读取测试数据，然后组装请求方法、URL、Headers、params 或 json，再用 requests 发送请求。拿到响应后，用 pytest 的 assert 做断言。
>
> 断言时不会只判断 HTTP 200，还会判断业务 code、message、data 结构和关键字段。比如登录接口要断言 token 是否返回，下单接口要断言订单号是否生成，订单查询接口要断言订单状态是否正确。
>
> 如果多个接口有依赖，比如登录后的 token、商品 ID、订单号，我会把上一个接口返回的数据提取出来，保存到上下文变量里，后续接口再引用。这样可以串起登录、下单、订单查询这类完整业务链路。

## 6. 接口测试与抓包定位

### 1. 接口测试一般关注哪些内容？

思路：

> 接口文档、请求、响应、业务、权限、异常、性能、数据一致性。

答案：

> 接口测试我会先看接口文档，确认请求方式、URL、请求头、参数位置、返回字段、鉴权方式和业务规则。
>
> 测试点包括正常参数、必填参数缺失、参数类型错误、边界值、权限鉴权、业务状态校验、重复提交、异常返回、响应时间、返回字段是否符合文档。
>
> 对于订单、支付、配送状态这类核心接口，我还会结合后台或数据库验证数据是否正确。

### 2. 页面提交失败，你怎么通过抓包判断问题在哪？

思路：

> 先看有没有请求，再看请求参数，再看响应状态码和响应体。

答案：

> 我会先看点击提交后有没有发请求。如果没有请求，可能是前端校验、按钮事件或 JS 异常问题。
>
> 如果有请求，就看 URL、请求方式、请求头、token、请求参数是否正确。再看响应状态码和响应内容，比如 400 可能是参数问题，401 / 403 可能是鉴权问题，500 可能是服务端异常。
>
> 如果接口返回成功但页面提示失败，就要继续看前端对响应字段的判断逻辑或页面渲染逻辑。

### 3. 接口返回 200，但业务失败，你怎么分析？

思路：

> 区分 HTTP 成功和业务成功。

答案：

> 我会先区分 HTTP 状态码和业务状态。接口返回 200 只能说明 HTTP 请求成功，不代表业务一定成功。
>
> 我会继续看响应体里的业务 code、message、data 和关键字段。如果业务 code 是失败，就根据 message 和请求参数定位，比如库存不足、状态不允许、权限不足、参数非法。
>
> 如果业务 code 成功但页面失败，就要看前端字段映射、状态判断、缓存或渲染逻辑。

### 4. 如果接口返回数据和数据库不一致，你怎么处理？

思路：

> 确认环境、数据源、查询条件、缓存、异步。

答案：

> 我会先确认接口环境和数据库环境是否一致，避免查错库或查错环境。然后确认查询条件，比如订单号、用户 ID、状态字段是否对应。
>
> 如果数据库是正确的但接口返回旧数据，可能和缓存、读写分离延迟或接口查询逻辑有关。如果接口返回正确但数据库不一致，可能是查的表不对，或者数据是异步写入还没完成。
>
> 我会把请求参数、接口响应、数据库查询结果和时间点整理出来，方便开发定位。

### 5. 怎么判断一个问题是前端 Bug 还是后端 Bug？

思路：

> 请求参数、接口响应、页面展示、数据库/后台数据。

答案：

> 我一般先看前端实际发出的请求参数。如果参数缺失、格式错误、字段传错，那更偏前端问题。
>
> 如果请求参数正确，但接口返回的数据、状态或数据库结果不对，那更偏后端或数据问题。
>
> 如果接口返回正确，但页面展示错误，比如状态文案、金额、按钮权限显示错，那一般是前端渲染或字段映射问题。核心链路我会结合后台和数据库一起确认。

### 6. 你用 Postman / Apifox 做接口测试的流程是什么？

思路：

> 看文档、建集合、配环境、调接口、断言、保存用例。

答案：

> 我会先根据接口文档建立接口集合，配置测试环境的 base URL、token、公共请求头等变量。
>
> 调试时先跑通正常接口，再覆盖异常参数、边界值、权限和状态校验。对核心接口会加断言，比如状态码、业务 code、返回字段、订单号或状态是否符合预期。
>
> 如果接口之间有依赖，比如登录后获取 token、创建订单后查询订单，我会把上一个接口返回的数据提取成变量，给后续接口使用。

>
> 这类问题不能只看页面，要把支付平台结果、接口响应、回调日志和数据库数据结合起来分析。

### 5. 线上用户反馈创建配送单失败，你怎么快速定位？

> 如果需要进一步定位，我会让开发或自己在权限允许范围内查看对应时间点日志，再结合数据库确认订单是否已经生成，避免页面提示失败但后台实际创建成功。

### 6. Redis 在测试中你了解什么？

答案：

## 8. 性能、兼容性与集成测试

### 1. 你怎么做接口性能测试？

思路：

> JMeter：线程组、请求、参数化、断言、报告、风险。

答案：

> 我会先明确压测目标，比如创建订单接口、查询订单接口、配送状态更新接口。然后准备测试环境、测试账号、token、订单数据和参数化数据。
>
> 在 JMeter 里配置线程组，设置线程数、Ramp-Up、循环次数，添加 HTTP 请求、请求头和参数。执行时加状态码断言和业务断言，避免只看 200。
>
> 结果主要看响应时间、TPS、吞吐量、错误率和服务器是否有异常。对于下单或创建配送单接口，还要关注是否出现重复订单、状态异常或数据不一致。

### 2. APP / H5 性能你会关注什么？

思路：

> 启动、加载、接口、卡顿、流量、弱网。

答案：

> 我会关注页面加载时间、接口响应时间、首屏展示、列表滚动是否卡顿、图片资源大小、弱网表现和异常提示。
>
> 如果是 APP，还会关注启动时间、崩溃、内存占用、耗电和后台切前台表现。配送类产品还要关注地图、订单列表、状态刷新和消息通知是否及时。
>
> 发现性能问题时，我会记录设备、系统版本、网络、操作步骤、耗时数据和抓包信息，方便开发定位。

### 3. 什么是集成测试？你怎么理解？

思路：

> 多模块联调，不是单点功能。

答案：

> 集成测试是把多个模块或系统串起来验证整体流程是否正常，不只是测某一个页面。
>
> 比如配送业务里，用户端创建订单、后台分配、配送端接单、状态更新、支付或结算、消息通知，这些模块单独测都正常，但串起来可能出现状态不同步、消息没发、后台数据不一致的问题。
>
> 所以集成测试要重点覆盖端到端主流程、跨模块数据传递、接口字段、状态流转和异常处理。

### 4. 你怎么做兼容性测试？

思路：

> 浏览器、设备、系统、容器、分辨率。

答案：

> Web / H5 我会覆盖 Chrome、Edge、Safari、微信 WebView、支付宝 WebView，以及不同分辨率和移动端尺寸。
>
> APP 我会覆盖 Android 和 iOS 的主流版本、不同品牌机型、不同屏幕尺寸。重点看核心流程、页面布局、按钮点击、输入框、弹窗、地图、支付唤起和消息提醒。
>
> 如果资源有限，会优先覆盖目标用户最常用的设备和核心业务链路。

### 5. 海外用户反馈访问慢，你怎么协助定位？

思路：

> 收集地区、设备、网络、页面、接口、资源。

答案：

> 我会先收集用户所在国家或地区、网络类型、设备、浏览器、具体页面和发生时间。
>
> 然后自己尝试复现，记录页面加载时间、接口响应时间、图片或脚本资源大小。重点看是否是接口慢、图片资源大、第三方服务慢、CDN 或网络线路问题。
>
> 测试这边不直接下结论，而是把环境、时间点、Network 记录、慢接口或慢资源整理出来，协助开发和运维定位。

## 9. Bug 管理、沟通协作与质量意识

### 1. 一个完整的 Bug 单应该包含什么？

思路：

> 开发能复现和定位。

答案：

> 一个完整的 Bug 单应该包含标题、所属模块、测试环境、前置条件、复现步骤、实际结果、预期结果、严重程度、优先级、截图或录屏、接口请求响应或日志信息。
>
> 如果是接口或数据问题，还可以补充请求参数、响应内容、账号、订单号、数据库查询结果和发生时间，方便开发快速定位。

### 2. 线上问题你怎么跟进？

思路：

> 先止损，再定位，再回归，再复盘。

答案：

> 线上问题我会先收集影响范围和复现信息，比如用户、时间、设备、订单号、截图、操作路径。然后判断是否影响主流程或资金数据，如果影响较大，要及时同步产品、开发和负责人。
>
> 定位时会结合前端复现、抓包、后台数据、日志和数据库。开发修复后，我会在测试环境和线上验证修复结果，并回归相关功能。
>
> 最后如果是比较典型的问题，我会整理原因、影响范围、修复结果和后续预防措施，沉淀到测试 checklist 或回归用例里。

### 3. 如果开发说这不是 Bug，你怎么处理？

思路：

> 不争论，回到需求、原型、规则、用户影响。

答案：

> 我不会直接争论，会先回到需求文档、原型图、接口文档或产品规则确认预期。如果需求里有明确说明，我会把依据同步给开发。
>
> 如果需求不清楚，我会拉产品一起确认。如果确认是 Bug，就继续跟进修复；如果确认是设计如此，但对用户体验有影响，我会转成优化建议。
>
> 重点是基于事实和依据沟通，而不是主观判断。

### 4. Bug 修复后你怎么回归？

思路：

> 原问题、关联流程、数据一致性。

答案：

> 我会先按 Bug 单里的复现步骤验证原问题是否修复。然后根据修改影响范围回归相关功能。
>
> 比如配送状态问题修复后，我不仅会测原来的状态，还会回归相邻状态、用户端展示、后台展示、配送端操作、接口返回和数据库状态。
>
> 如果涉及核心流程，还要做一次主流程冒烟，避免修复一个点引入新的问题。

### 5. 你怎么体现质量意识？

思路：

> 不只发现 Bug，也要预防问题和沉淀经验。

答案：

> 我理解质量意识不是只把 Bug 提出来，而是尽量提前发现风险、推动问题闭环，并把经验沉淀下来。
>
> 比如需求评审时主动指出规则不清楚的地方，用例设计时覆盖主流程和高风险异常场景，执行时关注接口和数据一致性，线上问题处理后把场景补充到回归用例里。
>
> 对配送、本地生活这类业务，我会特别关注订单状态、金额、时效、权限和多端一致性，因为这些问题对用户和业务影响更大。

### 6. 你怎么维护测试用例、测试脚本和操作手册？

思路：

> 对应 JD 第 6 点，讲沉淀和更新。

答案：

> 我会把稳定功能和核心流程沉淀成测试用例，按模块、优先级和场景分类维护。需求变更后及时更新用例，避免用例和实际功能不一致。
>
> 对重复性高、稳定性高的接口或流程，可以逐步沉淀成接口自动化脚本或回归 checklist。
>
> 操作手册方面，我会记录测试环境登录、账号准备、造数方法、常用后台路径、回归步骤和注意事项，这样新人或后续回归时能更快上手。

## 10. 自动化与脚本能力加分项

### 1. 你有自动化测试或脚本编写经验吗？

思路：

> 明确是加分项，不包装成高级自动化。

答案：

> 我这块不是把自己定位成专门的自动化测试工程师，而是作为接口测试和回归效率的补充。
>
> 我自己基于 Python + Pytest + Requests + YAML 搭过接口自动化练习框架，主要覆盖登录、商品、购物车、下单、订单查询等接口链路。框架里有统一请求封装、YAML 数据驱动、断言、响应字段提取和上下文变量传递。
>
> 我也了解 Selenium、Appium、Playwright 这类 Web / 移动端自动化工具的基本思路，但目前更适合作为加分项讲，核心还是功能测试、接口测试和问题定位能力。

### 2. 哪些场景适合做自动化？

思路：

> 稳定、高频、重复、价值高。

答案：

> 我认为适合自动化的场景一般是流程稳定、重复执行频率高、回归价值高的功能。
>
> 比如登录、创建订单、查询订单、状态更新、后台核心配置、接口主流程等。这些场景如果每次发布都要回归，沉淀成自动化可以提高效率。
>
> 但变化很频繁、页面元素不稳定、只测一次的功能不一定适合马上自动化，否则维护成本会比较高。

### 3. 接口自动化你怎么设计断言？

思路：

> 三层断言：HTTP、业务、关键字段。

答案：

> 我一般分三层断言。第一层是 HTTP 状态码，比如是不是 200。第二层是业务 code、message 和返回结构。第三层是关键业务字段，比如是否返回 token、订单号、订单状态、金额等。
>
> 对核心接口，只断言 200 不够，因为 HTTP 成功不代表业务成功。必要时还可以结合数据库断言，比如订单是否真的落库、状态是否正确。

### 4. 你做过 UI 自动化吗？

思路：

> 承认是基础了解，不包装。强调回归提效。

答案：

> 我目前 UI 自动化不是项目里的核心工作，更多是自己了解和练习过基础用法。
>
> 我知道常见工具像 Selenium、Appium、Playwright。Selenium 主要用于 Web 自动化，Appium 主要用于 APP 自动化，Playwright 也可以做 Web 自动化和端到端回归。
>
> 我的理解是，UI 自动化适合放在稳定、高频、重复执行的核心流程上，比如登录、下单、订单查询、支付后状态校验这类回归场景。它的目标不是替代手工测试，而是减少重复回归，提高效率。

### 5. 如果让你做一个简单 UI 自动化，你会怎么做？

思路：

> 选稳定流程，定位元素，模拟操作，加断言。

答案：

> 我会先选一个稳定的主流程，比如登录或订单查询。
>
> 然后分析页面元素，定位输入框、按钮、结果文案这些关键元素。脚本里按用户操作顺序执行，比如打开页面、输入账号密码、点击登录、等待页面跳转，断言是否出现登录成功后的用户名或首页元素。
>
> 如果是订单查询，就输入订单号，点击搜索，然后断言订单号、订单状态或金额是否正确展示。我会优先保证脚本稳定，不会一开始覆盖太多复杂场景。

### 6. Selenium 和 Appium 你怎么理解？

思路：

> 区分 Web 和 APP，讲基础能力。

答案：

> Selenium 主要是做 Web 自动化，可以通过定位页面元素来模拟用户操作，比如点击、输入、选择、断言页面结果。
>
> Appium 主要是做移动端 APP 自动化，思路和 Selenium 类似，也是定位元素、执行点击、输入、滑动等操作，只是对象变成了 Android 或 iOS APP。
>
> 我的理解是，Selenium 更适合 Web / H5 / 管理后台这类页面回归，Appium 更适合 APP 主流程回归，比如登录、下单、订单状态查询。

### 7. UI 自动化怎么断言？

思路：

> 不只看脚本跑完，要断言页面结果，核心业务可结合接口或数据库。

答案：

> 我不会只看脚本有没有跑完，而是会加断言。
>
> 比如登录后断言是否出现用户名、首页元素或登录后的页面状态；订单查询后断言订单号、订单状态、金额是否和预期一致；提交表单后断言成功提示或列表新增记录。
>
> 如果是核心业务，最好还可以结合接口或数据库做二次校验，但基础 UI 自动化里至少要有页面结果断言。

### 8. UI 自动化有什么难点？

思路：

> 稳定性和维护成本。

答案：

> 我觉得难点主要是脚本稳定性和维护成本。
>
> 比如页面元素经常变化、加载时间不稳定、弹窗遮挡、网络慢、测试数据变化，都会导致脚本失败。
>
> 所以我会优先选择稳定流程来做，用比较可靠的元素定位方式，必要时加显式等待，并维护好测试数据。对于变化太频繁的页面，不会强行自动化。
