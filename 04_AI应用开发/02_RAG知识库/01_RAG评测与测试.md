# RAG 评测与测试

> [!info] 笔记定位
> 这篇笔记回答“怎样证明 RAG 的效果，以及怎样定位问题”。当前先建立评测框架，指标公式、代码和真实结果将在项目实践中逐步补充。

## 一、为什么普通测试不等于 RAG 评测

普通接口测试可以验证状态码、字段和异常处理，但无法证明检索结果是否正确，也无法证明回答是否忠于知识库。

RAG 同时包含确定性软件行为和概率性模型输出，因此需要两类验证：

- 软件测试：接口、权限、状态、异常、并发、安全和数据一致性；
- 效果评测：检索命中、排序质量、回答正确性、引用、拒答、稳定性和延迟。

## 二、RAG 要分层评测

| 层级 | 主要检查内容 |
| --- | --- |
| 文档解析 | 正文、标题、表格和页码是否保留 |
| 切片 | 内容是否完整，边界是否合理，来源能否追溯 |
| Embedding | 模型、维度和索引版本是否一致 |
| 检索 | 正确片段是否进入 Top-K |
| 重排 | 正确片段是否被排到前面 |
| 上下文 | 最终证据是否相关、完整且没有被错误裁剪 |
| 生成 | 答案是否正确、相关并忠于证据 |
| 引用 | 引用是否真实支持对应结论 |
| 拒答 | 无依据问题是否稳定拒答 |

分层评测的目的，是区分“没有找到证据”和“找到证据但模型仍然答错”。

## 三、评测集是什么

评测集不是只有问题列表。每条用例至少应包含：

```json
{
  "id": "rag-001",
  "question": "用户问题",
  "question_type": "fact",
  "gold_sources": ["预期来源"],
  "gold_headings": ["预期标题或片段"],
  "reference_points": ["标准答案要点"],
  "answerable": true,
  "risk_level": "medium",
  "dataset_version": "v1"
}
```

评测问题优先来自：

1. 真实用户问题和脱敏历史对话；
2. 已审核的 FAQ、SOP 和知识文档；
3. 历史失败、投诉和容易混淆的问题；
4. 基于确定知识扩展出的同义句、错别字和边界问题。

如果使用 AI 生成评测题，应从已审核的知识或答案反向生成问题，不能让 AI 凭空同时生成问题和真值。

### 评测集的建立顺序

评测集更准确的说法是“构建和审核”，而不只是批量生成。刚开始先用一组小规模、能够人工确认真值的种子用例验证评测链路，再根据失败类型和覆盖缺口扩充。

```text
选择固定知识范围
→ 建立 10 条左右的种子用例
→ 人工核对预期来源、标题和是否可回答
→ 跑出第一份检索基线
→ 分析失败样本与缺失的问题类型
→ 扩充到 30～50 条 Gold Set
→ 固定版本用于调参与回归
```

不要在第一次基线前生成大量问题，否则错误真值、重复问题和类型失衡会增加审核成本。`personal-test-rag` 当前已有 10 条种子用例，正确顺序是先运行并保存这组用例的结果，再加入同义问法、相似概念、干扰项和更多无答案问题。

### `personal-test-rag` 种子用例结构

当前评测文件使用 JSONL 格式：一行是一个完整、相互独立的 JSON 用例，便于逐条追加、读取和比较版本。每条只有四个字段：

| 字段 | 含义 |
| --- | --- |
| `question` | 需要转换为向量并执行检索的用户问题 |
| `expected_source` | 预期命中的白名单文档相对路径；拒答用例为 `null` |
| `expected_heading` | 预期命中的章节标题；拒答用例为 `null` |
| `should_refuse` | `false` 表示知识库应该找到证据，`true` 表示不应召回达到阈值的结果 |

正例结构：

```json
{"question":"JMeter 如何通过 CSV 文件实现参数化？","expected_source":".../Jmeter笔记.md","expected_heading":"6.6 CSV参数化处理","should_refuse":false}
```

正例只有在同一个 Top-K 结果同时匹配预期文档和标题时才通过。当前有 8 条正例，分别覆盖 8 份白名单文档。

拒答例结构：

```json
{"question":"2032 年火星奥运会的金牌榜是什么？","expected_source":null,"expected_heading":null,"should_refuse":true}
```

拒答用例在相关度阈值过滤后没有剩余 Chunk 才通过。当前有 2 条拒答用例，分别检查未来虚构信息和需要外部实时数据的问题。

这组用例目前只足以评测检索层的文档与标题命中、拒答和来源路径有效性；它没有标准答案要点，因此不能直接评价最终答案正确性、Faithfulness 或回答是否覆盖完整。

### RAG 与 Agent 评测集能否共用

可以复用同一批业务场景、用户问题和参考答案，但不能直接用完全相同的真值与指标判分。

| 评测对象 | 额外需要的真值 | 主要检查 |
| --- | --- | --- |
| RAG | Gold Source、Gold Passage、是否可回答、答案要点 | 检索命中、Faithfulness、引用、拒答 |
| Agent | 初始状态、允许调用的工具、参数约束、预期业务结果、最终状态和失败兜底 | 工具选择、参数、权限、步骤依赖、幂等、业务副作用和多轮恢复 |

例如“查询退款规则并发起退款”可以作为同一个基础场景：RAG 评测检查是否找到正确退款条款；Agent 评测还要检查是否先取得订单信息、验证退款资格、使用正确参数调用退款工具，并在失败时避免重复退款。

实践中更适合维护一份带稳定 `case_id` 的主场景集，再派生 RAG 和 Agent 两个评测视图；两者共享问题、上下文、风险等级和参考答案，各自保存专属标注。只测试知识问答的用例可以进入 RAG 集但不进入 Agent 集，只测试工具编排的用例也不必强行加入 RAG 集。

## 四、检索层常见指标

### 第 2 天英文术语速查

| 英文 | 中文理解 | `personal-test-rag` 中的对应物 |
| --- | --- | --- |
| Evaluation Dataset | 评测数据集，用来固定地考系统的一组题 | `evals/questions.jsonl` |
| Test Case | 单条评测用例 | JSONL 中的一行 |
| Ground Truth | 人工核对过、用来判分的真值标注 | 预期来源、标题和是否拒答 |
| Gold Set | 含有可靠 Ground Truth 的固定评测集 | 当前 10 条是第一版种子 Gold Set |
| Gold Source | 这道题应该命中的正确文档 | `expected_source` |
| Gold Heading / Passage | 应命中的正确章节或证据片段 | `expected_heading`，当前还没有精确 Passage 标注 |
| Positive Case | 知识库中有依据、应成功检索的正例 | `should_refuse: false` |
| Negative Case | 知识库中没有可靠依据、应用来检查拒答的负例 | `should_refuse: true` |
| Retrieval | 根据问题从知识库中找相关 Chunk 的过程 | `search_chunks(...)` |
| Top-K | 按相关度排序后保留前 K 个结果 | 当前默认 Top-5 |
| Hit@K | 正确结果是否至少有一个进入 Top-K | 8 条正例中命中 7 条，则 Hit@5 = 7/8 = 87.5% |
| MRR | 第一个正确结果平均排得多靠前 | 正确结果排第 1、2、未命中时，MRR = `(1 + 1/2 + 0) / 3 = 0.5` |
| Refusal Accuracy | 无依据问题被正确拒答的比例 | 2 条负例正确拒答 1 条，则为 50% |
| Latency | 从开始检索到返回检索结果所用的时间 | 通常记录毫秒 `ms` |
| Threshold | 相关度最低门槛，低于它的结果被过滤 | 当前 `min_relevance_score` |
| Baseline | 不做优化前保存的第一份基准结果 | 后续修改 Top-K、Chunk 或阈值时的比较对象 |

`Gold` 不是“模型生成的漂亮答案”，而是“经过人工审核，可以作为判分标准的真值”。相关度分数也不是概率，例如阈值 `0.35` 不表示有 35% 的概率正确；它只是当前 Embedding 与检索实现下需要通过实验校准的分界线。

| 指标 | 回答的问题 |
| --- | --- |
| Hit@K | Top-K 中是否至少出现一个正确结果 |
| Recall@K | 应命中的相关片段有多少进入 Top-K |
| Precision@K | Top-K 中有多少结果是真正相关的 |
| MRR | 第一个正确结果排得是否足够靠前 |
| nDCG | 多个不同相关程度的结果排序是否合理 |
| Latency | 检索耗时是否满足要求 |

刚开始可以先使用 Hit@K、MRR、拒答准确率和检索耗时；随着评测集完善，再增加 Recall@K、Precision@K 和 nDCG。

### 召回质量的最小测试闭环

“召回准确率”不是一个统一指标，应拆成“是否命中、是否找全、误召回多少、正确结果排第几”。测试时只运行检索链路，先不要让生成模型回答，以免把检索错误和生成错误混在一起。

1. 选定固定知识库版本，建立一组经过人工审核的问题；
2. 为每道正例标注一个或多个相关 Chunk ID，组成 Gold Passage 集合；无依据问题单独标为负例；
3. 固定 Embedding、切片、Top-K、阈值和重排配置，保存每道题的有序检索结果；
4. 对每道正例计算指标，再对全部正例取平均：
   - `Hit@K = 1`：Top-K 至少包含一个 Gold Passage，否则为 `0`；
   - `Recall@K = Top-K 中 Gold Passage 数 / 全部 Gold Passage 数`；
   - `Precision@K = Top-K 中 Gold Passage 数 / K`；
   - `RR = 1 / 第一个 Gold Passage 的名次`，未命中为 `0`，所有问题的平均值是 MRR；
5. 对负例统计错误召回率或拒答准确率，并按问题类型分别出报告，避免总体平均值掩盖薄弱类别。

如果每道题只标注一个正确片段，`Recall@K` 会退化成与 `Hit@K` 相同的结果，无法判断“多条必要证据是否找全”。因此可以先用 Gold Source 或 Gold Heading 跑通基线，再逐步升级为精确的 Gold Passage 标注。阈值过滤后不足 K 条时，`Precision@K` 的分母是否仍按 K 计算要在评测脚本中固定，版本之间不能改变口径。

例如 8 道正例中有 7 道在 Top-5 命中，`Hit@5 = 7 / 8 = 87.5%`；但如果一道多证据问题共有 3 个 Gold Passage，只召回 1 个，则该题 `Recall@5 = 1 / 3`。前者表示“至少找到一个”，后者才表示“找全了多少”。

## 五、生成层常见指标

| 指标 | 主要含义 |
| --- | --- |
| 回答正确性 | 是否覆盖标准答案要点 |
| Faithfulness | 回答是否得到检索证据支持 |
| Answer Relevancy | 回答是否真正回应用户问题 |
| 引用正确性 | 引用是否支持对应结论 |
| 拒答准确性 | 有答案和无答案问题是否处理正确 |
| 稳定性 | 同一问题多次执行是否出现明显波动 |
| 延迟与成本 | 整体响应时间和模型资源消耗 |

### 用两组上下文隔离检索问题和生成问题

生成评测不要只跑一次完整 RAG 链路。同一批需求应至少比较两组输入：第一组绕过检索器，直接提供人工确认的 Gold Passage，验证模型在“证据一定正确”时能否生成合格用例；第二组使用生产检索器实际返回的上下文，验证完整链路。

```text
Gold Passage → 生成失败：优先检查 Prompt、模型、结构约束和证据遵循
Gold Passage → 生成通过，但真实检索 → 生成失败：优先检查检索与上下文组装
两组都通过：再验收完整链路的稳定性、延迟和成本
```

这种对照不能代替检索层的 Hit@K、Recall@K 和 MRR，但能避免把“模型没有拿到正确证据”误判成模型生成能力不足。

## 六、怎样自动判分

判分方式应按可靠性组合使用：

1. 确定性断言：检查状态、字段、来源、关键词、工具调用和拒答结果；
2. 指标计算：根据 Gold Source 或 Gold Passage 计算检索指标；
3. LLM-as-a-Judge：根据固定 Rubric 评价回答质量；
4. 人工审核：校准裁判，并复核低分、临界分和高风险结果。

裁判模型给出理由并不代表它一定正确。需要用人工标注的小样本比较裁判和人工是否一致，再逐步调整 Rubric、示例和阈值。

## 七、失败定位思路

```text
正确片段没有进入候选结果
→ 检查解析、切片、Embedding、查询改写和检索

正确片段进入候选但重排后丢失
→ 检查融合策略、Rerank 模型和 Top-K

正确片段进入最终上下文但回答错误
→ 检查上下文裁剪、Prompt 和 LLM

答案内容正确但引用不对应
→ 检查 Chunk 元数据、引用映射和展示逻辑
```

为了定位问题，一次执行至少应保留：

- 问题和用例编号；
- 数据集、知识库和系统版本；
- 检索候选、排序、分数和最终上下文；
- 模型输入、回答和引用；
- 各阶段耗时；
- 最终评分和失败分类。

## 八、对比实验原则

RAG 优化不能只看几个成功案例，应使用固定评测集进行版本对比。

基本原则：

- 先建立基线；
- 一次只修改一个主要变量；
- 保存模型、Prompt、切片和检索配置；
- 同时观察效果、延迟和成本；
- 保留失败样本并加入回归集。

可逐步比较：

```text
向量检索基线
→ 调整 Chunk 和 Top-K
→ 增加 BM25
→ 增加查询改写
→ 增加 RRF
→ 增加 Rerank
```

## 十、面试回答框架

> 我会把 RAG 分成检索层和生成层评测。先建立带预期来源或片段的 Gold Set，检索层看 Hit@K、Recall@K、MRR 和延迟；生成层看正确性、faithfulness、引用和拒答。如果正确证据没有进入 Top-K，就检查解析、切片、Embedding、查询改写、检索和重排；如果证据已经进入最终上下文但仍然答错，再检查 Prompt 和模型。自动评测会结合确定性断言、经过人工校准的 LLM 裁判和风险抽检，并固定数据集与配置做版本回归。

## 十一、基于 RAG 生成测试用例的闭环

RAG 的作用是为模型提供经过版本控制的需求、接口文档、业务规则和历史缺陷证据，不能把模型生成结果直接当成正确用例。

```text
需求解析与清洗
→ 按需求 ID、业务流程和规则切片并建立索引
→ 检索当前需求、关联规则、接口定义和历史高价值用例
→ LLM 按固定 Schema 生成候选用例
→ 确定性校验、去重和冲突检查
→ 人工评审
→ 携带来源与版本落库
→ 执行结果和线上缺陷反哺回归集
```

候选用例至少保留 `requirement_id`、标题、前置条件、步骤、测试数据、预期结果、优先级、用例类型、引用来源和生成配置。落库前先用规则检查必填字段、步骤与预期是否成对、接口参数是否合法，再进行语义去重、需求覆盖检查和高风险人工审核。

比较新旧版本时，应冻结同一批需求和评分规则，分别统计需求点覆盖、正向/异常/边界/权限场景覆盖、重复率、可执行率、可追溯率和人工采纳率；报告同时列出新增覆盖、退化项、失败样本、延迟与成本。LLM 裁判只能作为辅助评分，需先用人工标注样本校准，并对高风险和临界分样本复核。

### 单次生成评审与批量效果评测

“把 JSON 展示成表格”只能改善阅读，不能自动证明生成质量。测试用例生成应区分两类报告：

- 单次生成评审：面向一次需求，汇总生成状态、用例数、证据引用率、澄清项、重复项、场景分布和结构告警，并保留逐条人工结论；用于判断本次草稿能否进入审批。
- 批量效果评测：固定同一批需求和评分规则，统计覆盖率、重复率、可执行率、可追溯率、采纳率、延迟和失败分类；用于比较模型、Prompt、知识版本或检索配置。

单次报告可以自动确定“字段是否完整、引用是否存在、步骤数量、重复候选和状态”等结构事实；“业务结论是否正确、需求是否完整覆盖、证据是否真正支持预期”仍需要 Gold 要点、人工评审或经过校准的辅助裁判。原始 JSON 是事实源，HTML/Excel 只负责汇总、筛选和记录评审结论。

### 重复调用与幂等边界

一次“生成测试用例”请求应视为一次独立的草稿任务：创建新的 `generation_id`，锁定当时的知识版本，保存请求、结果和 Trace，并写入独立的导出目录。它不会按相同需求复用或覆盖旧草稿，因此重复调用会再次执行检索和模型生成；即使输入不变，模型输出也可能不同。

项目当前的精确去重只把本次草稿与**锁定知识版本中的已审批正式用例**比较，不会查询历史未审批草稿，也不会删除同一批模型输出中彼此重复的候选（评审报告会提示这类重复）。所以未审批时反复生成会保留多份可能重叠的草稿。审批同一 `generation_id` 本身是幂等的；审批会写入正式用例并发布新知识版本，后续生成才会跳过与这些正式用例完全相同的候选。
