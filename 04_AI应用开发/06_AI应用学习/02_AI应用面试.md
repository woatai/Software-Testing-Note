# AI 应用面试

> [!info] 笔记定位
> 这篇笔记把已经理解的概念和已经验证的项目实践整理成可复述、可追问的面试表达。知识定义见 [[00_AI应用核心知识]]，项目证据见 [[01_AI应用项目实践]]。

## 一、记录原则

- 先用 30～60 秒直接回答，再补充项目证据。
- 只使用真实实现或验证过的经历，不虚构功能、指标和线上规模。
- 同时记录关键技术选择、取舍原因和可能的深入追问。
- 不背诵孤立术语，要能说明组件在完整业务链路中的位置。

## 二、Agent 面试题

### 如果让你测试一个 Agent，你会考虑哪些方面？

**简答：** 测试 Agent 不能只看最终回复，而要先定义任务成功条件，再验证“意图与澄清—可观察的执行步骤—工具选择—参数—工具结果—系统状态—最终回答”整条 Trace。确定性的工具、参数、调用次数、数据库状态和幂等性用代码断言；语义质量用明确 Rubric 评估，并用人工 Gold Set 校准。还要横向覆盖权限与提示词注入、多轮会话隔离、异常恢复、时延和单任务成本。

例如退款 Agent 回复“退款成功”，仍需确认它校验了订单归属和支付状态，调用了正确工具，传入的订单号、金额和币种正确，退款流水唯一，数据库状态真实改变；如果接口超时但后台已经退款，重试不能造成重复退款。工具失败时，最终回答也不能声称成功。

这里的分层只是便于表达的自用测试框架，不是行业统一标准。不要要求模型暴露隐藏思维过程，只验证可观察的工具调用、参数、返回值、状态变化和审计记录；Agent 可能存在多条合理路径，应验证必要前置条件、业务不变量与最终状态，而不是锁死唯一调用顺序。

**项目证据：** 当前 `enterprise-ai-automation` 已验证的是工作流入口、幂等写库和接口测试，n8n、模型和 Agent 执行仍为 `计划中`。面试时应说“我理解并能设计这套测试方法，但还没有生产 Agent 测试经验”，不能把方案表达成已经落地。

**追问：** 接口超时但实际已执行成功时，怎样用状态查询、幂等键和重试策略避免重复副作用？当多条工具路径都能完成任务时，怎样设计不依赖固定步骤的评价标准？

来源：[[世纪众云面试题整理#13. 如果让你测试一个 Agent，你会考虑哪些方面？]]

### 大模型与 Agent 是什么关系？上下文持续变大怎样治理？

**简答：** 大模型是概率性的理解和生成核心；Agent 是围绕模型构建的任务执行系统，通常还包含系统指令、任务状态、上下文或记忆、检索、工具、控制循环、权限和安全规则。大模型负责生成下一步内容，Agent 负责组织任务并把模型输出接到可控的外部执行链路上。

上下文治理不能只靠一直追加聊天记录。稳定的系统约束和当前任务状态应保留；旧对话可压缩成结构化摘要；大文件、历史结果和长期记忆放到外部存储，需要时按 ID 或检索结果加载；每一步只注入相关工具说明和证据，并设置 Token 预算。压缩后还要回归验证用户目标、关键实体、约束和未完成事项没有丢失。

**项目证据：** 当前个人项目尚未实现 Agent 上下文治理。可说明已经理解设计方法，但状态持久化、摘要质量和长任务恢复仍待实际验证。

**追问：** 摘要压缩丢失关键约束怎样发现？短期上下文、长期记忆和业务状态分别应存在哪里？

来源：[[世纪众云面试题整理#14. 大模型与 Agent 是什么关系？怎样治理持续变大的上下文？]]

### n8n 节点怎样组成一个可验证的 HTTP 闭环？

**简答：** 先用触发器接收输入，再用连线把数据交给 HTTP Request；节点内部通过表达式把输入字段映射到请求头和 JSON body，最后把 Webhook 的返回策略设为“最后一个节点完成后返回”。闭环的验收不只看画布连线，还要确认 n8n 所在环境能访问 FastAPI、HTTP 状态码正确、幂等键有效，并在数据库中看到对应运行记录。

**项目证据：** 已在远程 n8n 保存 `Webhook(POST) → HTTP Request(POST /workflow/run)`，配置了 `Content-Type`、`n8n-{{$execution.id}}`、三个 `$json.body.*` 映射和最后节点返回；面板显示的生产 URL 仍为 `localhost`，说明对外基址也需要部署配置。本机 FastAPI 已验证 200/201，8 个测试通过；远程 n8n 到 FastAPI 的 8000 端口仍超时，因此面试时应表述为“最小工作流配置已完成，远程端到端联调待部署后验证”，不能说成生产通知闭环。

**追问：** 为什么要用 `Idempotency-Key`？如果 n8n 重试或网络超时，如何区分重放、冲突和真正失败？如果 FastAPI 与 n8n 在 Docker 中，公网 URL 和同网络服务名各有什么取舍？

### Webhook 和 HTTP Request 节点有什么区别？

**简答：** Webhook 是入站触发器，负责监听 URL、接收外部请求并启动工作流；HTTP Request 是出站动作，负责按配置调用其他 HTTP API。前者解决“谁来触发”，后者解决“工作流要调用谁”。两者通过上游输出和表达式传递数据，但不是必须成对出现。

**项目证据：** 当前远程画布使用 `Webhook → HTTP Request`：Webhook 接收 `$json.body` 中的任务字段，HTTP Request 组装 JSON、请求头和幂等键后调用 FastAPI；Webhook 设置为等待最后一个节点完成后返回。

**追问：** 为什么字段写成 `{{$json.body.user_id}}` 而不是直接写 `$json.user_id`？回答时应说明表达式必须匹配上游节点的实际输出结构，不能凭节点名称猜路径。

### 用 Docker 重建 FastAPI 容器，符合企业迭代流程吗？

**简答：** 符合底层机制，但是否达到企业级取决于发布控制。企业同样通过版本化镜像替换应用实例，并配合数据库迁移、健康检查和回滚；区别是不会长期依赖个人 SSH 到生产服务器手工构建，而会由 CI 测试并构建一次镜像、推送制品仓库，再把同一制品经过测试环境和审批发布到生产。企业化的判断标准是可重复、可审计、可回滚和环境隔离，不是是否一定使用 Kubernetes。

**项目证据：** 当前项目已验证自动化测试、FastAPI 镜像构建，以及本机 Compose 管理 API、MySQL、健康检查、迁移和共享外部网络；真实 HTTP 请求返回 201 后也在 MySQL 查到记录。远程服务器部署、n8n 外部网络配置、镜像仓库、CI/CD、分环境配置和自动回滚仍为 `待验证` 或 `计划中`，因此现阶段应表述为“已完成单机 Compose 发布基础并验证数据链路，正在从本机验证演进到远程可重复流水线”，不能描述成已经落地企业级生产发布。

**追问：** 为什么应当只构建一次镜像并在多个环境中使用？数据库迁移失败或新版本健康检查失败时怎样回滚？单机 Compose 在什么条件下足够，什么时候才需要 Kubernetes？

## 三、AI 测试用例生成平台项目表达

### 怎样用 60 秒介绍 `testcase_ai_`？

**20～30 秒开场：** 这是我个人完成的 AI 测试用例生成与评审项目。它不是把需求直接交给大模型，而是先从版本化知识库检索业务规则和已有用例，判断哪些测试意图已经覆盖，再只生成缺失用例，并通过结构、证据、重复检查和人工审批控制质量。目前主链路、Trace、多格式导出和审批回库已经实现，本地 133 项自动化测试通过；当前仍是本机单用户实践平台。

**简答：** 这是我个人完成的 AI 测试工程实践项目，目标不是让大模型直接输出一份看似完整的用例，而是建立一条可追溯、可审核、可沉淀的生成流程。平台接收文本、Markdown 或 DOCX 需求，锁定项目知识版本，通过 Dense、BM25 和 RRF 检索业务规则、Workflow 与正式用例；随后先规划测试意图，判断正式库对每个意图是已覆盖、部分覆盖还是全新，只生成缺失草稿。生成结果必须通过 Pydantic/JSON Schema、引用有效性、证据一致性和重复检查；证据不足时返回澄清，而不是猜业务规则。最后通过工作台查看 Trace、审核 JSON/Excel/HTML 产物，只有人工显式确认后才原子写入正式用例并重新索引。2026-10-14 当前工作区验证为 133 项自动化测试通过、Ruff 全通过。

**项目证据：** FastAPI、Pydantic、SQLAlchemy/Alembic、MySQL、Milvus、Ollama/OpenAI-compatible Provider、OpenPyXL、Docker Compose；当前项目仍是本机单用户实践平台，不是线上多租户生产系统。

**追问：** 为什么不直接把需求发给大模型？怎样判断“已覆盖”和“部分覆盖”？缺少退款金额规则时为什么必须澄清？人工审批怎样避免覆盖或重复写入正式资产？

### 这个项目是怎么搭建起来的？

**简答：** 这是我个人搭建的 AI 测试用例生成与评审项目，不是线上多租户生产平台。搭建时我先解决“直接把需求交给大模型，容易漏业务规则、重复生成且无法追溯”的问题，把系统拆成五层：第一是输入与知识层，只使用公开、自建或已授权脱敏的需求、规则和正式用例，并为知识建立 Revision；第二是检索层，用 Dense、BM25 和 RRF 从当前项目与 Revision 中召回证据；第三是生成层，先规划测试意图并判断正式用例对每个意图是已覆盖、部分覆盖还是全新，只生成缺失草稿；第四是质量层，用 Pydantic/JSON Schema、引用有效性、证据一致性和重复检查做门禁，证据不足就返回澄清，不让模型猜业务规则；第五是审核与沉淀层，在工作台查看 Trace 和 JSON/Excel/HTML 产物，人工确认后再原子写入正式用例并重新索引。后端使用 FastAPI，MySQL 保存任务、版本和审批状态，Milvus 承担向量检索；目前本地 133 项自动化测试和 Ruff 均通过。

**项目证据：** `Application` 统一装配数据库、模型、向量库及知识、检索、生成、审批服务；`project.yaml` 是业务包入口；Docker Compose 管理 MySQL 与 Milvus 依赖；CLI/API 复用核心服务。当前已实现增量 Trace 和按知识、请求、清单、策略及模型版本校验的生成断点。工作台仍采用 FastAPI 进程内单线程任务，适合个人本地演示，尚未实现独立 Worker、Redis、登录、多租户和生产级高可用。

**表达提醒：** 不把 Dense、BM25、混合检索说成三个依次执行的独立阶段；混合检索是把 Dense 与 BM25 的候选结果进行融合，当前项目使用 RRF。生成链路更准确地称为“可观测工作流”，不因为调用了大模型就直接称为 Agent。不能说把前公司资料搬到本地，只能表述为公开、自建或已授权脱敏的数据。

**追问：** 为什么 MySQL 与 Milvus 要分工？为什么生成任务要锁定知识 Revision？为什么使用混合检索而不是只用向量检索？Trace 具体记录哪些信息，断点续跑怎样避免混用不同知识或模型版本？如果改造成生产系统，任务队列、权限、监控和部署要怎样补齐？

来源：[[世纪众云面试题整理#12. 你的知识库内容从哪里来？怎样存储、检索和编排？]]

### 怎样把项目写进针对 AI 辅助测试岗位的简历？

**简答：** 项目标题写“AI 测试用例生成与评审平台（个人项目）”，先用一句话写测试业务价值，再用 4～6 条写自己完成的关键机制与可验证结果。重点是知识约束、覆盖判断、质量门禁、人工审核和测试证据，不堆砌全部组件名，也不写没有测量过的效率百分比。

**项目证据：** 可使用“133 项自动化测试通过、Ruff 全通过”作为工程质量证据；若附 GitHub 链接，必须先把本地领先远端的提交和稳定工作区推送，否则面试官无法复核简历中的主要能力。

**追问：** 这是个人项目还是公司项目？哪些代码由 AI 辅助完成，你本人负责了什么？项目有哪些生产化缺口？如果接入会员储值、次卡退款业务，需要新增哪些知识和评测样本？
