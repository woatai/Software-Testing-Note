# AI 应用项目实践

> [!info] 笔记定位
> 这篇笔记回答“我在 AI 应用项目中实际实现、运行和验证过什么”。通用概念见 [[00_AI应用核心知识]]，面试表达见 [[02_AI应用面试]]。

## 一、状态规则

| 状态 | 含义 |
| --- | --- |
| 已实现 | 代码或配置已经存在 |
| 已验证 | 已实际运行，并有命令、输出或其他证据 |
| 待验证 | 已有实现，但还没有真实运行证据 |
| 计划中 | 尚未实现，只是后续方案 |

记录项目实践时，必须区分“代码已经写好”和“功能已经实际验证”，不能把接口返回成功直接等同于数据已经落库。

## 二、`enterprise-ai-automation` 当前实现快照（更新至 2026-10-06）

### 1. 项目现在要解决什么

这是一个“企业工作流执行后端”的原型：接收用户和任务信息，为一次工作流生成运行编号并持久化整次运行；后续再执行并记录每个步骤，并接入 n8n 或 AI 处理。当前阶段已经打通“接收请求并落库”，还没有实现真实业务自动化。

当前磁盘源码的真实请求链路是：

`POST /workflow/run` → `workflows/router.py` 校验 HTTP 输入 → `workflows/service.py` 执行幂等与事务规则 → SQLAlchemy Session → MySQL → Router 转换 HTTP 状态与响应头

2026-09-26 已将 V1 业务方向确定为**电商运营日报与异常处置自动化**，并在项目 `docs/ecommerce-operations-requirements.md` 建立基线需求文档：单店、日级、合成或脱敏的双 Sheet Excel、前 7 个有效日基线、人工审核后发送一种通知渠道。由确定性代码完成清洗、指标计算与异常判断，AI 只基于已计算事实生成运营摘要、待验证假设和建议，再通过 n8n 通知并记录任务处理结果。需求文档为 `已实现`，业务闭环代码仍为 `计划中`。

当前订单清洗入口是独立的单表练习功能，与 V1 需求中的 `store_daily`、`sku_daily` 双 Sheet 导入合同不同。它已经检查输入/输出文件及 7 个清洗必需列，完成状态文字、数量、金额和文件内重复处理，但还没有检查日期、状态允许值或跨字段关系，也没有影刀/FastAPI 调用入口；跨次导入的幂等仍需另行设计。因此当前状态是“基础清洗已验证”，不是完整业务数据管道。

两张业务表的分工：

- `workflow_run`：保存一次完整任务的输入、输出、状态、错误和开始/结束时间。
- `workflow_step_run`：保存这次任务内部每一步及每次重试的请求、响应、耗时和状态。

### 2.1 n8n 最小联调工作流（2026-09-29）

**目标：** 先让 n8n 学会接收一份任务 JSON，再调用当前 FastAPI 的通用入口；这一步验证的是跨系统数据流，不是完整的电商日报业务闭环。

**已完成配置：**

1. 在远程 n8n 画布保留 `Webhook` 作为 POST 触发器，通过节点右侧 `+` 添加 `HTTP Request`，n8n 自动生成连线。
2. `HTTP Request` 使用 POST，目标为 `http://132.226.73.129:8000/workflow/run`。
3. 请求头为 `Content-Type: application/json` 和 `Idempotency-Key: n8n-{{$execution.id}}`。
4. JSON body 的三个字段分别映射为 `{{$json.body.user_id}}`、`{{$json.body.task_type}}` 和 `{{$json.body.department}}`。
5. Webhook 的返回方式设为 `When Last Node Finishes`，把最后一个节点的 JSON 返回给调用方。
6. Webhook 面板的生产 URL 当前仍显示 `http://localhost:5678/webhook/ace621da-d1f0-427b-a1bd-c096bc9820ce`；这代表 n8n 的显示基址未配置为公网地址。外部调用应使用同一路径拼接服务器地址 `http://132.226.73.129:5678/webhook/ace621da-d1f0-427b-a1bd-c096bc9820ce`，并在部署配置中修正 n8n 的对外 host/editor URL。

**验证证据：** 关闭配置窗口并重新加载 n8n 页面后，两个节点和配置仍然存在，页面提示数据已保存。本机启动当前 `0.2.0` FastAPI 后，`GET /health` 返回 HTTP 200，首次调用 `/workflow/run` 返回 HTTP 201 和 `accepted`，用同一幂等键重放返回 HTTP 200 且带 `Idempotent-Replay: true`；随后按该幂等键查询 MySQL，确认 `workflow_run` 中存在对应的 `run_id`、三个输入字段和 `accepted` 状态。当前工作区测试为 8 个通过。

**当前边界：** 直接请求远程 `132.226.73.129:8000/health` 超时，因此远程 n8n 到 FastAPI 的真实执行仍为 `待验证`。下一步必须在 n8n 所在服务器启动 FastAPI、开放可访问端口，或把两个服务放进同一 Docker Network 并改用内部服务名；同时修正 n8n 生产 URL 的对外基址。完成后再用 Webhook 生产 URL 发一份测试 JSON，检查 n8n 执行结果、FastAPI 返回码和 `workflow_run` 数据库记录。现阶段不能把 `accepted` 记录描述为日报已完成，也不能把节点配置描述为生产闭环。

### 2.2 Compose 化与服务器部署核对（2026-09-30）

**问题结论：** 服务器请求 `132.226.73.129:8000` 超时的根因不是 `/workflow/run` 的 JSON 或 n8n 节点表达式，而是 FastAPI 只在 Mac 本机运行，服务器上没有监听 8000 的 FastAPI 进程或容器。服务器中的 n8n 请求该地址时，访问的是服务器自己的 8000 端口，不会访问 Mac 的 `localhost:8000`。

**已验证的仓库事实：** 当前本地与 `origin/main` 都指向提交 `6e54e55`（`运维：拆分本地 MySQL 端口映射`）；`fastapi/Dockerfile` 的构建上下文为 `./fastapi`。根目录 `compose.yml` 已增加 `api` 服务：镜像版本来自 `APP_VERSION`，容器内覆盖 `MYSQL_HOST=mysql` 和 `MYSQL_PORT=3306`，等待 MySQL 健康，提供 API 健康检查，只向宿主机回环地址映射端口，并通过 `enterprise-fastapi` 别名加入 `enterprise-shared` 外部网络。真实 `.env` 未输出，示例环境和当前环境的 `docker compose config --quiet` 均通过。

**本机 Compose 状态：已验证。** 因宿主机已有调试进程占用 8000，本轮使用 `API_PORT=8001` 构建并启动 `enterprise-fastapi:0.2.0`；MySQL 与 API 均为 `healthy`。`docker compose run --rm --no-deps api alembic -c alembic.ini upgrade head` 成功连接 MySQL；`GET /health` 返回 `{"status":"ok"}`；幂等键 `compose-step1-20260930` 的真实请求返回 HTTP 201，并在 `workflow_run` 查到 `DEPLOY001 / compose_validation / accepted`。临时容器通过 `enterprise-shared` 请求 `http://enterprise-fastapi:8000/health` 同样成功，证明外部网络别名可用；8 个自动化测试仍全部通过。

**远程部署状态：待验证。** Compose 与本机端口拆分改动已经提交并推送到 `origin/main`，但尚未在服务器拉取和执行。下一步按以下顺序实施：

1. 服务器更新仓库到提交 `6e54e55`，基于 `.env.example` 创建不入库的 `.env` 并替换示例密码。
2. 创建一次性外部网络 `enterprise-shared`，再依次执行 `docker compose up -d --wait mysql`、`docker compose build api`、容器化 Alembic 迁移和 `docker compose up -d api`。
3. 在 n8n 的 Compose 中声明同一个外部网络；首次联调也可手工把 `n8n-n8n-1` 接入。
4. n8n 改为调用 `http://enterprise-fastapi:8000/workflow/run`。
5. 依次验证 `/health`、真实 `POST /workflow/run`、MySQL 记录以及 n8n Webhook 的完整响应。`/health` 当前不访问数据库，不能代替迁移和落库验证。

为了避免暴露内部 API，当前 Compose 已把 FastAPI 限制为 `127.0.0.1:${API_PORT}:8000` 供宿主机诊断；n8n 通过共享 Docker Network 访问容器端口，不需要在云安全组开放公网 8000。API 侧共享网络已经持久化到 Compose；n8n 侧仍需在服务器的 Compose 中补充同一外部网络。

**MySQL 端口拆分：已验证。** 2026-09-30 公共 `compose.yml` 已删除 `mysql.ports`，新增 `compose.local.yml` 为 Mac 追加 `127.0.0.1:${MYSQL_PORT:-3306}:3306`。两份配置分别通过 `docker compose config --quiet`；解析后的公共配置端口列表为 `[]`，Mac 合并配置准确生成回环地址映射。用合并配置执行 `up -d mysql` 后，`enterprise-ai-mysql` 仍为 `healthy`，仍挂载 `enterprise-ai-automation_mysql_data:/var/lib/mysql`，此前幂等键 `compose-step1-20260930` 的数据库记录计数仍为 1。服务器只使用公共配置，Mac 使用两份配置；本轮删除的是宿主机端口发布规则，不是 MySQL 服务、容器定义或数据卷。

### 2.3 V1 落地顺序（计划中）

1. 需求口径已在基线文档中冻结；下一迭代生成约 60 天的可复现双 Sheet Excel 和异常标准答案，并先用纯 Python 完成解析、行级校验、指标、`rolling_7d` 基线和规则单元测试。
2. 增加电商导入 API、行级校验、文件哈希与数据版本；通过 Alembic 建立店铺/SKU 日事实表。相同文件重试与同一天修订数据必须分开处理。
3. 用确定性代码计算指标、前 7 个有效日基线和异常，并记录规则版本。日退款金额与当日 GMV 的比值需标明日期口径；分母为零和基线不足时不强行报警。
4. 先打通无 AI 的最小闭环：可查询的运行步骤与结果、报告草稿、人工审核、任务创建和状态更新；再接入结构化 AI 报告、n8n 单渠道通知和通知幂等/重试。
5. 补真实 MySQL 集成测试及端到端验证。当前 `workflow_run` 只会落为 `accepted`，`workflow_step_run` 尚无写入路径；人工审核、通知和任务状态应与批处理运行状态分别维护。

当前只推进第 1 项作为下一个可验收交付物。完成标准是：同一随机种子可重建相同测试文件；错误数据能定位到 Sheet、行和字段；公式、7 日基线、历史不足、分母为零和预置异常都有确定性测试。该阶段不接 AI、n8n，也不先设计全部业务表，避免在数据口径尚未被代码和测试证明时扩大返工范围。

### 2.4 开源项目借鉴（计划中）

- [ecommerce-automation-agent](https://github.com/w1tv/ecommerce-automation-agent)：已核对实际代码。订单抓取先按状态构造列表 URL，默认只取待发货，再按订单号哈希排除最近 7 天已抓取订单，最后限制最大数量。退款规则按“人工审核 → 自动同意 → 自动拒绝 → 跳过”的优先级判断。该仓库配置名与实现不完全一致：配置中的 `refund_only`、`auto_approve_reasons` 没有被判断代码使用，而且 `fetch()` 最终返回未去重的 `orders`，因此只能借鉴规则思路，不能原样复制到本项目。
- [Retail KPI Root-Cause Analysis](https://github.com/AarontheGalaxy/Retail-KPI-Root-Cause-Analysis)：已核对仓库实际包含 `main.py`、`src/data_generator.py`、`src/db_loader.py`、`src/analyzer.py` 和测试。借鉴“可复现合成数据 → 入库 → 指标/异常分析 → 报告”的分步组织及已知异常测试；本项目需替换为日级双 Sheet Excel、前 7 个有效日基线和 MySQL 持久化。该示例通过删表重建重复运行，且报告直接把销量下降写成物流原因；这些做法不适用于需要保留历史版本和区分“事实/待验证假设”的 V1。
- [FastAPI Best Architecture（Gitee）](https://gitee.com/fastapi-practices/fastapi-best-architecture)：已核对仓库的 `api`、`schema`、`service`、`crud`、`model` 等目录与[项目文档](https://fastapi-practices.github.io/fastapi_best_architecture_docs/backend/summary/intro.html)。借鉴层间职责，保持当前 `workflows/router.py`、`schemas.py`、`service.py` 和 ORM 模型的轻量结构；只有查询复杂到需要复用时才增加 CRUD 层。该仓库是通用后台架构，不提供电商指标、人工审核和异常处置闭环。

### 3. 当前运行态与版本注意事项

当前磁盘源码版本为 `0.2.0`。2026-09-25 已重新启动 Docker Desktop 和 MySQL 8.4，并直接运行当前工作区源码完成在线复验：数据库迁移处于 `20260920_0001 (head)`，`alembic check` 无差异，8 个自动化测试通过，`pip check` 和 `compileall` 通过，OpenAPI 只有 `/health` 与 `/workflow/run` 两条业务路径。

## 三、按运行流程阅读与调试

### 1. 先固定被调试的版本

如果 8000 端口被其他进程占用，调试磁盘上的 `0.2.0` 源码时使用独立端口：

```bash
.venv/bin/uvicorn --app-dir fastapi app.main:app --reload --port 8001
```

然后只请求 `http://127.0.0.1:8001`，并可在 `/docs` 中手工发送请求。这样才能保证运行行为与编辑器里打开的代码一致。

### 2. 当前 API 请求链的打开顺序

1. `fastapi/app/main.py`：确认应用版本以及 `workflow_router` 已注册。
2. `fastapi/app/workflows/schemas.py`：检查 HTTP 输入校验与响应字段。
3. `fastapi/app/workflows/router.py`：检查 Header、Session 依赖、HTTP 状态码和异常转换。
4. `fastapi/app/db/session.py` 的 `get_db()`：确认请求级 Session 被创建并最终关闭。
5. `fastapi/app/workflows/service.py`：检查幂等查询、并发冲突回查、对象创建和事务边界。
6. `fastapi/app/models/workflow_run.py`：确认 ORM 字段、唯一约束和索引。
7. Router 的 `WorkflowRunResponse`：确认 ORM 对象如何转换为 HTTP JSON。

建议断点依次放在 Router 的 `run_workflow()`、Service 的 `create_workflow_run()`、首次幂等查询、`WorkflowRun(...)` 对象创建、`commit()`、唯一约束冲突后的回查和 Router 最终返回处。

有效输入：

```json
{"user_id":"HR001","task_type":"attendance","department":"生产部"}
```

请求还必须提供长度为 8～128 的 `Idempotency-Key` 请求头。首次请求预期返回 HTTP 201、随机 `run_id`、原样返回的三个字段、`"status":"accepted"` 和数据库创建时间。缺少字段或幂等键时返回 422，并且路由函数不会命中。

### 3. 数据库地基的打开顺序

数据库问题单独按下面顺序检查：

1. `compose.yml`：MySQL 是否启动、端口如何映射、环境变量从哪里注入。
2. `.env.example` 与本地 `.env` 的变量名：只检查变量是否存在，不在日志或笔记中输出密码。
3. `fastapi/app/core/config.py`：输入是环境变量，输出是 `Settings` 和 SQLAlchemy `database_url`。
4. `fastapi/app/db/session.py`：输入是 `database_url`，输出是 Engine、`SessionLocal` 和请求级 `get_db()`。
5. `fastapi/app/models/workflow_run.py`：检查整次工作流要写入哪些字段、约束和索引。
6. `fastapi/app/models/workflow_step_run.py`：检查步骤、重试、耗时和错误如何关联到整次运行。
7. `fastapi/migrations/versions/20260920_0001_create_workflow_tables.py`：检查实际建表结构是否与 ORM 模型一致。
8. `fastapi/migrations/env.py`：检查 Alembic 如何读取配置、导入模型并连接数据库。

在 `get_db()` 创建 Session 的位置放断点，当前 `/workflow/run` 请求应当命中；随后能继续跟到 `add()`、`commit()` 和 `refresh()`。

### 4. 按症状快速定位

| 症状 | 先看哪里 | 判断重点 |
| --- | --- | --- |
| 服务启动失败或模块找不到 | `README.md` 启动命令、`app/main.py`、`requirements.txt` | `--app-dir fastapi app.main:app` 是否正确 |
| 返回 422 | `WorkflowRequest` 与发送的 JSON | 字段名、缺失字段、数据类型；此时还没进入路由函数 |
| 返回 404/405 | 路由装饰器与请求 URL/方法 | 当前应为 `POST /workflow/run` |
| 路由断点不命中但响应结构更复杂 | 请求端口、运行容器 | 很可能请求到了 8000 端口的旧镜像 |
| 返回 200 和 `Idempotent-Replay: true` | 幂等查询分支 | 同一个幂等键与相同请求返回已有记录，不会重复插入 |
| 返回 409 | 幂等键和请求内容 | 同一个幂等键被用于不同请求，或唯一约束发生冲突 |
| 返回 500 | `commit()` 异常分支和服务日志 | 数据库操作失败，接口会先 `rollback()` 再返回错误 |
| MySQL 连接失败 | `compose.yml` → `.env` → `config.py` → `session.py` | 容器健康、host/port/user/database 是否匹配 |
| 表不存在或字段不一致 | ORM 模型 → Alembic 迁移 → 数据库实际结构 | `alembic current` 与 `alembic check` 的结果 |

调试时每经过一层都记录四件事：输入是什么、输出是什么、是否真的进入这一层、异常在哪一层首次出现。不要从最终错误直接跳到最底层猜原因。
