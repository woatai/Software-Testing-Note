### 办公流程自动化、运营自动化与工业自动化

制造企业里的简历筛选、表格清洗、生产例会纪要和跨平台提醒，属于**办公流程自动化**，不等于由 PLC、传感器、机械臂和 SCADA/MES 参与的**工业自动化**。电商运营自动化与前者是同一类软件工作流，只是业务对象不同。

| 类型 | 主要对象 | 例子 | 典型风险 |
| --- | --- | --- | --- |
| 电商运营自动化 | 商品、订单、流量、广告、库存、评价 | 异常日报、商品内容质检、售后分流 | 错误结论、重复通知、误操作业务数据 |
| 制造企业办公自动化 | 简历、工资表、会议记录、通知 | 简历筛选、表格清洗、会议待办提取 | 隐私泄露、计算错误、遗漏待办 |
| 工业自动化 | 设备、产线、实时信号和控制指令 | 设备控制、产线联动、故障停机 | 人身与设备安全、实时性和高可用 |

前两类共享同一套软件工作流骨架：`触发/采集 → 校验与标准化 → 规则或 AI 处理 → 人工审批或系统动作 → 状态持久化与审计 → 通知和反馈`。可复用的是接口、幂等、状态机、步骤记录、重试、权限和日志；需要按领域替换的是输入 Schema、业务规则、模型提示、外部连接器和测试集。

项目设计应当“需求层面具体、架构层面可复用”：先用一个自己熟悉且能获得测试数据的真实场景完成闭环，再用第二个工作流证明通用能力，不要一开始把产品定义成没有明确成功标准的万能自动化平台。

### 单入口订单数据清洗流程

**清洗函数**可以作为一次处理任务的单一入口：接收输入文件路径和输出文件路径，依次读取订单、统一可确定的格式、标记异常并写出结果。异常检查遇到无法安全推断正确值的记录时，应保留原始行号和原因，例如数量为空、非数字或小于等于 0。对当前一次性练习，先用一个 `clean_orders(input_path, output_path)` 函数写清流程；规则增多或需要复用时再考虑拆分内部步骤。

**表结构校验**检查所需列是否存在；**字段值校验**检查每行的值是否符合类型、取值范围和业务规则；**格式标准化**只修正可确定的表示差异，例如去掉状态文字首尾空格；**业务筛选**从已经可用的数据中选出本次流程需要处理的记录，例如只保留“已支付且未发货”的订单。四者可以同属数据预处理流程，但职责不同。当前 `clean_orders` 已实现必需列检查、状态文字标准化、数量和金额的逐行校验，以及同一 Excel 内的重复识别与异常标记；日期、状态合法值和业务筛选仍未实现。

**文件内去重**先选业务键，再比较同键记录的内容：同一订单号且内容相同的后续行可按明确规则删除；同号但内容不同可能是商品明细或订单更新，应保留并核对。空订单号不能作为去重键。**跨次抓取去重**还需持久化已处理订单号及处理范围；仅在一次清洗函数内用集合或字典，无法识别下次运行的旧订单。当前项目默认保留重复行并标记异常，显式开启 `drop_exact_duplicates=True` 才从输出 JSON 删除完全相同的后续行；这里不需要为订单号计算哈希。

验证清洗结果不能只看程序是否成功运行，还要同时检查：输入总数能与正常记录和异常记录对上；只有规则允许的字段发生变化；每条异常保留原始行号、原值和原因；原始文件未被修改。再用专门包含空值、非数字、零、负数、重复值和边界值的小样本逐条验证规则，最后抽查真实文件的清洗前后差异。

影刀订单练习的当前流程为 `读取原始 Excel（第 2 行表头）→ 状态、数量和金额格式标准化 → 数量、金额及重复记录校验 → 输出带清洗状态和异常原因的 JSON`。已验证当前 303 条练习数据中有 292 条正常、11 条异常：6 条数量或金额异常、2 条空订单号、3 条完全重复的后续行。影刀调用入口及日期、状态合法值等规则仍为`计划中`。常见误解是把所有“看起来不一致”的值直接改掉或删掉；实付小于总价可能来自优惠，重复订单号也要结合记录粒度和整行内容判断。

### Python 常用容器：列表、元组、集合、字典

| 类型 | 示例 | 关键特点 | 订单场景 |
| --- | --- | --- | --- |
| 列表 `list` | `["A001", "A002", "A001"]` | 有顺序、可重复、可增删改 | 保存按原顺序读取的订单号 |
| 元组 `tuple` | `("支付状态", "订单状态")` | 有顺序、可重复；创建后不能替换、增加或删除其中的元素 | 保存固定要处理的列名 |
| 集合 `set` | `{"订单号", "支付状态"}` | 元素不重复；支持差集等运算，不按位置取值 | 查找缺失列、对订单号去重 |
| 字典 `dict` | `{"订单号": "A001", "状态": "待收货"}` | 每个键对应一个值，键不能重复 | 表示一条订单的字段和值 |

列表可以用内置函数 `len()` 计算元素个数，返回一个整数。例如 `orders = ["A001", "A002", "A001"]`，`len(orders)` 返回 `3`；`len([])` 返回 `0`。`len()` 统计的是最外层元素数量，因此 `len([["A001", "A002"], ["A003"]])` 返回 `2`，不会递归统计内层一共有多少项。Python 列表没有 JavaScript 风格的 `.length` 属性，应写 `len(orders)`。

元组本身不会保证元素唯一：`("订单号", "订单号")` 合法；`set(("订单号", "订单号"))` 才会得到只含一个订单号的集合。元组也不能原地增删改，例如 `fields[0] = "新列名"` 会报错；`fields = fields + ("数量",)` 是创建新元组并让变量重新指向它。若元组中放了列表，仍可修改那个列表的内容，但不能替换元组的对应位置。空字典写 `{}`，空集合写 `set()`。

项目中的 `required_columns - set(orders.columns)` 先把 pandas 列名转换为集合，再用差集找出必需但缺失的列；这里的 `set(...)` 不是字典。

订单清洗时可用 `list[dict]` 表示内存中的数据：一个字典是一条订单，列表保存全部订单并维持行顺序。`order["支付状态"]` 可以直接取值或修改；`json.dumps(orders, ensure_ascii=False)` 才把这些 Python 数据写成 JSON 文本。JSON 中的“对象”对应 Python 字典，但 JSON 文件本身不是正在运行的 Python 对象。若字段和约束稳定，也可像 [ecommerce-automation-agent 的 `OrderInfo`](https://github.com/w1tv/ecommerce-automation-agent/blob/main/core/order_fetcher.py) 那样先定义数据类，再用 `asdict()` 转成字典保存。

字典列表是可选的中间表示，不是输出 JSON 的必经步骤。当前项目直接在 pandas `DataFrame` 中标准化字段，并为每行维护异常原因列表，再用 `to_json(orient="records")` 写成订单对象数组；需要更复杂的跨字段判断或领域行为时，再定义订单数据类更有价值。

### Python 包导入与测试运行目录

`ModuleNotFoundError: No module named 'app'` 表示 Python 当前的模块搜索路径中找不到 `app` 包，不代表 `app` 文件不存在。此项目的包位于 `fastapi/app/`；从仓库根目录直接执行 `fastapi/tests/test_order_cleaning.py` 时，测试文件所在的 `fastapi/tests/` 会进入搜索路径，而 `fastapi/` 不会因此自动进入。进入 `fastapi/` 后用 `../.venv/bin/python -m pytest -q tests/test_order_cleaning.py` 运行，已验证 2 个测试通过。通用做法是从包含目标包的目录运行测试，或明确设置 `PYTHONPATH=fastapi`；`python -m pytest` 还会把当前工作目录作为模块搜索起点。

### 测试输出与指定目录

清洗结果写到哪里由调用 `clean_orders(input_path, output_path)` 时传入的 `output_path` 决定；函数返回输出路径，不会自动打印 JSON。当前 `test_clean_orders_uses_local_excel_without_changing_it` 直接指定 `/Users/Admin/Downloads/订单列表_清洗后.json`，运行测试就会覆盖该文件，并从同一路径读回校验。测试不需要临时目录时，可以不声明 `tmp_path` 参数。

若测试需要隔离输出，`tmp_path` 是 pytest 可选的内置 fixture：pytest 根据形参名字查找同名 fixture，创建该测试专用的临时目录，再把表示目录的 `Path` 对象传入。触发注入的是形参名 `tmp_path`，不是后面的 `: Path` 类型注解。直接在普通 Python 代码里调用带该参数的测试函数时没有 pytest 参与，因此必须自己传入参数。

## 二、ORM 模型

ORM（Object-Relational Mapping，对象关系映射）模型是“Python 对象与关系型数据库表之间的映射规则”，让应用可以主要通过类、对象和属性操作数据，而不必为每次读写都手写 SQL。

| Python/SQLAlchemy | MySQL |
| --- | --- |
| `WorkflowRun` 类 | `workflow_run` 表 |
| 一个 `WorkflowRun(...)` 对象 | 表中的一行记录 |
| `run.status` 属性 | `status` 列 |
| `run.steps` 关系属性 | 通过外键关联的多行步骤记录 |

在典型请求链中的位置：

`HTTP JSON` → Pydantic 请求模型 → 业务逻辑 → ORM 对象 → SQLAlchemy Session → MySQL 行记录

Pydantic 模型和 ORM 模型不要混淆：

- Pydantic 模型负责校验和整理 API 输入输出，数据可以只存在于内存中。
- ORM 模型负责描述数据库表、列、约束和表关系，并参与数据库查询与持久化。

创建 ORM 对象不等于已经写入数据库。通常还要经过：

```python
db.add(run)     # 放入当前 Session
db.commit()     # 提交事务，才真正持久化
db.refresh(run) # 重新读取数据库生成或更新的值
```

ORM 模型也不等于建表脚本。SQLAlchemy 模型描述应用期望的结构；在 `enterprise-ai-automation` 中，实际表结构通过 Alembic 迁移创建和演进，不在应用启动时自动 `create_all()`。

项目映射：

- `WorkflowRequest` 是 Pydantic 请求模型，只负责 `/workflow/run` 的输入校验。
- `WorkflowRun` 是 ORM 模型，对应一次完整工作流的 `workflow_run` 表记录。
- `WorkflowStepRun` 是 ORM 模型，对应某一步及某次重试的 `workflow_step_run` 表记录。
- 当前接口已经创建 `WorkflowRun` ORM 对象并执行 `add()`、`commit()` 和 `refresh()`；真实落库证据见 [[01_AI应用项目实践]]。

### 数据库迁移与 n8n 集成

**数据库迁移**是用带版本的脚本修改本应用数据库结构，例如创建表、增加列或索引；它位于“ORM 模型设计 → Alembic 迁移 → MySQL 表结构”的链路。**n8n 集成**则是 FastAPI 与 n8n 通过 HTTP/Webhook 交换任务和执行结果，属于运行时的跨系统通信。前者准备好存放运行记录的表，后者才会真正触发工作流并回写状态。

项目中的首个迁移创建了 `workflow_run`、`workflow_step_run`，并预留 `n8n_execution_id` 字段；这只提供存储位置，不表示已连接 n8n。当前 `/workflow/run` 只保存 `accepted` 记录，n8n 调用、回调和步骤状态更新仍为 `计划中`。常见误解是“表里有 n8n 字段就完成了集成”；判断是否接通，应检查真实调用、回调和持久化结果。

### n8n 节点连接与最小 HTTP 闭环

**n8n 节点**是工作流中的一个可执行步骤；触发器接收外部事件，普通节点读取上一步输出并产生下一步输入。节点右侧的 `+` 会在当前输出端创建并自动连线，和把新节点拖到连线上是同一个核心动作：先确定数据从哪里来，再决定下一步由谁处理。

最小 HTTP 闭环可以理解为：

`Webhook(POST 接收 JSON) → HTTP Request(POST 调 FastAPI) → FastAPI 校验/落库 → HTTP 响应返回 Webhook 调用方`

#### Webhook 与 HTTP Request 的职责

`Webhook` 是入站触发器，像工作流的“前门”：它监听一个 URL，外部系统发送 POST 请求后，n8n 才开始执行。它主要负责接收请求，不负责调用 FastAPI。请求数据通常分成 `body`、`headers`、`query` 等部分；本项目的业务字段在 `$json.body` 中。

`HTTP Request` 是出站动作，像工作流的“客户端”：它按照配置向另一个 HTTP 服务发请求，支持选择方法、URL、请求头、查询参数和请求体。它会把上游输入通过表达式组装成下游 API 需要的格式，并把对方的响应作为自己的输出交给后续节点。

两者可以独立使用，但常见组合是“Webhook 接收事件，HTTP Request 调业务 API”。本项目中，`{{$json.body.user_id}}` 表示读取 Webhook 的输入，`n8n-{{$execution.id}}` 表示为本次 n8n 执行生成幂等键；若上游节点改变了输出结构，表达式也必须跟着实际输入 JSON 调整。

在 n8n 的 Webhook 输入中，POST JSON 通常位于 `$json.body`，因此下游字段映射写成 `{{$json.body.user_id}}`、`{{$json.body.task_type}}` 和 `{{$json.body.department}}`。HTTP Request 还要发送 `Content-Type: application/json`，并用 `n8n-{{$execution.id}}` 生成本次执行的幂等键；Webhook 的 `Respond` 设为 `When Last Node Finishes`，调用方才能收到最后一个节点的返回数据。

常见误解是“画布上有一条连线就已经闭环”。连线只说明数据流向；真正闭环还必须同时满足：下游 URL 从 n8n 所在环境可达、请求体与 FastAPI Schema 一致、幂等键满足接口约束、触发器配置了返回策略，并且用一次真实执行检查 HTTP 状态和数据库状态。当前项目的 `/workflow/run` 只代表创建 `accepted` 运行记录，不代表电商日报已经执行完成。

项目映射：2026-09-29 已在远程 n8n 画布保存最小链路 `Webhook → HTTP Request` 及上述字段映射；本机当前 FastAPI 已验证返回 200/201，但远程 n8n 到 `132.226.73.129:8000` 的端口连通性仍待部署或网络配置后验证，所以不能把这次配置称为端到端完成。另一个部署细节是：Webhook 面板显示的生产 URL 仍是 `http://localhost:5678/webhook/...`，说明 n8n 的对外基址配置尚未设置；外部调用时应使用服务器地址，长期应配置正确的 n8n host/editor URL。

### 本机、服务器与 Docker 容器中的 `localhost`

`localhost` 和 `127.0.0.1` 永远表示“当前进程所在的机器或网络命名空间”，不是某个固定的开发环境。本机 FastAPI 的 `127.0.0.1:8000` 只属于本机；服务器公网 IP 指向服务器；容器里的 `127.0.0.1` 又只指向该容器本身。因此，本机能够 SSH 或访问服务器，不代表服务器能反向访问本机进程；FastAPI 若只在 Mac 上运行，服务器中的 n8n 请求服务器 IP 的 8000 端口仍会失败。

同一台服务器上的容器应优先通过用户自定义 Docker Network 和容器名通信，例如：

`n8n --http://enterprise-fastapi:8000--> FastAPI --mysql:3306--> MySQL`

这里 `enterprise-fastapi` 和 `mysql` 由 Docker 内置 DNS 解析，不需要把容器内部请求绕到公网 IP。FastAPI 的 8000 端口可以只映射到服务器 `127.0.0.1` 供本机诊断，n8n 仍通过共享网络访问容器端口；这样通常无需在云安全组开放公网 8000。常见误解是把 API 容器里的 `MYSQL_HOST=127.0.0.1` 当作宿主机或数据库容器，正确值应是 API 所在 Docker Network 中的 MySQL 服务名。

部署完成至少要依次验证：容器仍在运行、FastAPI 进程健康、Alembic 已迁移、真实业务请求能写入 MySQL、n8n 能从自己的网络访问 FastAPI。当前 `/health` 只返回进程状态，不访问数据库，所以它成功不能单独证明数据库连接或表结构正常。

#### 容器端口与宿主机端口映射

Compose 中删除 MySQL 的 `ports: - "127.0.0.1:3306:3306"`，只会取消“宿主机 3306 → MySQL 容器 3306”的发布规则，不会关闭 MySQL 容器内部的 3306，也不会影响同一 Docker Network 中的 FastAPI 通过 `mysql:3306` 访问它。公共/服务器 Compose 可以不发布数据库端口；Mac 如果需要 Navicat 或宿主机 Uvicorn 直连数据库，可用单独的 `compose.local.yml` 补回回环地址映射。

修改 Compose 文件也不会自动改变已经创建的容器。必须用包含目标配置的 `docker compose up -d` 让 Compose 重建受影响服务，再通过 `docker compose ps` 或容器检查确认运行态；验证配置文件和验证现有容器是两件事。

### 容器化项目怎样持续更新

Docker 部署不是把初版代码永久封在服务器里，而是把每个可发布版本构建成新镜像，再用新容器替换旧的应用容器。典型链路是：`本地开发与测试 → Git 提交并推送 → 服务器拉取代码 → 构建新镜像 → 执行 Alembic 迁移 → 重建 FastAPI 容器 → 健康检查和真实请求验证`。

更新时要区分改动类型：

| 改动 | 更新动作 |
| --- | --- |
| Python 业务代码或依赖 | 重新构建镜像并重建 FastAPI 容器 |
| ORM 字段、表、索引 | 先生成和评审 Alembic 迁移，再在服务器执行迁移，然后发布兼容的新应用 |
| 环境变量 | 修改服务器 `.env` 并重建读取它的容器 |
| n8n 工作流 | 单独更新、测试和发布 n8n 工作流；不等于更新 FastAPI |
| MySQL 数据 | 保存在命名数据卷中，正常替换 FastAPI 容器不会删除；不要把 `docker compose down -v` 当作日常更新命令 |

应用容器应被视为可替换的运行实例，数据库数据卷才是需要持续保留的状态。开发阶段也应使用版本化镜像并保留上一个可用版本，发布失败时才能回到旧应用；如果新版本已经执行了不向后兼容的数据库迁移，单独回滚应用镜像可能仍然失败，因此数据库变更应优先采用兼容式分步迁移。

镜像清理不应等同于“每次发布都删除全部旧镜像”。旧的停止容器通常可以在确认新版本正常后删除；镜像建议至少保留当前版本和一个上一稳定版本，其余不再被容器引用的历史版本再定期清理。`docker image prune` 默认只清理悬空镜像；`docker image prune -a` 会删除所有未被容器引用的镜像，可能连准备回滚的版本一起删除，执行前必须检查。不要在日常镜像清理中使用带 `--volumes` 的系统级清理，因为数据卷与可重建的镜像不是同一类资产。

#### 从手工发布到企业 CI/CD

版本化镜像、数据库迁移、替换容器、验证和回滚符合企业发布的底层机制，但长期由开发者 SSH 到生产服务器执行 `git pull` 和 `docker build`，只适合原型或小团队早期阶段。成熟流程通常是：`提交/合并代码 → CI 自动测试与检查 → 只构建一次带版本或提交号的镜像 → 推送镜像仓库 → 部署到测试环境 → 验证或审批 → 生产环境拉取同一个镜像 → 迁移、健康检查、监控与回滚`。

企业化的关键不是必须使用 Kubernetes，而是发布过程可重复、可审计、可回滚并且环境隔离。单服务器 Docker Compose 也可以承载小规模正式服务，但应逐步具备：CI 构建与测试、镜像仓库、开发/测试/生产配置分离、Secret 管理、迁移评审和备份、健康检查、日志与告警，以及明确的回滚版本。只有服务数量、流量、高可用和滚动发布需求明显增加后，才需要评估 Kubernetes 等编排平台。

项目映射：当前仓库已经把 FastAPI、健康检查、MySQL 依赖和 `enterprise-shared` 外部网络写入 Compose，并完成本机构建、迁移、启动、真实写库和共享网络别名验证。之后日常发布可收敛为构建 API、执行迁移、重建 API、验证四个步骤，而 MySQL 和 n8n 无需随每次 API 代码改动一起重建；远程服务器部署和 n8n 接入该外部网络仍为 `待验证`。

## 三、FastAPI 接口写入数据库

接口落库的核心链路是：

`HTTP JSON/Headers` → Pydantic 校验 → `Depends(get_db)` 注入 Session → 创建 ORM 对象 → `add()` → `commit()` → `refresh()` → 返回响应

各步骤的输入输出：

| 步骤 | 输入 | 输出 |
| --- | --- | --- |
| Pydantic 校验 | HTTP JSON | 经过校验的 Python 对象 |
| `get_db()` | 数据库配置和连接池 | 本次请求使用的 Session |
| 创建 ORM 对象 | 请求对象和业务生成字段 | 尚未持久化的 Python 对象 |
| `db.add(obj)` | ORM 对象 | 对象加入当前 Session，不代表已提交 |
| `db.commit()` | 当前事务中的变更 | 执行并提交 `INSERT`；成功后数据才持久化 |
| `db.refresh(obj)` | 已提交对象 | 数据库中的主键、默认时间等最新值 |
| 返回响应 | 已持久化对象 | HTTP JSON |

事务失败时需要 `db.rollback()`，把 Session 从失败状态恢复，再把合适的错误转换为 HTTP 响应。`get_db()` 的 `finally` 负责请求结束后关闭 Session，但关闭 Session 不能替代业务代码对已捕获数据库异常的显式回滚。

`enterprise-ai-automation` 已实现并验证这条落库链路：`/workflow/run` 通过 `Depends(get_db)` 接收 Session，用请求数据构造 `WorkflowRun`，提交后返回 `run_id`、数据库状态和创建时间。接口通过 `Idempotency-Key` 请求头接收调用方提供的稳定幂等键；同键同请求返回原记录，同键不同请求返回 409。

Service 的幂等处理先按键查询已有记录：同键同输入返回原记录并标记 `replayed=True`，同键不同输入抛冲突异常；查不到才生成 `run_id` 并写入 `accepted` 记录。仅靠“先查再写”挡不住两个请求同时查不到的情况，因此 `workflow_run.idempotency_key` 还有数据库唯一约束；发生并发唯一约束冲突时，Service 回滚并重新查询，再按相同输入重放或不同输入冲突处理。Service 返回记录和重放标记，Router 才决定 HTTP 状态码。

异常处理分两层：`IntegrityError` 是 `SQLAlchemyError` 的子类，先捕获它以尝试处理并发唯一约束冲突；其他数据库错误由后面的 `SQLAlchemyError` 分支回滚并转为 `WorkflowPersistenceError`。回滚只撤销本次失败事务，不会撤销另一请求已提交的记录；回查失败或查不到对应幂等键时不能假定发生了正常重放，应报持久化失败。`raise 新异常 from 原异常` 会保留异常原因链，方便定位底层错误。

异常处理原则：预计某段操作可能失败，且当前层能恢复、清理资源或转换为本层有意义的错误时，才用尽量小的 `try` 和具体的 `except`；无法处理时让异常继续向上。程序发现业务规则不允许继续（如同键不同输入）时主动 `raise` 领域异常；Router 再将领域异常映射为 HTTP 状态。`finally` 适合无论成功失败都必须执行的清理。不要用宽泛的 `except Exception: pass` 隐藏未知错误，也不要把正常的“查询无结果”一律当作异常。

`Annotated` 不是函数，而是 Python `typing` 提供的类型注解形式：`Annotated[类型, 附加信息]`。它本身不读取请求，也不调用数据库函数；FastAPI 读取附加信息后，才在处理请求时执行相应操作。在 Router 中，`Annotated[Session, Depends(get_db)]` 表示由 FastAPI 为本次请求注入数据库 Session；`Annotated[str, Header(alias="Idempotency-Key", min_length=8, max_length=128)]` 表示从请求头取必填的幂等键并校验长度。`response_model` 规定对外 JSON 字段，即使函数内部返回的是 ORM 对象，也只按响应模型序列化。首次创建默认返回 201；同键同内容重放改为 200 并设置 `Idempotent-Replay: true`；同键不同内容由 Router 映射为 409，持久化失败映射为 500。缺少必填输入或长度不合要求时，FastAPI 在进入路由函数前返回 422。

项目已经统一第一阶段状态语义：接口只完成“接收并落库”时写入 `accepted`；真实业务执行完成后再更新为 `succeeded`。数据库约束允许 `accepted`、`running`、`succeeded`、`failed`、`cancelled`、`timed_out`。

## 四、FastAPI 业务分层与领域组织

业务分层的目标不是增加目录数量，而是让每一层只因一种原因变化。最小可用链路是：

`HTTP 请求` → `Router` → `Service` → `SQLAlchemy Session / ORM` → `数据库`

| 位置 | 主要职责 | 不应承担 |
| --- | --- | --- |
| `main.py` | 创建 FastAPI、注册 Router、中间件和生命周期 | 具体业务规则、SQL、事务分支 |
| `router.py` | 解析 HTTP 输入、调用 Service、声明响应 | 拼 SQL、编排复杂状态、直接处理所有数据库异常 |
| `schemas.py` | Pydantic 输入输出及字段级校验 | 依赖数据库的业务判断 |
| `service.py` | 业务规则、事务边界、幂等、状态转换 | FastAPI `Response`、Header 等传输层细节 |
| `models.py` | ORM 表、关系、约束、索引 | HTTP 响应格式 |
| `client.py` | n8n、模型供应商等外部系统调用 | 本项目的核心业务规则 |

项目很小时，按文件类型建立全局 `routers/`、`schemas/`、`models/`、`services/` 可以工作；业务领域增多后，更适合按领域形成 `workflows/`、`auth/` 等包，每个领域内部再放自己的 Router、Schema、Model 和 Service。这样一次业务修改集中在同一目录，跨领域依赖也更明确。

常见误区：

- 多一层 Repository 不一定更专业。只有查询明显复杂、需要复用，或存在多种存储实现时再引入；简单 SQLAlchemy 查询可先由 Service 持有。
- `async def` 不自动等于高性能。同步 PyMySQL 配合同步路由是自洽方案；如果切换为异步路由，应同时使用支持 `await` 的数据库和 HTTP 客户端，不能在事件循环中直接执行阻塞 I/O。
- 进程内 `BackgroundTasks` 不是可靠工作队列。需要重试、可见性、调度或不能丢失的任务，应交给 n8n 或 Celery、Arq、RQ 等独立执行机制。

`enterprise-ai-automation` 当前只有工作流一个业务领域，适合先形成一个轻量 `workflows/` 领域包；不需要立即引入完整 DDD、Repository 接口或 Celery。参考：[FastAPI Best Practices](https://github.com/zhanymkanov/fastapi-best-practices)。
